## 愿景与终态

### 愿景

**让一个人拥有一支可随业务增长与变化而扩展、调整的智能团队，把个人的目标、判断和经验转化为持续、可靠、可积累的交付能力；公司的行动与交付能力不再受个人时间和精力的线性限制，而方向、质量、风险和最终责任始终由人掌握。**

「一人公司」不是一个人亲自完成所有工作，也不是无人值守的公司。人承担经营者和最终负责人的角色，适合委派的工作由不同能力的 Agent 承接，人从重复执行、协调和盯进度中逐步解放出来。

### 最终要达成的效果

1. **经营目标和结果**：人判断什么值得做、定义目标与标准、处理关键取舍、验收经营结果，不再充当任务分配员、进度管理员和信息中转站。
2. **超越个人工时的交付能力**：多项有价值的事情可以并行推进；业务规模扩大时，个人的沟通、协调和管理投入不等比例增加。
3. **可靠结果而非 Agent 活动**：真实问题得到解决，成果符合质量要求、可验证和可使用，并形成实际业务价值。
4. **全局掌控与例外处理**：正常推进时不持续打扰人；人的注意力集中于关键决策、重要风险、异常阻塞和最终验收。
5. **经验成为公司资产**：业务理解、有效方法、重要决策及原因、质量标准和失败经验能够持续复用，不依赖某一次对话或某一个 Agent。
6. **自动化与责任边界并存**：方向由人选择，价值由人判断，重大风险由人决策，最终结果由人负责。
7. **组织能力随业务生长**：业务增长或变化时可以扩充、调整智能体；新增能力继承公司的背景、经验和质量标准，而不是增加孤立工具和管理负担。

### 经营成效判据

- **有效交付增加**：更多真正有价值、符合验收标准的事情完成。
- **个人经营负担下降**：减少协调、追问、重复解释、上下文切换和无效返工。
- **组织能力持续积累**：经验可复用、决策有迹可循，同类事情第二次、第三次做得更省力。

「可看、可控、可计量」是支撑这个愿景的管理基础，不是最终愿景本身。

## 当前核心问题与根本转变

当前最重要的问题不是消息数量本身，而是**很多事情等待人发起、等待人指示、等待人推动**。同时开发三个项目时，人需要在飞书中分别沟通、决策和推动，最多只能支撑约 2～3 个项目。

具体表现：

- 多项目的沟通、决策与推动集中在一个人身上。
- 架构 Review、代码治理和产品巡检依赖人主动发起。
- 提交代码、PR、合并、构建部署和清理分支等常规事项反复消耗人。
- Agent 之间的文档、背景、产出和理解确认依赖人肉中转。
- 站点数据、行业趋势和内容生产仍由人每天启动和串联。
- 托管可能出现无效返工、持续空转、Token 成本失控和凭证越权。

需要完成的根本转变是：

**从「把单项任务交给 Agent」，转向「把一类有明确目标、边界和结果要求的责任委派给智能团队」。**

人经营目标、规则、质量和结果，而不是每一次对话和每一个执行步骤。工作的发起和延续不应都依赖人开口。

## 人的介入边界与共性约束

### 可逐步退出的托管

追求的不是无人值守，而是**可逐步退出的托管**：新工作前期由人参与需求、方案、过程和质量校准；同类工作形成稳定标准、质量持续可靠后，人逐步退出重复过程，保留方向判断、关键决策、重要风险和结果责任。退出过程不等于失去知情权或放弃质量责任；质量、异常或成本出现问题时，人能够重新介入、调整或停止。

### 开发工作的介入边界

| 工作环节 | 人的参与方式 | 必须成立的效果 |
|---|---|---|
| 需求澄清理解 | 持续参与，不能退出 | 做的是人真正需要的事情，避免方向性返工 |
| 架构设计 | 持续参与并讨论，不能退出 | 人理解决策依据与实现方式，掌握长期演进方向 |
| 架构选型 | 知道结果，统一团队标准 | 不必每次参与比较，但不同 Agent 不能随意选择 |
| 代码编写 | 可以退出 | 需求与架构明确后不再逐步指挥 |
| 代码 CR | 可以退出，由 Agent 把控并反馈结果 | 人不阅读每次 CR，但真实质量问题不能被放过 |
| CI 构建与自动化测试 | 可以退出 | 验证持续推进，不依赖人催促 |
| 测试环境部署 | 可以退出 | 常规验证流程自然向后推进 |
| 生产环境部署 | 必须由人确认 | 未经确认不能越过最终风险闸门 |
| Bug 反馈 | 仍然由人参与 | 保留对真实使用问题和体验问题的判断 |
| 领取 Bug、修复并更新状态 | 可以退出 | 人反馈后不再充当流程推动者 |

分批提交代码、提交 PR、合并、常规构建部署和清理代码分支等标准化工程动作，不应反复占用人的注意力；生产环境部署始终是独立的人工确认边界。

### 非开发工作的介入边界

- **内容工作**：以阅读性、配图、内容结构、事实可靠性和整体表达评价质量。前期由人校准，稳定后逐步退出生产过程，保留方向与结果评价。
- **其他新业务**：前期允许人深入参与，随着标准稳定和质量可靠逐步减少过程参与；对外发布不默认授权。

### Bug 与巡检的不同修复权限

- **人主动反馈的 Bug**：问题和预期明确后，可以直接进入分析、修复、验证与状态更新，不必每次再问「要不要修」。
- **Agent 巡检发现的问题**：当前阶段无论大小，都先告知人，由人确认后再修。
- 两种情况涉及生产环境部署时，都必须由人确认。

### 代码评审触发方式与最多三轮

Code Review 分为两类触发场景，不得把例行开发中的评审统一理解为定时 Review：

- **例行开发：PR 触发**。Agent A 提交 PR 后，根据项目策略触发 Squadsight 的阻塞式评审或 Agent B 的非阻塞评审。评审方在对应 PR 下指出问题，Agent A 修复或说明问题不成立，评审方负责复审和给出评审结论。
- **定期技术债治理：定时任务触发**。Agent B 定期评估代码技术债并在 GitHub Issue 登记发现的问题；后续治理改动提交 PR 时，仍进入上述 PR 评审闭环。

**评审是否阻塞 Agent A 合并由项目策略配置**，两种模式采用不同承接方：

- **严格／阻塞模式**：直接由 **Squadsight** 完成评审、复审和放行，**不安排 Agent B 参与评审**。Squadsight 放行后 Agent A 才能合并；适用于需要严格质量闸门的项目，刚起步项目可以采用。
- **宽松／非阻塞模式**：由 Agent B 进行评审和复审，Agent A 可以不等待评审结论而合并；Agent A 仍须修复问题或说明理由，未决事项和后续处理必须可追踪。适用于希望减少评审等待的成熟项目。
- 宽松不等于跳过 Review、默认通过或免除质量责任；项目采用哪种模式及其调整应明确可查看，不能由 Agent 在一次 PR 中临时自行改变。

同一次代码变更的「评审—修改—复审」最多进行 **3 轮**，无论评审方是 Squadsight 还是 Agent B 均须遵守：

1. 优先发现逻辑错误、回归风险、安全问题和违反关键架构约束等真实问题，不用风格偏好反复打回。
2. 同类问题一次说清、整体排查，而不是每轮只指出一处。
3. 后续复审聚焦本次新增变化，不反复扩大范围；存量问题进入代码质量治理。
4. Agent A 可以修复问题或说明问题不成立，但须由当前评审方复审认可；Agent A 不能凭自己的说明自行关闭意见或放行 PR。已处理、已说明理由并经复审确认不改的事项，不重复拉扯。
5. 三轮仍未收敛时停止当前循环，说明遗留问题、已尝试处理和建议方案，重新评估；涉及需求、架构或高风险事项时由人决策。
6. 达到三轮不等于评审通过，真实问题未解决时不能以轮次用完为由视为已收敛。阻塞模式下，未获 Squadsight 放行时 Agent A 不得合并；非阻塞模式下，已经合并不免除遗留问题的处理、追踪和交付说明。

### 模型 Token 成本约束

- 正常消耗不应要求人持续盯盘，但人能够判断投入、进展和结果是否匹配。
- 能发现长时间空转、重复返工和无明确产出的持续消耗。
- 工作可能失控时，人仍能调整或终止。
- 不单纯追求 Token 越少越好，而是在质量、速度和成本之间保持合理平衡。
- 运行情况查看必须回答：**事情有没有向前推进、结果是否可靠、投入是否值得。** Claude Code 以实际采集的 Run 与 Token 为准；WorkBuddy 首版只展示 Task、A2A、Assignment 与产出，Run、对话和 Token 显示「未接入 / —」，不得按 0 或采集失败处理。

### 访问 Token 与权限边界

访问 Token 与模型 Token 是两类不同问题：前者关系到权限与安全，后者关系到成本与投入产出。

- 核心不是把 Token 分发给更多 Agent，而是统一维护规则与使用边界。
- 能完成被授权的工作，不等于可以任意使用凭证。
- 指定项目和正常任务中的 PR 授权，不自然扩展为操作其他仓库、连接生产服务器或执行无关动作。
- 权限范围需要按具体资源和动作明确，不能因 Agent 持有凭证就默认可用。

## 用户场景体系与业务验收

当前共 **12 个用户场景**。US-11、US-13、US-14 已移除，后续场景编号保持不变，避免历史引用漂移。

### 业务能力归类

| 业务能力 | 场景 | 要解决的问题 |
|---|---|---|
| 经营统筹与多项目交付 | US-12 | 多项目并行时，人不再成为所有项目的沟通与推进瓶颈 |
| 产品创造与问题闭环 | US-02、US-01、US-03 | 从想法到成果，以及问题反馈、发现、修复和验证 |
| 代码质量与标准治理 | US-04、US-07 | 主动发现质量风险，让团队标准跨项目传承并持续生效 |
| 协同与组织经验复用 | US-05、US-06、US-08 | 同一事项顺利交接，成熟能力完整复用，新技术验证后推广 |
| 内容生产与站点运营 | US-09、US-10 | 把工程事实和经营信号转化为有质量、有业务价值的内容 |
| 经营保障 | 上述共性约束 | 权限、质量和 Token 成本支撑规模化而不失控 |
| 文档与决策治理 | US-15 | 文档合并、更新和收尾由 Agent 主动收敛，避免多份内容重复维护和由人纠错 |

### 相近场景的去重与依赖

- US-01 与 US-03 共用修复验证闭环，但保留不同的修复授权：主动反馈可直接修，巡检发现先确认。
- US-02 解决一件事从想法到成果，US-12 解决多件事并行时人的注意力和上下文切换，两者不合并。
- US-04 关注整体代码和架构健康；US-07 关注规范学习、迁移和持续遵循，是质量治理的标准来源。
- US-05 解决同一事项跨 Agent 交接；US-06 解决成熟能力跨项目复用；US-08 解决新技术验证，验证后可衔接 US-06。
- US-09 与 US-10 共用内容质量标准，但前者来自真实工程实践，后者来自站点数据和行业趋势。
- US-15 关注文档与结论的唯一事实源及生命周期；US-05 关注工作交接是否完整，US-07 关注工程规范是否持续遵循。它们可以复用同一正式文档，但不合并为同一场景。

### US-01 产品试用与 Bug 反馈

**必须达到**：人通过专用的 **Bug 机器人**在飞书用自然语言连续反馈多个 Bug 或体验问题，必要时补充截图或操作过程。Bug 机器人通过相应技能完成问题拆分、去重和提交；信息足够时直接承接，关键信息不足时只询问必要内容，项目不明确时先澄清而不猜测。提交后的各问题分别进入修复计划，排查、修复、验证和状态更新不依赖人逐项催促；完成后说明修复内容、验证情况和遗留影响。相同问题重复反馈时应关联既有问题，相似问题反复出现时还应识别共同根因，不能永远作为孤立 Bug。**PR 关联且当前提交 CI 通过后进入待验收；人在 GitHub 合并 PR 即完成验收并自动收口，CI 记录只是待验收提示而非验收裁决；人工兜底接受/退回经原 Bug 机器人传达，修复回告、Task done 或 A2A ACK 都不等于业务接受。**

**业务验收**：人只向专用 Bug 机器人反馈，不需要自行拆分、查重或逐个提交，也不需要反馈一个、盯一个；预期明确后不再问「要不要修」，每个问题都有去向和验证结果。待验收后由人在 GitHub 合并 PR 完成验收；未被合并覆盖的情形经原 Bug 机器人人工兜底接受或退回，退回时在同一问题上继续返工，不另建重复事项。无法复现、预期歧义、需求变化、架构或重要方案取舍时回到人；生产发布必须由人确认。

### US-02 从创意想法到可见成果

**必须达到**：前期共同澄清为什么做、目标用户、核心问题、价值、范围、约束和完成标准；人持续参与需求与架构设计，架构选型知会人并符合团队标准。对齐后，编码、CR、CI、自动化测试和测试环境部署持续推进，最终交付可查看、可体验、可验证的成果及验证依据、未完成事项和已知限制。

**业务验收**：使用真实需求，需求和架构对齐后不再需要人发出常规过程推动指令；最终不是只有开发总结。需求歧义、重要架构调整或关键取舍回到人，生产发布单独确认，试用问题进入 US-01。

### US-03 产品问题主动巡检

**必须达到**：人不主动发现时，功能、数据、性能或体验异常也能被发现并先核实。告知人时说明现象、影响、依据、初步原因、处理建议和需要决定什么，避免大量误报。当前所有巡检问题先由人确认再修；确认后的代码修改、CR、测试和测试环境验证持续推进。

**业务验收**：不再依赖人偶然试用和发起排查；未经确认不直接修，未经单独确认不发布生产。相同或相似问题反复出现时，能提示更深的质量风险。

### US-04 代码质量与架构劣化治理

**必须达到**：Code Review 按以下两类场景分别触发和承接，既融入每次例行开发，也能主动治理存量技术债。

1. **例行开发中的 PR 评审**：Agent A 提交 PR 后，按项目策略自动进入对应评审，而不是等待人发起或统一等到定时 Review。
   - **严格／阻塞模式**：直接由 **Squadsight** 评审和复审，不安排 Agent B 参与。Squadsight 在 PR 下指出问题，Agent A 逐项修复或说明意见为何不成立；Squadsight 复审认可并放行后，Agent A 才能合并。
   - **宽松／非阻塞模式**：由 Agent B 在 PR 下评审和复审，Agent A 逐项修复或说明理由；Agent A 可以不等待评审结论而合并，但评审、问题处理和结果追踪仍须完成，宽松不等于跳过 Review。
   刚起步项目可以严一些，成熟项目可以松一些。两种模式都遵守三轮上限，达到三轮不等于评审自动通过。
2. **定期技术债评估**：由定时任务触发 Agent B 评估代码和架构健康，关注硬编码、违反分层、重复实现、缺少封装、职责模糊、命名失控等存量问题。发现值得治理的问题后，在 GitHub 创建 Issue，写清代表性证据、影响范围、业务与维护影响、处理建议、大致投入和暂不处理的风险，而非只留风格意见清单。问题不确定、不明确或需要人评估时，通过飞书向人反馈并请求审批；Issue 登记不等于自动获得修复或生产发布权限，后续治理仍遵守对应授权边界。

阻塞式 PR 评审直接复用现有 **Squadsight** 系统，不再为它设置 Agent B 评审角色，也不要求在控制台重复建设相同功能；非阻塞评审由 Agent B 承接。两种路径的 PR 评论、复审结论、放行或合并结果都应可关联追溯。

**业务验收**：使用真实 PR 验证两种项目策略：阻塞模式全程由 Squadsight 评审，没有 Agent B 评审动作，Squadsight 未放行时 Agent A 不能合并，放行后可以合并；非阻塞模式由 Agent B 评审，Agent A 不等待评审结论也可合并，但 PR 评论、修复或说明、复审结论及遗留问题仍有完整去向。两种模式都不需要人逐步推动。另以一次定时技术债评估验证自动创建内容完整的 GitHub Issue，需要人判断的事项能通过飞书获得审批。治理结果说明改善、行为变化、验证和遗留风险，不无限审查或重构。

### US-05 多 Agent 协作中的上下文与成果交接

**必须达到**：交接包含原始目标、决策原因、不可改变的约束、当前成果和后续责任，而非只有一份最新文档。影响结果的空白、矛盾或关键假设集中向人澄清；没有关键歧义时持续推进，目标变化后以最新要求为准，最终成果可追溯。

**业务验收**：人不再逐步安排「A 写文档、B 阅读、B 汇报理解」，也不需传话和催反馈；某环停住时能说明等待什么。避免反复讨论却无结果、持续消耗 Token。

### US-06 成熟能力的跨项目复用

**必须达到**：人指定参考对象、复用目标、必须保持一致的效果和允许适配的部分。承接方理解参考项目已验证的完整实现与使用效果，合理处理项目差异，不能静默降低能力或改变预期。

**业务验收**：以 A 已认可、B 待复用的真实能力验收；最终由人判断关键效果是否一致，不再依靠人逐项比对和十几轮细节纠正。项目特有的重要产品或架构取舍仍由人参与。

### US-07 项目规范迁移与持续一致性

**必须达到**：学习参考项目时，不仅复制目录表面，还理解组织方式的原因、代码归属、命名、分层、职责边界及新功能如何延续规范。规范约束后续新增和调整代码，合理项目差异与真正偏离能够区分。

**业务验收**：人确认参考项目、核心习惯和团队标准；较大架构调整与规范变化仍由人参与。偏差在积累大量技术债之前被发现，不再每种新偏差都由人重新教育。

### US-08 新技术验证与跨项目推广

**必须达到**：新技术在合适产品上形成真实验证，而非一次演示；结果说明解决的问题、相对价值、预期达成、限制、成本、风险和推广适用性。人决定是否值得验证、评估价值并决定是否推广，具体调研和常规验证不逐步等待人。

**业务验收**：人决定推广后，其他项目继承已验证经验，不从零研究或重新听人讲一遍；成熟实践可进入 US-06。

### US-09 工程实践沉淀为系列实践内容

**必须达到**：人从选题池选择题目并说明目标；写作 Agent 延续风格和质量标准，直接向实施 Agent 获取和核实架构、决策、实践过程、问题、解决方案、实际效果及必要截图。素材不足继续追问，不编造；实施 Agent 对事实负责，写作 Agent 对读者理解和表达负责，系列文章形成清晰关系。

**业务验收**：人不再收集、转交素材和完成第一轮改写；可以参与角度、观点、结构和质量讨论。标准稳定后逐步退出常规写作流转，保留方向和结果评价，未确认事实不得当作确定内容。

### US-10 站点日常运营：从数据与行业趋势到内容行动

**必须达到**：持续关注 aitech 后台经营数据和行业趋势，区分有效信号与噪声。重要变化说明事实、站点或用户关联、关注理由、依据来源和可形成的内容方向；方向明确后资料补充、事实核对、文章组织、配图和初稿持续推进，关键事实可溯源。

**业务验收**：不再由人每天查数据、搜趋势、安排写作；普通波动不随意打扰，不确定信息不伪装成结论。标准稳定后人退出日常过程；没有值得行动的变化时保持安静，不制造低价值内容或失控消耗。

### US-12 多项目并行与整体掌控

**必须达到**：各项目在明确目标和边界内持续推进，人能分清正常、等待、需要自己、待验收及异常停滞。需要决策时一次获得背景、问题、选项、影响和建议；切换项目可快速恢复目标、阶段、重要决定、下一步和阻塞。需要进一步了解某个 Agent 的具体过程时，可从其运行状态进入已采集的只读对话查看；日常掌控不能依赖人逐条阅读全部对话。常规工程动作不分别等待指示，长期无进展、返工或 Token 异常能被发现。**WorkBuddy 首版无 Run、对话和 Token 采集，相应位置显示「未接入 / —」，不能用缺失数据判断其离线或零消耗。**

**业务验收**：人处理项目 A 时，B、C 的常规工作继续；无需不断主动询问或重读全部对话。不是把消息集中后让人面对更多通知，也不是要求人持续盯着每个 Agent。

### US-15 文档与决策的唯一事实源维护

**必须达到**：Agent 新增或修改文档前，先查找同类正式文档、索引和既有结论；能够更新正式文档时，不另建一份长期并存的需求稿、对齐稿或总结稿。确需临时过程稿时，应明确其临时用途，并在结论合并后的同次收尾中删除，不留下需要共同维护的第二份。变更时同步更新相关索引、数量、交叉引用和受影响表述，清理已被合并或替代的内容；发现真实决策冲突时集中说明差异并请相关人裁决，而不是复制后各自漂移。

**业务验收**：以一次真实需求讨论和文档合并验收，结束后每类事项只有一份明确有效的正式文档，不存在内容重复且需要同步维护的过程稿；正式结论和必要背景不丢失，旧引用有去向，后续 Agent 不需要阅读多份文档比较哪个更新。人不需要主动巡检目录、发现重复或提醒删除，文档维护本身的检查和纠错不再成为人的持续工作。

## 用户价值优先级与首个完整闭环

### 优先级原则

1. 优先解决「事情等待人发起和推动」，而不是优先增加可见信息或通知数量。
2. 优先建立可信交付，再扩大自动发起、跨项目复用和新业务范围。
3. 自动化程度不是目标；人的需求、架构、生产发布和最终责任边界从第一阶段就成立。
4. 三轮评审、真实质量、权限不越界和 Token 投入可控是所有阶段的共性约束。
5. 以下优先级是用户价值的解决顺序，**不直接等于现有开发里程碑或功能排期**。

### 场景优先级

| 优先级 | 场景 | 用户价值与理由 |
|---|---|---|
| **P0：先摆脱人的流程瓶颈** | US-02、US-01、US-12、US-15 | 解决需求对齐后仍逐步指挥、Bug 逐个盯、多项目互相等待，以及重复文档靠人发现和纠正，首先形成真实交付闭环 |
| **P1：让持续推进可靠、可复制** | US-03、US-04、US-05、US-07、US-09 | 主动发现风险，补齐交接、规范和工程内容，规模化不以质量下降为代价 |
| **P2：扩展组织能力和业务版图** | US-06、US-08、US-10 | 在前期标准、信任和协作能力上复用成熟能力、推广新技术并扩展内容运营 |

P2 不代表业务价值低。US-15 的「唯一事实源、合并后清理、同步更新引用」从首个闭环起就是文档工作的共性约束。US-05 不是首个闭环的强制正样本，只有真实事项确需跨 Agent 时才使用。

### 首个完整业务闭环（真实 Bug）

**一个真实 Bug，从人在原 Bug 机器人反馈开始，经自动承接、修复、PR 与 CI、待验收，最终由人在 GitHub 合并 PR 自动验收收口；人工兜底接受/退回修改仍经原 Bug 机器人。**

该闭环验证 US-01 与 US-12 的核心效果，并为后续 US-02 完整需求交付复用协调链路：

1. 人只向原 Bug 机器人反馈一次，机器人完成必要的澄清、拆分和去重；项目不明确时先问清，不猜测归属。
2. 系统只按确定性规则把问题分给已登记承接方；无项目、无规则或归属冲突时集中请人，不由多个模型或私人记忆分别决定。
3. 承接 Agent 自己创建 Task 并确认承接，排查、修复、提交 PR 和后续 CI 持续推进，不需要人发出常规过程推动指令。
4. PR 按项目策略进入评审：阻塞模式由 Squadsight 评审、复审和放行，非阻塞模式由 Agent B 评审；两类均最多三轮。评审与测试环境结果可作为补充证据，但不是所有 Bug 统一的待验收前置条件。
5. 关联可访问 PR 且**当前 PR 提交的必需 CI 全部通过**后，问题进入待验收；旧提交的绿色 CI、当前提交的失败 CI 或 Agent 自报完成均不能进入待验收。
6. 修复结果回到原 Bug 机器人。人在 GitHub 合并 PR 后问题自动验收收口；需人工干预时经原 Bug 机器人「接受」强制收口或「退回修改」，退回时在同一问题上记录理由并继续返工，不另建重复事项。
7. 原始反馈、承接、修复、PR、CI、返工和最终接受可回溯；A2A 回执 ACK 只代表上游 Task 验收，不等于业务接受。
8. 生产发布仍是独立人工确认，不因修复、PR、CI、Task/WorkItem 状态或人工接受而自动触发。

### 首个闭环的用户验收标准

- 使用一个真实项目的真实 Bug，不用人为演示任务或模拟 CI 替代。
- 人发出的常规过程推动指令为 **0**；新增输入只用于必要的 Bug 澄清、风险、验收和生产发布事项。
- 至少真实经历一次 CI 失败与一次原 Bug 机器人退回：CI 失败不能进入待验收，退回必须在原问题上返工；随后以真实 PR+CI 再次进入待验收，并在 GitHub 合并后自动验收收口。
- 人处理其他项目期间，本项目常规执行不因等待这些指令停住；恢复关注时无需重读全部对话。
- 代码评审不超过三轮；未收敛有明确遗留问题和重新评估结果，不冒充通过。
- 未经确认不发生产发布；巡检问题当前也必须经人确认后才修。
- 人能判断结果可靠性和 Token 合理性，出现空转、失控或越权时能够调整或停止。

首个闭环不以页面上线代替业务验收，不要求一次性纳入主动巡检、定期架构治理或完整新需求交付等全部场景。

### 首次使用与自动初始化（2026-11-03 确认）

**目标**：首次使用时，用户只做必要授权、一次安装执行和一次配置确认，不需要理解数据库、RouteRule、Mandate、worker_inbox、A2A 信封或 launchd 等内部概念，也不需要手工编辑 JSON/YAML、plist 或路由配置。系统必须以引导式自动装配降低认知负担，并在开始前完成可解释的初始化检查。

| 步骤 | 用户需要输入或操作 | 系统必须自动完成 |
|------|--------------------|------------------|
| 1. 启动工作台 | 输入首次启动在本机输出的一次性 bootstrap token，并设置管理员口令；frp 复用既有部署配置，不在向导重复输入 | 无管理员凭据时仅开放 bootstrap mode；初始化 PostgreSQL 与扩展、执行 schema 迁移、创建空知识目录和备份目录、检查健康状态；不展示数据库或索引配置，也不要求先配置 `CONSOLE_INIT_PASSWORD` |
| 2. 添加执行机 | 在控制台选择「添加执行机」，在目标机执行一次安装命令，并以隐藏输入/stdin/env 提供一次性加入令牌 | 签发一次性 enroll token；安装脚本自动换取机器 ID 与采集密钥，识别主机与系统、安装唯一 aw-node、写入 launchd、启动并自检；不要求填写 collector_id、plist 或进程配置 |
| 3. 注册项目 Agent | 选择系统发现的项目/仓库和运行时，补充必要的 GitHub 或 Bug 机器人授权，并确认主责 Agent | 优先由 aw-node 上报的 cc-connect 配置预填项目、目录、Agent 和渠道身份；创建 agent.id、稳定 agent.key 与非敏感运行时配置，默认 `project.primary_agent`；**Bearer 在 aw-node 的 `POST /api/aw-node/config` 中按请求轮换并返回最新值，ACK 后不再返回明文，重试不需要第二次安装**；只有发现不了时才询问项目名、仓库地址和工作目录 |
| 4. 启用首个 Bug 工作流 | 选择 Bug 来源、仓库和 CI，核对系统生成的项目、主责 Agent、`bug_fix`、PR+CI 待验收及合并即自动验收摘要，点击确认 | 生成 Git 版本化 RouteRule、Mandate 与证据要求，配置 Bug 提交与合并验收/兜底退回事件，检测 GitHub/CI、Agent、远程 MCP、aw-node 与权限连通性，并给出逐项预检结果；无需用户编写 RouteRule |

**初始化边界与验收**：

- 首次进入是空库、空知识和空任务，不导入旧 SQLite 或旧 Markdown；不得把旧数据导入当作初始化步骤。
- 用户只需依次完成「初始化控制台 → 在目标机执行一次安装命令 → 选择并确认项目与主责 Agent → 核对默认 Bug 工作流与初始化检查」；不得要求用户先创建 Task、手工编写 RouteRule 或配置多个执行面进程。
- 机器 ID、Agent ID/key、一次性密钥、远程 MCP 配置、默认主责 Agent、默认 `bug_fix` 规则、Mandate/证据模板及连通性检查必须自动生成或预填；一次性密钥不得进入命令行参数、shell history 或日志。
- 预检必须分别显示数据库、机器心跳、采集、远程 MCP、Agent 身份、项目角色、Bug 来源和 GitHub/CI 的成功、失败或未配置状态；失败时给出对应修复入口，不能显示为「已就绪」。
- WorkBuddy 首版 Run/对话/Token 显示「未接入 / —」，不得因其过程数据缺失阻止初始化或 A2A 使用。
- 初始化完成后，用户应能直接在原 Bug 机器人反馈真实问题并进入「首个完整业务闭环」；在项目、角色和 Source 配置完整时，不得再落入 `needs_person`。
- 日常使用只要求用户「反馈问题」与「在 GitHub 合并验收」，生产资源访问和生产发布仍单独授权。

## 1. 产品定位与协作边界

智能体工作台是支撑上述愿景的经营与交付中枢：帮助一个人把事情交代清楚、组织完成、掌握关键状态、作出必要决策、验收成果，并留下可复用的资产。

在当前产品阶段，把散落在飞书群、黑板表格、本地脚本里的多 Agent 协作，收进一个可看、可控、可计量的工作台——人能看清 Agent 在干什么，系统能拦住它不该干的事，账上能算清花了多少。管理的是「事情和结果」，Agent 状态与协作是为了让事情可靠完成。

**目标用户**：持有多个 Agent（WorkBuddy / cc-connect + Claude Code）的个人开发者（当前唯一用户：诸葛东明）。

**核心价值**：当前协作栈（cc-connect + 飞书群 + 黑板表格 + 规范文档）跑通了 A2A，但状态不可见、知识用不上、约束停在纸面。控制台补的是控制面，不替换飞书。

### 1.1 产品形态：控制台 + 飞书双面并存

- 控制台管「状态与权力」：运行态、任务、授权、知识
- 飞书管「说话与拍板」：下任务、看结论、一键批准/拒绝
- 控制台不承担 IM 功能：不做对话主入口、不用于长文讨论、不提供发送或回复消息能力
- 控制台支持从 Agent 运行状态下钻到**已采集对话的只读视图**，用于了解过程、核对依据和排查问题，不因此变成新的沟通入口
- 一期四屏：总览 / 任务 / 授权 / 知识；Agent 详情是总览的下钻页，不新增独立主导航

### 1.2 协作形态与可见性边界（2026-10-30 补充）

真实形态是**每个 Agent 各自持有飞书机器人**，人直接对某个机器人说话；控制台是旁挂的观察与记录面，不是消息中转站。飞书有两条硬约束，决定控制台能看见什么：

- 群聊里机器人**只在被 @ 时**收到消息；私聊只有被私聊的那个机器人收到。
- 机器人**不把另一个机器人的消息当作输入**（防循环）。

推论：**控制台不能通过飞书直接收取不属于它的消息；Agent 之间在飞书里互相不可见。** Agent 详情只能展示该 Agent 已成功采集的本地执行会话，不能据此宣称看到了全部飞书消息。跨 Agent 协作只能走控制台信箱（A2A），不能靠「在群里看别人说了什么」。

#### Agent 详情与只读对话查看（2026-11-02 补充）

**目标**：人在总览看到某个 Agent 的运行状态或最近任务后，可以直接点击该 Agent，进一步看清「人交代了什么、Agent 回复了什么、执行过程中发生了什么」，不必回到本机查找会话文件或重读多个渠道。

**必须达到**：

1. **入口与上下文**：总览中的 Agent 名称或所在行可点击，进入该 Agent 的详情页。详情页保留机器、项目、运行状态、最近任务和 Token 消耗等摘要，并能返回原总览上下文。
2. **主流对话呈现**：对话按时间顺序，以用户与 Agent 区分明确的消息形式展示，至少包含发言方、内容和时间；进行中的会话能增量看到新内容。不能把一堆原始日志或 JSON 当作对话视图交付。
3. **执行过程可辨认**：工具调用、命令执行、文件修改、错误等执行事件与正常对话区分展示，可展开查看详情或收起减少干扰；关键执行事件不能被静默省略，也不能伪装成 Agent 的自然语言回复。
4. **会话与任务关联**：默认展示当前或最近一次会话，可切换同一 Agent 的历史会话；有关联任务时可跳转任务详情，从任务也可回到对应会话。没有任务记录的日常 run 仍能查看对话，不得以 `task_id` 为空为由不展示。
5. **可见范围真实**：只展示已成功采集且允许当前用户查看的会话。页面需标明数据更新时间及可见性限制；没有对话、采集延迟、采集中断或历史不完整时，应展示对应状态和原因，不能空白冒充无消息，也不能声称全量可见。**WorkBuddy 首版固定显示「未接入 / —」，不生成空对话视图，也不把它归类为采集故障。**
6. **只读与安全**：只能查看，不能在该页面发送消息、追问 Agent、修改或删除对话；敏感凭证、口令和私钥等内容默认脱敏。查看行为不改变 Agent 运行状态，也不替代既有授权和审批。

**业务验收**：选择一个正在运行且未建任务的 Agent，从总览点击进入后能看懂最近一轮人机对话，并看到后续新增内容；再选择一个有关联任务的 Agent，能在会话与任务之间互相定位。未采集到的会话有明确提示，页面没有发送或回复入口。

四种协作形态（验收正样本）：

| # | 形态 | 参与方 | 记录要求 |
|---|------|--------|----------|
| A | 单人单机单向 | 人 ↔ 单个 Agent | 默认只记 run（会话 / token）；要发 A2A、要授权、有 deadline 或产出需归档时才建单 |
| B | 两方单向索取 | 人 → B，B → A | B 建自己的任务并发 A2A 请求；A 自建任务，在确认收件时挂到 B 的任务之下（`handoff` 事件） |
| C | 群内广播并行 | 人 → A/B/C/D | 各 Agent 自建任务，`project` 由 Agent 自报；控制台按项目并列展示。控制台只有也被 @ 时才收到该消息，**它不是本场景的必经点** |
| D | 三方链式 | A → B → C | 每段一条任务，用 `handoff` 事件与 `refs` 串成链；任务详情可顺链回看每环产出 |

**建单规则（唯一口径）**：

1. **谁干活谁建单**——任务由执行方 Agent 经 MCP `task_create` 创建，`assignee` 恒为自己，创建后不可变；禁止代建他人任务。
2. 收到指令**不自动建单**。只有命中以下任一条件才建：接受 Assignment、要发 A2A（信封必填 `task_id`）、要申请授权（票据绑定 `task_id`）、有 deadline 需超时升级、产出物需归档并被引用。
3. 控制台**没有人工建单入口**；Agent 只能通过控制台远程 `/mcp` 的 `task_create` 建自己的单，Agent Bearer 与任务归属均由服务端校验，首版不引入 `run_token`。

### 1.3 管理面的基础效果

后文每个场景都用来证明其中一条：

| # | 效果 | 可验证的判据 | 不达标长什么样 |
|---|------|--------------|----------------|
| 1 | **看得见** | 打开总览 3 秒内说出「谁在跑、跑到哪、用了多少 token」；任一任务能回答「卡在哪一环」 | 要挨个去问 Agent；看到的是两小时前的快照 |
| 2 | **拦得住** | 生产资源零长期凭证；控制台自有控制工具 100% 经服务端判定与审计，资源授权可追溯 `task_id`；第三方 MCP、原生工具与终端直跑明确不计入覆盖 | 把约束只写在文档里，或把未覆盖通道冒充全量拦截 |
| 3 | **算得清** | 按 Agent / 项目统计 token 消耗；超日用量上限能停 | 月底才发现用量早已失控 |
| 4 | **用得上** | 同一问题第二次不用重复解释 | 每个 Agent 各自从零积累上下文 |

「追得到」（任一结论回到谁做的、凭什么做的）不单列，它是 1~4 的前提。

## 2. 协作形态与横切场景走查

前述 12 个用户场景定义业务价值与用户效果；本节 A～D 描述协作拓扑和可见性边界，E～K 描述横切风险。它们是用例走查，不替代业务场景，也不代表用户价值优先级。

每个场景回答四件事：**时序**（谁在什么情况下做什么）、**系统必须做**、**怎么算过**、**边界在哪**。机制细节不在此重复，只给落点。

### 2.1 场景 A：单人单机单向

> 我在飞书私聊 Claude Code 那个 bot，让它开发 XX 项目的一个功能；它干活、回我结论。全程只有我和它。

**时序**

1. 私聊 → 只有这个 bot 收到（飞书硬约束），控制台机器人**收不到这条飞书消息**；后续可展示的内容以本地会话文件的实际采集为准。
2. bot 在我机器上跑，写 Claude Code 会话文件。
3. aw-node 采集模块增量读该文件 → `POST /api/ingest`。
4. 控制台归一化成 run 与运行事件，总览出现这一行。
5. 它把结论回给我。**默认不建任务。**

**系统必须做**

| # | 义务 | 落点 |
|---|------|------|
| A1 | aw-node 采集模块按「文件 + inode + 偏移」增量读，ACK 后才推进位点 | arch/04 §3 |
| A2 | 入库按机器、流、序号三元组去重，允许部分确认 | arch/02 §3.8 |
| A3 | run 的 `task_id` **可为空**；总览不得因缺 `task_id` 丢弃这类 run | arch/02 §3.1 |
| A4 | token 用量入 token 账，重复投递不重复计数 | arch/02 §3.6 |
| A5 | 总览实时推送，帧带版本号，客户端缺口即重取快照 | arch/01 §7 |
| A6 | **不建单**；只在 §1.2 建单规则第 2 条的四种情形下自建 | §1.2 |
| A7 | 前端明示「仅展示已成功采集的会话，不承诺全量可见」；点击 Agent 可查看已采集的只读对话 | §6 |

**验收**：手机上打开总览，能看到这台机、这个项目、当前在做什么、今日 token 消耗，且**没有任何任务记录**时页面照常工作；点击该 Agent 后能查看已采集的只读对话，进行中的会话有新内容时可继续看到。

**边界**：控制台只能查看该 Agent 已采集的会话；未被该 bot 接收或未被采集的飞书消息仍不可见，Agent 之间在飞书里的可见性不因此改变。

### 2.2 场景 B：两方单向索取

> 需要跨 bot 协作：让 B 找 A 要 A 那个任务的实现过程文档，B 拿去发表。

**时序**

1. 我在飞书跟 B 说「找 A 要文档」。
2. B 判断这是跨 Agent 的活 → 先建**自己的**任务（因为要发 A2A）。
3. B 发 A2A：`task_id` = B 自己的任务，收件方为 A，意图为请求，截止时间与期望齐全。
4. 控制台落消息与投递记录，返回消息号。
5. A 取件 → **A 自建自己的任务**；确认（ACK）时带上自己的任务号，系统把这条任务挂到 B 的任务之下并记一条 `handoff` 事件。
6. A 干活，产出文档 → 归入知识库（候选）→ 回信携带该知识条目标识。
7. B 确认收到 → 投递完成；B 使用这份产出。

**系统必须做**

| # | 义务 | 落点 |
|---|------|------|
| B1 | 建单只能建自己的，`assignee` 恒为调用方、创建后不可变 | arch/01 §5.2 |
| B2 | 发信前校验：`task_id` 是自己已存在的任务 + 收件方在委派白名单内，任一不满足即拒 | arch/05 §6.1 |
| B3 | 消息内容与投递运输分开记；「已投递」只以对方确认为准 | arch/02 §3.3 / arch/01 §6 |
| B4 | 只能取收件人是自己的未确认消息；跨 Agent 取件返回 403 | arch/01 §5.1 |
| B5 | 未确认的消息在租约过期后重新可见（至少一次投递），接收方按消息号去重 | arch/01 §5.1 |
| B6 | 超过截止时间未确认 → 进死信 + 回执发件方「已过期，请重新发起」，**不自动重发** | arch/01 §6 |
| B7 | handoff 事件写在**下游**任务上、用 `from_task_id` 指向上游；**不转移归属**（上游任务仍归原承接方） | arch/02 §3.1 |
| B8 | 任务详情能看到完整往来线程（按轮次升序 + 投递状态） | arch/03 §4.2 |

**验收**：这条链在控制台上表现为**两条任务**（B 的、A 的），A 的任务挂着一条指向 B 任务的 handoff；B 的任务线程里有请求与回复两封信，状态均已投递。任务与消息的事实、正文和投递状态只存在控制台，不经飞书群传递；飞书协作群只展示〔交接〕〔接单〕〔完成〕〔验收〕四条无 @ 播报，未配置或不可用时链照常跑完。回执 ACK 只表示上游 Task 验收，不等于所属 WorkItem 已由人接受。

**边界**：A 若在截止时间内没处理，链会卡在 B 的任务上——控制台能看到「卡在哪一环」，但**不会替 A 重发**。

### 2.3 场景 C：群内广播并行

> 我在群里 @ A/B/C/D 四个 bot，让它们各自在自己项目里复用优化同一个实现，做完回我。

**时序**

1. 群里 @ 四个 bot。控制台机器人**没被 @，收不到这条消息**。
2. 四个 Agent 各自判断这是「有产出需反馈」的活 → 各自建任务，`project` 各自自报。
3. 四条任务并列出现在任务屏；人按项目分组看。

**系统必须做**

| # | 义务 | 落点 |
|---|------|------|
| C1 | 一条任务一个承接方；四个 Agent = 四条任务，不合并 | arch/02 §3.1 |
| C2 | `origin=feishu`（活从飞书来）；`assigner` 是人的 `open_id`（Agent 自报，可信度低于宿主注入的 `from`）；事件里记自报者是哪个 Agent | arch/02 §3.1 |
| C3 | 任务屏按项目并列展示，支持按项目 / 承接方过滤 | arch/03 §4.2 |
| C4 | 前端提示「仅显示已自报的任务」——某个 Agent 若判断不需要建单，它就**不会出现在列表里** | arch/03 §4.1（待补） |

**验收**：四条任务同屏，各自能下钻到自己的 run 与产出。

**边界（重要）**：控制台不参与这次广播，它看到的只有「四个 Agent 事后各自报了账」。**它无法证明广播发给了四个、更无法证明第四个为什么没动。** 这是产品形态决定的，不是缺陷，但前端不能说成「全量可见」。

### 2.4 场景 D：三方链式

> A 实现功能 → B 找 A 要文档 → B 发给 C → C 写专利文档。

**时序**：A 与 B 之间同场景 B；B 与 C 之间再走一遍同样的 A2A（B 为发起方、C 为接收方）。B 身上有**两条**任务：一条是**向 A 发起索取时**自建的（发 A2A 必须先有任务，见 §1.2 第 2 条），一条是向 C 发起时自建的；这两条之间是**同一 Agent 的续接**，不是跨 Agent 交接。A 收到请求后自建自己的任务，C 亦然。

**系统必须做**：B1~B8 全部复用，加上——

| # | 义务 | 落点 |
|---|------|------|
| D1 | 链上相邻任务只有两种关系：跨 Agent 交接（`relation=a2a`）与同一 Agent 续接（`relation=continuation`）；两者都落成「下游指向上游」的一条边，链长不受限 | arch/02 §3.1 |
| D2 | 任务详情能沿链**向上**逐环回看产出，并回答「我这条是谁交给我的」以及关系类型 | arch/03 §4.2 |
| D3 | 产出物以知识条目标识传递，**不传本地路径** | arch/01 §5 |

**验收**：从 C 的专利任务能一路点到链上**最早的任务**；上游若只有 run 而无任务（例如 A 在私聊里直接实现），**如实止于该任务**，不凭空补一条任务；链上每一环都有独立任务记录与 handoff 事件，Claude Code 的 token 独立计量，WorkBuddy 的 Run/对话/Token 首版显示「未接入 / —」。

**边界**：链式协作的产物仍是「多条任务」，不是一棵树。树形展示留 M4 评估（见 §9-11）。

### 2.5 横切场景（E~K）

| 场景 | 必须发生什么 | 验收 |
|------|--------------|------|
| **E 连生产机** | Agent 在任务内申请，**必须挂自己的 `task_id`**；人批准后由 Teleport 签发 15 分钟证书；签发中不留在中间态，失败即驳回并告警；到期自然失效，剩余不足自动续期；凭证可追溯到任务 | 生产资源零长期凭证；任一凭证能查到属于哪条任务、何时签发、是否续期 |
| **F 执行高危命令** | 只有控制台自有 `task / a2a / kb / work` 控制工具经过服务端判定：只读白名单放行、写自己的账校验后放行、未知工具拒绝，审计写失败即拒绝执行。**本机第三方 MCP、Claude Code 原生工具与终端直跑均不在管控范围内**；一期不做 OS 级沙箱 | 自有控制工具 100% 经判定并留审计；第三方 MCP 与原生工具不得计入拦截率或伪装成全量 MCP 覆盖 |
| **G 第二次问同一问题** | 知识检索常驻放行；先关键词召回再语义召回，合并去重；命中带出处；未命中的新品只能进候选，**人采纳后才生效**；语义引擎不可用时只走关键词并明示降级 | 同一问题第二次命中同一条目，且检索调用留有审计记录 |
| **H 跑超预算（token 口径）** | Claude Code token 事件幂等入账；按 Agent 匹配日用量上限；到警戒线告警，到硬顶拒绝新的自有控制工具调用与 Assignment，但不冒充能停止第三方工具或运行中进程；WorkBuddy Token 首版留空 | 可采集 Agent 能出数；超上限时可控入口停止，未覆盖通道有明确说明 |
| **I 停机 / 断网** | M2.5 之前停机纯观测、不影响执行；M2.5 之后 Agent 间通信中断但**消息不丢**，恢复后补投；aw-node 采集事件在本机缓冲，容量上限内不丢 | 停 30 分钟再起：事件序列完整、消息全部补投、没有重复执行 |
| **J 新机上线** | 控制台选择「添加执行机」→ 在目标机执行一次安装命令并安全提供一次性 enroll token → 系统自动登记、安装 aw-node 并上报 cc-connect 发现结果 → 用户确认主责 Agent 与默认配置 → 系统自动下发运行时 MCP 配置并观察 10 分钟心跳与缓冲回落 | 机器自动上线；同机只有一个 aw-node，发现、配置和回执可追踪，两机数据互不干扰 |
| **K 任务被打回** | 打回时累加返工次数并记录原因与轮次；`round`（往返轮次）与返工次数**不得互相替代**；真实 Bug 退回还必须回到同一 WorkItem 并形成后续输入 | 任务屏能看出被打回几次、每次为什么、谁打的；Bug 不生成重复事项 |

## 4. 明确不做清单

- 不做多租户 SaaS，不做对外商业化
- 不重写 Agent 运行时（Claude Code / cc-connect 是资产）
- 不做像素风 / 游戏化可视化
- 不接入 20+ 消息渠道；人机交互只用飞书，Agent 往返走系统内通道
- 不做自建 IM、移动端原生 App、跨组织账号体系
- 不做飞书黑板表格投影（黑板已停用，2026-10-29 裁决）
- 本期不替换 cc-connect
- 不做执行机 MCP proxy、第三方 MCP 网关或第三方 MCP 全量管控
- 不做在线 Slow Router、模型自动派工或基于 Source 私人 Memory 的任务分配
- 不做 SQLite → PostgreSQL 数据迁移、旧知识导入、双写或旧协议兼容层
- 首版不采集 WorkBuddy 的 Run、对话或 Token，相关位置只显示「未接入 / —」

场景层的反例（同样不做）：

| 不做 | 原因 |
|------|------|
| 在控制台里和 Agent 对话 | 说话在飞书；控制台只查看已采集的对话，不提供发送或回复能力 |
| 通过飞书直接看到人与其他 bot 的私聊 | 控制台机器人收不到；对应 Agent 的本地会话若已采集，可在其详情中按实际采集范围只读查看 |
| 保证「群里每个 Agent 都被记录」 | 只能记录自报的 |
| 手工建任务 | 谁干活谁建单，控制台无入口 |
| 用 aw-node 或逆向内部 API 唤醒 WorkBuddy | 使用官方 automations 轮询 Assignment/Input，不增加本地服务，不维护私有接口兼容 |

## 6. 验收标准

- 业务闭环：按「首个完整业务闭环（真实 Bug）」验收；常规过程推动指令为 0，真实经历 CI 失败与原 Bug 机器人退回后仍能在同一事项返工，最终由人接受
- 首次使用：按「首次使用与自动初始化」验收；用户只需必要授权、一次安装执行和一次确认，无需手工编辑 RouteRule/plist/数据库配置，预检失败不得显示已就绪
- 人工边界：需求澄清、架构设计、真实 Bug 反馈与验收、生产发布确认符合既定边界；未经人确认不得发布生产，巡检发现的问题当前不得未经确认直接修
- 评审策略与收敛：例行开发由 PR 触发评审；阻塞模式直接由 Squadsight 评审、复审和放行，不让 Agent B 参与，放行后 Agent A 才能合并；非阻塞模式由 Agent B 评审，Agent A 无需等待评审结论即可合并，但仍须完成问题处理与追踪；同一次变更最多三轮，未收敛不得视为通过，也不得继续无限修改
- 技术债治理：定时任务触发 Agent B 评估并自动创建内容完整的 GitHub Issue；不确定、不明确或需要人评估的事项通过飞书请求审批，Issue 登记不替代修复或生产发布授权
- 总览：打开 3 秒内看清所有 Agent 在干什么；点击 Agent 可进入详情并查看已采集的只读对话
- Agent 对话：用户与 Agent 的消息按时间顺序清晰展示，工具调用等执行事件可区分、可展开；进行中的会话能增量查看新内容；无任务的 run 也能查看；会话与关联任务可互相定位；无发送或回复入口，未采集范围有明确提示，敏感凭证默认脱敏
- 任务：任一任务能回答「卡在哪一环」
- 授权：生产资源零长期凭证；短时证书 TTL 15 分钟且自动续期；审计可追溯 task_id
- 知识：同一问题第二次不再重复解释
- 沟通：缺字段的消息被拒收；任务一次交付通过率 ≥ 60%（`rework_count = 0` 的已交付任务占比，口径见 §9-12 #5）
- 协作：§1.2 的 A/B/C/D 四种形态各能跑通一次；跨 Agent 协作 100% 有任务记录；单人私聊以 run 记录呈现，不以「没有任务」为由判失败
- 路由：已知 Thread 只续接原 owner；新工作只命中唯一版本化规则，未知或冲突集中请人；任一派工能以规则 ID 与版本解释，不接受在线模型自动派工
- 工具边界：控制台自有控制工具经远程 `/mcp` 与服务端校验，A 的 Bearer 不能操作 B 的任务或收件箱；第三方 MCP 不出现在工具列表或审计覆盖承诺中
- 可见性：前端必须明示「仅展示已成功采集的会话，不承诺全量可见」，不得声称全量可见；WorkBuddy Run/对话/Token 首版显示「未接入 / —」
- 产出：任务闭环率、耗时、返工、产出物、token 消耗可按 Agent 与项目统计；WorkBuddy 缺失的过程数据不参与 Token 或 Run 指标，不伪造为 0
- 文档治理：同类事项只有一份明确有效的正式文档；临时稿在结论合并后的同次收尾中删除，相关索引、数量和引用同步更新；不需要人发现重复、比较多份版本或提醒清理
