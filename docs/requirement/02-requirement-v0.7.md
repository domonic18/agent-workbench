## 一、产品形态与职责边界
### 1.1 结论：控制台 + 飞书，双面并存
调研四个参考项目（HappyClaw / CowAgent / PilotDeck / Paperclip）后得到一个共同规律：它们都没有把「管」放进 IM，而是分成两个面——控制面负责配置、权限、预算、审批、历史与用量；IM 只当输入输出口。
我们现在的状态正好相反：控制面几乎为零，所有「管」的事塞进了群和表格。所以「想了解进度只能逐个翻群」不是飞书的问题，是飞书被当成了控制台用。
定案：补控制台，不换飞书。
| 面 | 由谁承担 | 回答什么问题 | 交互特征 |
|---|---|---|---|
| 控制面 | 工作台 Web 控制台 | 谁在跑、跑到哪、花了多少、能不能让它动这台服务器 | 结构化、可回翻、可批量、可比对 |
| 人机面 | 飞书（群 + 卡片 + 黑板投影） | 我要它做什么、结果如何、批不批 | 流式、随手、手机上 |
| 协作面 | 控制台系统内通道（A2A） | Agent 之间怎么派活与交付 | 机器读、人不必逐条看 |
### 1.2 职责边界：哪些事只在一个面做
只在控制台做
- 全部 Agent 的运行态、任务链、轮次、成本、日志下钻
- 权限的授予、吊销、审计查询（审批动作的两端都在控制台，飞书只做通知与一键跳转）
- 预算设定与超支处置
- 知识库的浏览、编辑、索引重建
- A2A 消息线程的查看与人工干预
只在飞书做
- 人向 Agent 下任务（自然语言，不走表单）
- Agent 向人汇报结论与需要拍板的点
- 移动端随时查看与一句话批复（卡片点「批准/拒绝」直达控制台对应记录）
两边都有，但只有一个真相源
| 东西 | 真相源 | 在另一侧怎么呈现 |
|---|---|---|
| 任务与轮次 | 控制台库（task / a2a_message） | 黑板多维表格作为投影，供飞书侧浏览 |
| 能力授权 | 控制台库（capability） | 飞书卡片是通知入口，不存状态 |
| 运行态 | 控制台库（agent_run） | 飞书只推异常与升格摘要 |
| 知识库 | 本地 kb/（Git 可版本化） | 控制台提供浏览与编辑，飞书不承载正文 |
> 口径变更（重要）：v0.4 及以前的「没进黑板 = 没发生」，v0.5 起改为「没进控制台库 = 没发生」。黑板从事实源降为投影，理由是黑板本身没有事务、没有并发控制、无法承受高频写入，而运行态与 A2A 消息都是高频。投影失败只影响飞书侧可读性，不影响事实。
投影的三条纪律（不做这三条，双源迟早会打架）
1. 只允许单向：控制台 → 黑板。人在表格里手改的任何值都不回写，下次同步会被覆盖
1. 表格里必须显示「最后同步时间」，且同步超 60 秒时该行标灰；否则人会拿一份过期数据做判断
1. 关键状态不依赖投影：完成、阻塞、待批准这三类变化一律走卡片推送，投影只负责「想看全表时能看到」
### 1.3 为什么飞书链路必须保留
不是过渡妥协，是三条硬理由：
1. 人是移动的。 控制台是桌面形态，人不在电脑前时，唯一能触达的通道就是飞书。若砍掉，等于把「随时拍板」变成「回到工位」。
1. 卡片审批已经是现成能力。 飞书卡片能带按钮、能回传结果、能留痕，做「批准/拒绝」比自建推送便宜得多。控制台做审批台，飞书做审批入口，两者共享同一条记录。
1. 不重复造 IM。 自建 IM 意味着再做一遍消息、通知、已读、多端同步——这是投入黑洞，且永远不如飞书好用。
1. 控制台最终要长在飞书里。 按 §1.6 的规划，控制台会以「飞书网页应用」的形式嵌进飞书，人在飞书里点开就是实时数据、且免登录。到那一步，飞书既是入口也是宿主，控制台是它内部的一块能力——两者不是并列的两个系统，而是「外层入口 + 内层能力」。
> 这条也回答了「黑板要不要留」：一旦控制台能嵌进飞书，黑板那份表格副本的主要价值（让飞书侧能看到全貌）就被替代了，它只需退成周报快照（见 §12 第 11 条）。
反过来说，控制台也不该退化成 IM：不做对话主入口、不做长文讨论、不做消息流。第一期只做四屏：总览、任务、授权、知识。
### 1.4 数据流：一次任务在两面的样子
```
人在飞书群说「帮我把 macmini 上的评测跑一遍」
   ↓ Agent 解析，落控制台 task（未进库则拒收）
控制台：task 出现在任务屏，状态=待执行；agent_run 开始记事件
   ↓ 需要动线上资源
控制台：生成 capability 请求 → 飞书卡片推给人在手机上点「批准」
   ↓ 批准回写控制台，签发 15 分钟凭证
Agent 执行 → 事件进控制台 → 人可随时在看板看进度，不必问
   ↓ 完成
控制台：task 闭环、成本记账、产出登记
飞书群：只推一条摘要「跑完了，18 条通过 16，报告链接…」
```
关键点：飞书里出现的每一条，都能在控制台点开对应记录；控制台里发生的每件事，需要人知道的才推飞书。
### 1.5 控制台一期范围（四屏）
| 屏 | 内容 | 依赖需求组 | 出口 |
|---|---|---|---|
| 总览 | 一行一 Agent：机器、项目、当前任务、状态、最近事件、今日 token/花费 | R1 | 打开 3 秒内看清所有 Agent 在干什么 |
| 任务 | 一行一任务：下发人、承接、轮次、阶段、产出、耗时、成本；可下钻到事件与 A2A 线程 | R1 + R5 | 任一任务能回答「卡在哪一环」 |
| 授权 | 待批请求、生效凭证、历史审计；批准/拒绝/吊销 | R2 | 生产资源零长期凭证；吊销 60 秒生效 |
| 知识 | kb/ 条目浏览、编辑、候选采纳、索引重建与检索测试 | R4 | 同一问题第二次不再重复解释 |
第一期不做：拖拽式编排画布、多租户、移动端原生 App、自建 IM、跨组织账号体系。
原型：prototype/console.html（单文件，浏览器直接打开，含 mock 数据，四屏可切换、任务可下钻）。界面上所有黄色小圆点对应文末 §12 的待确认项，看完原型再定。
原型里体现的几条界面约定：状态用颜色 + 文字双编码（不靠颜色单传）；总览按「运行 → 等批准 → 等回应 → 空闲 → 离线」排序，最需要人干预的排最前；异常与待决策单独一块，不混进消息流；任务下钻是右侧抽屉而不是新页面，看列表时保持上下文；手机端导航收成一行，待确认入口进导航栏、不用悬浮球挡内容。
### 1.6 部署与访问形态
目标形态：本机起服务，frp 反向代理穿透到公网，电脑与手机都能访问；后期作为飞书网页应用嵌入，实现免登录。
```
手机浏览器 / 电脑浏览器 / 飞书网页应用（iframe）
              │ HTTPS
              ▼
   frps（公网服务器，443 端口，绑 control.<你的域名>）
              │ 加密隧道（frpc ↔ frps，token + TLS）
              ▼
   frpc（本机 MacBook，转发到 127.0.0.1:8787）
              ▼
   控制台进程（Node / TypeScript，SQLite）
```
穿透方案：frp（已有成熟部署，不列为本项目工作项）
选定 frp 的理由只记一句：它是唯一同时满足「有公网 HTTPS 地址（飞书 iframe 能加载）+ 不依赖第三方账号」的方案；Tailscale 的地址飞书侧访问不到，飞书私聊机器人承载不了页面。
本项目在穿透这件事上只负责三件：① 控制台只绑 127.0.0.1:8787，不自己处理 TLS；② 提供 /healthz 供 frpc 健康检查；③ 生成一份 frpc 配置片段（local_port / custom_domains / transport.tls）交付给已运行的 frpc。
frps 部署、证书、域名解析全部按你现有方案走，不在本项目的里程碑里。
登录分期（一期口令，二期飞书免登）
| 阶段 | 方式 | 细节 |
|---|---|---|
| M3（一期） | 口令 + 会话 | 单用户口令；HttpOnly + Secure + SameSite=Lax 的 Cookie，7 天滑动过期；连续失败 5 次锁 10 分钟；可主动登出全部会话 |
| M4（二期） | 飞书网页应用免登 | 页面在飞书 iframe 内加载 → 前端用 JSAPI 取免登 code → 后端换 open_id → 命中白名单即放行。需要在飞书应用里开通「网页应用」能力、配置应用首页地址与可信域名 |
| 长期并存 | 两种都在 | 外部浏览器仍走口令，飞书内走免登；两者落到同一个用户身份，审计里区分来源 |
公网暴露的代价，必须用这几条对冲
1. 只开 HTTPS，80 端口 301 跳转；证书用 Let's Encrypt 自动续
1. 应用层登录不能省——不能只靠 frp 的 basic auth，那只是第一道
1. 写操作带 CSRF token；所有 POST 校验来源
1. 页面永不返回密钥或凭证明文，只返回「已生效 / 已吊销 / 剩余 12 分钟」
1. 登录、登出、授权、吊销四类动作全部写审计
1. 可选加固：frps 侧按来源 IP 限流；控制台仅绑定 127.0.0.1，只由 frpc 转发
1. 移动端：375pt 起可用；总览屏竖屏自动切换为卡片流，不横滚表格
技术栈：TypeScript 全栈（与服务端 a2a 模块同语言），Node + SQLite + React；前端静态资源同进程托管，aw serve 一条命令起。审计库（capability_audit）与运行库分离，append-only，界面不提供删除入口。

## 三、R5 沟通机制与内容契约（P0）
### 3.1 现在的三个问题
问题一：通道混用。 群消息、黑板表格、邮箱、直连混在一起用。同一件事在群里说一遍、表里写一遍、邮件再发一遍；换个场景就不知道该走哪条，人也不知道该信哪一份。
问题二：消息没有骨架。 现在是「双面消息」——一行机器字段加一句人话。但机器那行只有 task_id / from / to / round，最重要的「要什么、给什么、什么时候要」全在人话里，机器读不到，也就没法校验、没法统计、没法自动升级。
问题三：内容质量靠自觉。 派活不说验收标准，汇报不给证据，「看着办」「尽快」这种词一出现，来回三四轮才发现理解错了。而且说不清是返工还是需求变更。
### 3.2 两层通道（邮件取消）
| 层 | 通道 | 谁在里面 | 承载什么 | 明确不做 |
|---|---|---|---|---|
| H 人机层 | 飞书群 @ | 人 + Agent | 人下任务、人看结论、人拍板；Agent 向人汇报关键节点 | 不做 Agent 之间的日常往返 |
| A 协作层 | 工作台系统内（API / MCP） | Agent ↔ Agent | 派活、问数、交付、阻塞、复核 | 人不需要逐条读 |
| F 事实层 | 飞书黑板 | 双方 + 人 | 任务、状态、轮次、交付物索引 | 不放讨论正文与临时结论 |
三条硬规则
1. 人机层只发生人关心的事：任务发布、关键结论、需要拍板、异常。其余不进群
1. Agent 之间一律走系统，不进群：群里出现的只能是结论摘要与指针，不是往返过程
1. 没进黑板 = 没发生：跨 Agent 事务必须有黑板记录，否则不计产出、不进看板、不算完成
邮件通道正式取消：它当初是为了绕开「机器人收不到对方消息」的临时手段；A2A 有系统内通道后，邮件只剩噪音与泄露面。
### 3.3 升格规则：A2A 什么时候才该惊动人
A2A 不刷群之后，人会担心「看不见」。解法不是全量抄一份到群里，而是定清楚什么时候必须升格。
必须升格到人机层的五种情形：
| 情形 | 升格到哪 | 卡片要说什么 |
|---|---|---|
| 需要授权（L2/C 类动作） | 飞书卡片 | 要做什么、对哪台、为什么、点批准或拒绝 |
| 卡住（block） | 飞书群 + 看板 | 卡在哪、已试过什么、需要人做什么决策 |
| 轮次超 3 | 飞书群 + 看板 | 双方各一句「分歧在哪」 |
| 交付完成 | 飞书群（摘要） | 一句话结论 + 产出链接 |
| 异常（超预算 / 失败重试耗尽） | 飞书群 + 看板 | 发生了什么、当前损失、建议动作 |
升格 = 推一条摘要，不搬全文。全文留在系统里，需要时点链接看。
反过来也定一条：没有触发以上五种情形的 A2A 活动，只在看板可见，不推送——否则「统一看板」会退化成一堆通知。
### 3.4 传输与唤醒（技术前提，必须先定）
A2A 离开飞书群后，必须有真正的消息通道。这里有个绕不开的难点，先摆出来。
服务端：工作台内置 a2a 模块，消息落 SQLite，提供三个接口——a2a_send（投递）、a2a_inbox（拉取未读）、a2a_stream（订阅推送）。每条消息带幂等键与 TTL。
客户端（每个 Agent 一个信箱适配器）
| Agent | 现状 | 怎么收消息 | 难点 |
|---|---|---|---|
| cc-connect + Claude Code | 常驻进程，但只对飞书事件响应 | 加一个 inbox 订阅，收到后注入一次 turn | 要改它的触发源，不能只认飞书 |
| WorkBuddy | 被动式，不常驻 | 定时拉取（cron / automation），或服务端投递时唤起一次 | 没在跑的时候叫不醒，只能排队等下次上线 |
离线与超时：目标不在线时消息排队，上线补投；ACK 超时后按 3.3 的升格规则通知人，而不是无限等。
跨机可达：本机（MacBook）与 macmini 不在同一台机器上，系统内通道要跨机。三种做法：
1. 内网直连（同局域网时最简单）
1. 隧道（Tailscale / Cloudflare Tunnel / frp），把工作台 API 挂到私有网络里
1. 退化方案：继续用飞书做传输，但走私聊机器人而不是群，人不可见
我倾向 2，代价最小且不影响现有飞书使用；第 3 种虽省事，但违背「Agent 交流不在群里」的初衷，只能当兜底。
### 3.5 消息骨架（机器层必填，缺则拒收）
```
{
  v: "a2a/1",
  task_id,          // 黑板记录号
  round,            // 第几轮，从 1 开始
  from, to,         // Agent 身份（宿主签发，不接受自述）
  intent,           // ask | assign | report | block | approve | reject
  summary,          // ≤ 80 字，一句话说清要什么
  expect,           // 期望对方做什么（动作 + 交付形态）
  deadline,         // 截止时间，必须具体到小时
  refs,             // 黑板记录、文件、链接
  auth              // 签发者与作用域
}
```
人话层不设格式，但必须回答三个问题：要谁做什么、什么时候、做完给什么。
校验规则（系统强制，不是建议）：
- intent 为 assign 时，expect 与 deadline 必填
- summary 超过 80 字拒收，要求压缩或改用 refs
- 出现「尽快」「看着办」「你懂的」「随便」等模糊词，退回并给出改写建议
- task_id 在黑板不存在 → 拒收，先建任务再说话
### 3.6 内容契约：三类消息的标准结构
派活（assign）五要素
1. 目标：一句话说清最终要什么
1. 验收：怎么算完成（可判断，不写「做好一点」）
1. 交付形态：文档 / 代码 / 表格记录 / 链接
1. 期限：具体时间点
1. 边界：不要做什么（这条最常被省略，也最容易出返工）
汇报（report）四段
结论先行 → 证据（文件、数据、链接）→ 未决项 → 下一步建议
提问（ask）三段
已排查什么 → 卡在哪一步 → 需要谁提供什么
卡住（block）必带
阻塞点、已尝试方案、需要的决策或资源、不解决会怎样。
### 3.7 状态机与升级
```
assign → ack → progress* → report(完成) 
                ↘ block → (unblock) → progress
                ↘ reject（拒收并说明原因）
```
- ACK 超时 15 分钟：系统内重投一次，同时在看板标「未响应」；重投仍无响应才按 2.3 升格通知人
- 单任务轮次 > 3：自动升级人工，要求双方各写一句「分歧在哪」
- 同一 task_id 同一 round 重复消息：幂等丢弃，只处理第一条
- 超期未完成：进入看板的「卡住」视图（与 R1 打通）
### 3.8 度量
| 指标 | 定义 | 目标 |
|---|---|---|
| 一发通过率 | 一轮就交付被接受的比例 | ≥ 60% |
| 平均往返轮次 | 完成任务的平均 round | ≤ 2 |
| 阻塞率 | 出现 block 的任务占比 | 观察，先建基线 |
| 平均响应时长 | assign 到首个 ack | ≤ 15 分钟 |
| 返工率 | 被人退回重做的比例 | 逐月下降 |
### 3.9 验收
1. 缺必填字段的消息被系统拒收，并提示补什么，不进入对方上下文
1. 抽检 20 条消息，人能在 10 秒内说出「谁要谁干什么、什么时候要」
1. 任一跨 Agent 任务在看板可查到完整轮次链，不需要翻群
1. 轮次超 3 自动升级，且升级原因被记录
1. 重复消息不会导致对方重复执行
1. Agent 之间的往返不出现在飞书群里：抽查一周群记录，除升格摘要外无 A2A 内容
1. 目标离线时消息不丢：上线后按序补投，且不重复执行
### 3.10 与现有规范的关系（v1.4 需升 v1.5）
《【规范】飞书空间 · 智能体协作 v1.4》里定的几条，这次要降级适用范围：
| 原规则 | 新定位 |
|---|---|
| 「必须 @ 对方」（用原生 <at>） | 降为人机层规则：Agent 对人说话必须 @；Agent 之间走系统，不需要 @ |
| 双面消息（机器行 + 人话） | 保留，但只用于人机层与升格摘要 |
| ACK 15 分钟 | 保留，语义从「群里回一句」改为「系统内确认」 |
| 邮箱备通道 | 删除 |
| L0–L2 风险分级 | 保留，并入 R2 能力授权 |
R5 要新增到规范里的内容：通道分层、升格五种情形、消息骨架与校验、内容三套模板、轮次上限。
落地顺序：模板 + 校验 + 黑板必填字段（一周内可上）→ 传输层与唤醒（依赖 3.4 的跨机方案）→ 状态机与看板打通。

## 四、R1 统一观测（P0）
> 本节所说的「看板」即控制台的总览屏与任务屏（§1.5）；飞书黑板是它的投影，不是它的本体。
### 4.1 现状与判断
两类 Agent 跑在两套 runtime 上：WorkBuddy（本机人格 Agent）与 cc-connect + Claude Code。
关键发现（已在本机验证）：两类 runtime 都落结构化会话记录，不需要改造它们就能观测。
| 来源 | 位置 | 字段 | 规模 |
|---|---|---|---|
| WorkBuddy | ~/.workbuddy/projects/<项目>/<会话>.jsonl | id、parentId、timestamp、type、name、callId、status、output、providerData、sessionId、cwd | 218 个会话 |
| Claude Code | ~/.claude/projects/<项目>/<会话>.jsonl | type、timestamp、sessionId、cwd、message（含 usage） | 247 个会话 |
| cc-connect | ~/.cc-connect/sessions/*.json | session id、agent_session_id、agent_type、created_at、updated_at、last_user_activity | 多会话 |
| 任务态 | 飞书黑板任务板 | task_id、from、to、action、status、round | 现行 |
结论：看板 = 一个采集器 + 一个归一化模型 + 两张视图，不动任何 Agent 的入口。
### 4.2 功能
- 采集：文件尾部增量读取（记录 offset），5 秒一轮；cc-connect 会话文件提供「哪个 Agent 在哪台机、绑了哪个项目」
- 归一化：统一成 agent_run（一次运行）与 run_event（过程中的事件）
- 视图 A｜全局看板：一行一个 Agent，显示所在机器、当前项目、当前任务、状态（运行 / 等批准 / 等回应 / 空闲 / 离线）、最近事件时间、今日 token 与花费
- 视图 B｜任务看板：一行一个任务，显示下发人、承接方、轮次、阶段、产出、耗时、成本
- 判定规则：60 秒内有事件 = 运行；有未批准能力请求 = 等批准；有未 ack 的 assign = 等回应；30 分钟无事件且进程在 = 疑似卡住；进程不在 = 离线
### 4.3 验收
1. 打开看板 5 秒内看到全部 Agent 的当前状态，无需刷新
1. 任一任务的每次工具调用与每条消息都能点开看摘要
1. 采集器 CPU < 2%，重启后不重复计数
1. 不改动 cc-connect 配置与飞书群，停掉看板不影响任何任务执行

## 五、R2 能力授权（P0，最高权重）
### 5.1 问题定义
现在 Agent 访问线上资源靠的是长期凭证：SSH 私钥在本地、云 AK 写在配置文件、数据库口令散在脚本里。一旦判断失误或被注入，损害不可逆，事后也说不清是谁做的。
要解决的不是「拦住某个命令」，是把「谁、在什么任务下、对哪个目标、能做多久」变成一张有期限的授权凭证。
### 5.2 能力模型
```
capability = {
  subject:  agent 身份（宿主签发，不接受自述）
  target:   资源标识（server:prod-api-01 / api:tencent-cvm / db:order-ro）
  action:   read | exec | write | restart | delete | grant
  scope:    命令白名单、路径前缀、SQL 只读、时间窗
  ttl:      默认 15 分钟，最长 4 小时
  approver: 人 或 仲裁 Agent
  ticket:   关联 task_id
}
```
### 5.3 三条访问通道
| 通道 | 适用 | 做法 |
|---|---|---|
| A 只读 API 代理 | 查日志、看指标、读配置、查数据库 | Agent 只拿代理凭证，代理用服务端密钥转发；SQL 强制只读、限行数、限表 |
| B SSH 临时证书 | 需要在服务器上执行命令 | 签发 15 分钟证书，登录即记录；命令走白名单，越界断开并告警 |
| C 人工在场 | 重启服务、改生产配置、删数据、改权限、对外发布 | 不给凭证：人执行 Agent 记录，或飞书卡片逐条批准 |
原则：能只读就不给写，能给 API 就不给 shell，能给 15 分钟就不给 1 小时。
### 5.4 流程
1. Agent 发起请求：要做什么、为什么、预计多久
1. 系统判级别（A/B/C）：A 直接签发并记录，B 一次批准，C 逐条批准
1. 批准在飞书卡片里点（复用现有链路）
1. 到期自动失效；任务完成可主动吊销
1. 全程写审计：谁、何时、对哪台、执行了什么、结果摘要
### 5.5 验收
1. 生产资源在 Agent 侧无长期凭证可用
1. 未批准高危动作拦截率 100%，并给出「怎么申请」的下一步
1. 凭证 TTL ≤ 15 分钟；吊销后 60 秒内失效（含踢掉已登录会话）
1. 每次访问可追溯到 task_id；审计不可修改
1. 伪造身份的请求被拒并告警
### 5.6 前置动作（需要你提供）
本机扫描：无生产 SSH 配置（仅 github.com），无云凭证文件。线上资源应是从别处访问的。需要一份资源清单：哪些服务器、用途、当前登录方式、谁在用。

## 六、R3 运行与产出量化（P1）

- 产出指标：交付物数量（文档 / 代码提交 / 表格记录 / 报告）、被采纳率

## 七、R4 知识沉淀（P1）
### 7.1 两层结构
| 层 | 内容 | 载体 | 谁写 |
|---|---|---|---|
| 会话记忆 | 当前项目的短期事实、偏好、未完成事项 | 每 Agent 一份 MEMORY（本地 Markdown） | Agent 自动，人有否决权 |
| 项目知识 | 方法论、结论、踩过的坑、可复用流程 | kb/ 下 Markdown 条目 + 索引 | 萃取后人工采纳 |
### 7.2 萃取流程
不做「把聊天记录全倒进向量库」——那只会得到一个谁也不看的垃圾桶。改成：
1. 任务完成或会话结束时，Agent 提 3 条候选（一条做法 / 一条结论 / 一条坑）
1. 人一键采纳或丢弃（飞书卡片，可批量）
1. 采纳的入 kb/，带元信息（适用场景、来源任务、最后校验日期）
1. Agent 每轮开工前自动预取 top-3
### 7.3 验收
1. 20 个真实问题回归：同一问题第二次提出时能命中已有条目，不再要求人重复解释
1. 条目可被人直接阅读与修改，索引可整库重建
1. 未采纳候选 7 天后自动清理

## 八、数据模型
控制台库（SQLite，唯一事实源）
- agent_registry：agent_id、名称、runtime、机器、项目根、绑定会话、可见范围
- task：task_id、标题、下发人、承接 agent、来源通道（feishu/console/a2a）、状态、阶段、轮次、预算上限、已花费、最后事件时间、待谁回应、产出
- agent_run：run_id、agent_id、task_id、started_at、last_event_at、status、tokens、cost
- run_event：id、run_id、seq、kind（message/tool/approval/error）、payload、created_at
- a2a_message：msg_id、task_id、round、from、to、intent、summary、expect、deadline、channel（h/a）、state、trace_depth
- capability：id、subject、target、action、scope、ttl、approver、ticket、state
- kb_entry / kb_index（FTS5 + 向量）
- projection_state：target（feishu_board / feishu_card）、last_synced_at、pending_count、last_error
审计库（独立文件，append-only）
- capability_audit：id、capability_id、actor、target、command_digest、result_digest、created_at
飞书黑板（降为投影，不承载事实）
新增字段：关联目标、预算上限、已花费、阶段、最后事件时间、当前轮次、待谁回应。
同步是单向的：控制台 → 黑板。投影失败记 projection_state.last_error 并重试，不影响任务判定；控制台提供「手工补投影」按钮。
> 保留黑板的原因不是当事实源，而是让飞书侧的人不必开电脑也能扫一眼进度。它的读性能、并发和事务能力都不足以承载高频写入，这一点在 v0.5 已改口径。

## 十一、里程碑
| 阶段 | 内容 | 出口标准 |
|---|---|---|
| M1 | 资源清单 + 通道边界确认 | 服务器清单与访问方式明确，A/B/C 边界定死 |
| M1.5 | 沟通契约（R5 轻量版） | 消息模板上线、必填校验生效、任务必填字段补齐 |
| M2 | 能力授权（R2） | 生产资源无长期凭证；高危拦截 100%；审计可查；审批入口先走飞书卡片 |
| M2.5 | A2A 通道（R5 传输层） | Agent 间往返脱离飞书群；跨机可达；离线消息不丢 |
| M3 | 控制台一期（总览 + 任务） | 两类 Agent 同屏可见，首屏 3 秒；手机可访问；口令登录生效；黑板投影可用 |
| M3.5 | 控制台二期（授权屏 + 知识屏） | 授权审批在控制台完成，飞书卡片保留一键入口；kb 可浏览可重建 |
| M4 | 产出量化（R3）+ 周报 + 飞书网页应用免登 | 周报自动出；任一数字可下钻；飞书内打开免登录 |
M1.5 单列的理由：它几乎不需要新基建（模板 + 校验 + 字段），但能让后面所有环节都有结构化数据可用；而且授权审批本身就要靠这条链路走。
M2.5 单列的理由：把 A2A 从群里搬出来不是配置改动，需要「服务端 + 信箱适配器 + 跨机通道 + 唤醒机制」四件东西齐备；没齐之前贸然停群会让协作直接断掉，所以它要和 M3 控制台（能看到消息去向）配对上。
M2 先于 M3 的理由：控制台是「看见」，授权是「兜底」。看不见会慌，兜不住会出事——后者不可逆。所以授权先上，但审批入口先用飞书卡片（复用现成能力，不必等控制台），等 M3.5 再把审批台搬进控制台，卡片退为通知与一键跳转。
M3 拆成两期的理由：总览与任务两屏吃的是同一套采集与归一化数据，一起做最省；授权屏要接凭证签发与 SSH/MCP 代理，复杂度是另一个量级，单独一期更稳，也避免一期做太久看不到东西。
