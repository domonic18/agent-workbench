# M2-2 Teleport CE + tbot 接入 验收记录

> 归属: M2-2 Teleport CE + tbot 接入 ｜ 验收日期: 2026-10-31 ｜ 依赖: M1-5(Teleport 契约定稿)
> 出口标准: 签发 15 分钟证书;按 renewal interval 续期;每 Agent 一个 bot + 每任务一个 trait,`aw-task-id` 由 `cert_extensions` 以 `{{ external.aw_task_id }}` 插值;库中只存 `ticket_id`。

## 结论

- 适配器 `src/adapters/teleport/` 落地:manifest 白名单渲染、`tctl create --force -f -` 经 stdin 写入、`execFile` 无 shell 执行、错误不带清单内容;12 条单测覆盖。
- 本地 Docker Teleport CE 18.7.3 实测:请求 15m 实发 **16m**(1m 时钟余量);两个 bot 的 `aw-task-id` / `aw-ticket-id` 均正确插值为任务与票据标识;`internal.*` 按预期保留字面量。
- 续期成立:同一个 bot 以 30s TTL / 10s interval 续期,12s 与 24s 两次取样证书哈希不同。
- SSH 面成立:`agentwork` 登录成功,`root` 被拒(`access denied`);`session.start` 的 `user_traits.aw_task_id` 带 `task-0001`。
- **新发现(已回写 05 §7)**:bot traits 异步同步到 Teleport user;同步完成前签发会把 `{{ external.* }}` 原样写进证书。签发前必须等 user 上的 trait 就位。

## 口径

- 验证环境:127.0.0.1 + 自签 CA,全部跑在 Docker(compose 项目 `aw-teleport-spike`);复现脚本 `docker/spike/run.sh`(`up|ssh|renew|report|down`)。
- 本次只验「签发 / 续期 / traits / SSH」四项;公网 `tp.example.com` 与 frpc 第二条规则按用户裁决推迟,不在本记录范围。
- 库侧只记录 `ticket_id` 的约束由 M2-1 表结构承担(`capability.ticket_id`),本次不写证书内容到任何库表。

## 同步窗口(新发现,影响 M2-3)

- 现象:首次干净跑时 `bot-b` 证书里是字面量 `{{ external.aw_task_id }}` / `{{ external.aw_ticket_id }}`。原因是 `tctl create` 写入 bot traits 后,traits 异步同步到 Teleport 的 user 资源;证书插值读的是 user,同步未完成即签发就会写入未插值模板。
- 实测:轮询 `tctl get user/bot-<name>` 至 ticket 出现,同步耗时约 **229ms**;等待后重新签发,两个 bot 均正确插值。
- 处置:`run.sh` 增加 `wait_bot_traits` 在签发前轮询。生产侧 **M2-3 不得假设「写入 traits 后立即签发即新值」**:批准后置 `issuing` 只是发出写入;证书生效以下一次续期为准,「已生效」只能由对账(证书扩展 / `session.start.user_traits`)确认,不能由写入成功推断。M2-7 对账按此口径实现。
