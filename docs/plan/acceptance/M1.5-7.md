# M1.5-7 抽检验收记录

> 归属: M1.5-7 抽检验收 ｜ 验收日期: 2026-10-31 ｜ 依赖: M1.5-2(信封校验)、M1.5-5(指令解析与回执)
> 出口标准: 每条能在 10 秒内说清「谁要谁干什么、什么时候要」;拒收样本写明缺哪个字段。

## 结论

- 20 条样本按预期判定:**13 条收下、7 条拒收**,无一条需要补一个再试一次。
- 13 条有效样本逐条能读出四要素:谁(`from`)→ 向谁(`to`)→ 干什么(`summary` / `expect`)→ 什么时候要(`deadline`)。
- 7 条拒收样本的缺失项 / 非法项与 `validateEnvelope` 实跑输出逐字一致;拒收原因定位到字段,不返回笼统的「格式错误」。
- `notify` 免 `deadline` 是契约允许的:`S08` / `S09` 只回答「谁告诉谁什么事」,「什么时候要」不适用。

## 口径

- 样本取自本项目真实协作场景(接口契约、测试数据、知识条目、只读核对、周报素材),不构造无意义字符串。
- 20 条样本原样喂给 `src/shared/protocol.ts` 的 `validateEnvelope`(M1.5-2 产出),下表「校验结果」为当日实跑输出;同一批规则由 `src/shared/protocol.test.ts` 长期覆盖。
- 「10 秒可读」的判定方式:只看信封、不看上下文,按四要素口述;任一列为「—」即不通过(`notify` 的 `deadline` 除外)。
- 本次验收只覆盖**校验器的缺失项集合**;面向 Agent 的 A2A 回执文案在 M2.5-3 发件箱入口落地,不在本记录范围。

## 拒收样本(7)

| # | intent | 谁 → 向谁 | 缺陷字段(实际回执) | 为什么被拒 |
|---|--------|-----------|--------------------|-----------|
| S14 | request | WorkBuddy → Codex | `summary` / `expect` / `deadline` 三项同时 missing | 三条必填全缺,一次报全,不要求分批补 |
| S15 | request | WorkBuddy → Codex | `deadline` missing | request 必须给交付时限 |
| S16 | request | WorkBuddy → Codex | `intent` invalid | `ask` 不在 `request / reply / notify / escalate` 内 |
| S17 | request | WorkBuddy → Codex | `v` invalid | 未知协议版本 `2.0`,当前只接受 `1.0` |
| S18 | request | WorkBuddy → Codex | `summary` invalid | 201 字符,超过 200 上限;正文应走 `refs` |
| S19 | request | WorkBuddy → Codex | `round` invalid | `0` 不是 ≥ 1 的整数(且 `round` 本应由服务端分配) |
| S20 | request | WorkBuddy → Codex | `deadline` invalid | `2026-11-02` 不是 RFC3339 时间,无法判定截止时刻 |

S14–S20 中,除缺陷字段外其余字段均合法,因此回执只指向缺陷字段,不会顺带报无关项。
