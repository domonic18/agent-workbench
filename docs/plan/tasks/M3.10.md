**M3.10-6 验收剧本（复演 11-08 事故，七步）**

1. 起 CC系统开发2号交互会话在目标仓开发（保持活跃 + 工作区脏）；
2. 经测试专家一次报 5 bug；
3. 断言：WorkItem ×5 即时建立；**群播报一次**「已挂起」；无 Claude 派发会话产生；事项详情可见挂起原因与挂起时长；连续多轮派发被挡后转入退避；
4. 结束交互会话、提交或清理工作区；
5. 断言：退避周期内自动唤醒 → **一个**无头会话领 5 件 → **一个** PR 带 5 个 `Fixes #`；群里仅收口播报，不逐件刷屏；
6. 合并 PR → 5 个 issue 逐个关闭 → 各 WorkItem 走人工接受收口；
7. 反向演练：派发会话运行中强杀 → 2h 后回收作业 blocked task + 重排 assignment，闸门放行后自动重派；第二次失败后停在 stalled 不再自动重试。

对应图示：[常规批次](../../arch/diagrams/dispatch-coordination-s1-batch.html)、[挂起后自动接手](../../arch/diagrams/dispatch-coordination-s2-hold-resume.html)、[僵死回收重排](../../arch/diagrams/dispatch-coordination-s3-zombie-reclaim.html)。

**明确不做**：`dispatch_mode` 枚举（D1）、紧急插入按钮（D3）、WorkItem 合并、在线 Slow Router、管控交互会话本身、任务附件一等公民与死信推送（D7/D8 维持 A2A 现语义）。

**实现注记（相对设计裁决的偏差）**：G2「cwd 活跃会话」不取 `streams.updatedAt`（它每轮扫描必刷新，恒为"活跃"，判不出真会话）；改按会话文件 mtime 双采样判"仍在写入"——两轮派发间 mtime 有前进或窗口内新出现的文件才算活跃，避免刚结束的派发会话把下一批挂起 15 分钟。语义不变（≤15min 活跃窗口、G3 为更强信号），实现按此落地。
