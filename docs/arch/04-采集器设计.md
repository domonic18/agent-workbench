# aw-node 执行面设计

> 创建日期: 2026-10-29 ｜ 重命名: 2026-11-03（原「采集器设计」）
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。入库结构见 [02-数据服务设计.md](./02-数据服务设计.md)。

## 1. 定位

每台运行 Agent 的机器只部署一个 **`aw-node`**，其中采集模块贴近数据源做增量读取并推送控制面，调度模块负责 Claude Code 的 A2A / Assignment / Input 唤醒。执行机不再部署 MCP proxy 或独立 dispatch 服务，控制面不直接访问其他机器的文件系统。

| 项 | 约定 |
|----|------|
| 形态 | 每机一个 Node 进程、一个安装包、一个 launchd 服务、一份配置；采集与调度是内部模块 |
| 驻留 | launchd（`KeepAlive=true`），开机自启，崩溃自动拉起；单实例锁防重复副作用 |
| 方向 | **采集模块只推不拉**；调度模块只拉本机 Agent 的工作收件箱，控制面不反向访问机器文件系统 |
| 状态 | 断点与缓冲落在本机 `~/.aw-node/`，不依赖内存；单实例锁同样落盘，调度侧的并发防护由它保证（见 §2.2.1） |

**为什么不做中心化轮询**：控制面若直接读远端文件，需要开放 SSH 或共享目录，权限面远大于「单向 HTTPS 推送」。

aw-node 不做安全判定、不代理第三方 MCP，也不接管 Claude Code 原生工具；这些均不在执行机管控边界内。

## 2. 采集对象

| 来源 | 内容 | 增量依据 |
|------|------|----------|
| Claude Code 会话文件 | 每轮对话、工具调用、token 用量 | 文件追加写入，按字节偏移读 |
| cc-connect 运行日志 | 消息收发、投递结果、异常 | 同上 |
| 本机进程与系统指标 | CPU、内存、Agent 进程存活 | 周期快照，不做增量 |

采集器**只读**，不修改被采集文件，也不向 Agent 注入任何内容。

**当前运行时边界（2026-11-03 裁决，2026-11-06 修订）**：采集模块只解析 Claude Code / cc-connect 的会话与日志。无 aw-node 的外部运行时（WorkBuddy/Codex/DeepSeek harness）可通过控制台远程 MCP 和官方 automations 参与协作，但首版**明确不采集其 Run、对话或 Token**；这些字段显示「未接入 / —」，不是 0、离线或采集失败。首版只保留 Task、A2A、Assignment 与产出等业务事实。**判别依据是 `runtime='claude_code'` 且 `agent.machine_id` 非空**——外部运行时即便登记了宿主机器也不归采集侧管，`machine_id` 现在只是「宿主机器」标注，不再是「有没有采集器」的单字段开关。

**下发给 aw-node 的配置只含 `claude_code`**：外部运行时即便绑了机器，其配置由自己的客户端持有，不由本机 aw-node 写进 `claude.json`。

**不判定 run 边界**：采集器只上报事件与 `occurred_at`，一段 run 的起止由控制面判定（口径见 [02](./02-数据服务设计.md) §3.2）。采集器侧若用文件 mtime 自行切分，会与总览口径打架，且文件口径在多进程共用时无法区分。

**run 收尾三层信号**（2026-11-09 裁决，M1–M3 实装）：收尾职责按「事实离谁近谁宣告」分三层——①惰性切分（同流新事件 ≥30min 间隔，控制面既有路径）；②进程退出宣告（M2 实装：aw-node 对自己 spawn 的派发会话在退出时以机器 Bearer 上报 `POST /api/aw-node/run-end`，它作为父进程拥有 firsthand 事实；best-effort——失败重试一次，再失败放弃）；③兜底收敛（M1 实装：控制台 `run-reclaim` 作业把滞留 `running` 超 30min 的 run CAS 收尾，`end_reason` 三值可审计；M3 实装 L2 豁免——心跳携带 `active_streams`（自上一跳有新字节的流），机器心跳新鲜且报了该流的 run 不收，见 §6）。不变量：`running` 是临时状态，任何信号源失联仍须在有限时间收敛为 `ended`。执行面派发闸门（G2/G4）继续用本地观测、不查控制台 run 表——投影只服务展示/统计/审计。

CPU / 内存**只随心跳上报，不入库、不建表**：它们服务于「这台机是不是快撑爆了」的即时判断，不是分析数据。若将来需要趋势，再单独加 `metric_snapshot` 并另定保留策略，不在这版预埋。

### 2.1 观测事件与业务 Trigger 的边界

采集器看到的是本地执行与通信产品的记录，不代表它拥有这些系统的全部消息，也不代表文本中的请求已经过身份与授权验证。因此：

- `/api/ingest` 产生的会话、工具、进程、心跳和 token 数据默认是**观测事件**，用于 Run、只读对话、用量和已关联事项的进展判断；不会因为出现「请修复」「可以发布」等正文就直接创建可执行工作。
- 可驱动工作的 `work_trigger` 只能由 [01](./01-后端服务设计.md) §9 登记的可信 Source 适配器或内部领域事件产生。控制台机器人、专用 Bug 机器人、GitHub / CI 各自验证来源；采集器不是这些来源的替代品。
- 已关联工作事项的 Run 事件可以作为进展证据，但不能改变授权范围；无 Task 的 Run 仍可只读展示，不为了路由或统计补建任务。
- 采集器不订阅飞书、不接管 Agent 输入、不向 Agent 注入续接指令。业务 Thread 的后续事件如何到达 Worker 由对应 Source / 执行适配器负责，不能假设采集器能看到或推动全部对话。
- 心跳、日志增长和 Token 增加只说明活动或消耗，不等于实质进展；进展判定在控制面按 [01](./01-后端服务设计.md) §9.5 执行。

这条边界避免把「读到了一句话」误当成「验证了谁在说、是否有权做」。若未来确需从本地会话形成业务候选，也只能先进入无执行授权的评估，不得借采集通道绕过人工确认与 `decide()`。

### 2.2 调度模块

图示：[派工协调系统架构](diagrams/dispatch-coordination-architecture.html) ｜ 场景 [常规批次](diagrams/dispatch-coordination-s1-batch.html) / [挂起后自动接手](diagrams/dispatch-coordination-s2-hold-resume.html) / [僵死回收重排](diagrams/dispatch-coordination-s3-zombie-reclaim.html)

- 对本机已登记的 Claude Code Agent 拉取 A2A / `worker_inbox`，有待处理工作才 spawn headless 会话；拉取、锁与唤醒命令只能使用已登记配置，不从采集文本推导。
- Assignment 由 Agent 读取后自行创建 Task 并 ACK；Input 只表示后续事件消费。aw-node 不代替 Agent 建 Task，也不把 ACK 解释为 WorkItem 完成。
- 进程异常或会话中途死亡时，未 ACK 项由控制面租约回收；aw-node 重试不得重复建 WorkItem 或 Task。
- WorkBuddy 不经过 aw-node 调度，使用官方 automations 轮询；首版过程数据留空不影响其业务事实回传。

#### 2.2.1 A2A 调度循环（2026-11-05 实装）

调度循环是 `aw-node` 的第五个循环，与采集的四个循环并列：

| 项 | 裁决 |
| --- | --- |
| 轮询 | `AW_DISPATCH_MS`（默认 30s，置 0 关闭）；`AW_SESSION_TIMEOUT_MS`（默认 30min，超时先 SIGTERM 再 SIGKILL） |
| 触发条件 | a2a 或 work 任一收件箱有**待领取**条目才起会话；两者皆空零 spawn（静置不打扰）；过闸门前不探视退避期内的 Agent（见 §2.2.2） |
| 探视方式 | 先 `GET /api/a2a/inbox?wait=0&peek=1`，a2a 命中即起协作会话；未命中再 `GET /api/work/inbox?wait=0&peek=1`——都是**只看不领**，不占用消息/行租约；条目原样留给 Agent 自己的会话领取（普通拉取会占 30s 租约，Agent 会话随后领不到，形成活锁） |
| 会话 | 在该 Agent 的项目目录下 `claude -p <提示词> --session-id <预生成uuid> --allowedTools Read,Grep,Glob,Bash,mcp__aw-console`（会话 id 预生成是为了能提前登记归因，见 §4.0.1）；a2a 唤醒用六步协议提示词，**按收到的 intent 分支**（request/escalate：task_create→a2a_ack 带 task_id→干活→a2a_send 回执→task_update 收尾 `status=done`；reply/notify：只 a2a_ack，不建任务也不回执——对回执再回执会形成乒乓、根任务无法自动收口），work 唤醒用批次化工作提示词（见 §2.2.3），变更需同步本节 |
| 收尾口径 | 提示词与 `task_update` 工具说明都点明「关单只需 `status=done`，stage 可停在任意阶段」，并禁止把 `review` 直接跳到 `closed`（非法跃迁会让 Agent 放弃收口，根任务随之无法自动收口；2026-11-06 跨设备实测） |
| 防重 | 同一 Agent 同时只允许一个会话（内存 busy 集，aw-node 每机单实例锁保证其成立；消息租约另作一层保护，被会话领走的消息不再可见）；会话退出清 busy；a2a 待办优先于 work 派工，同一轮不混用两种提示词 |
| 密钥 | Agent Bearer 只存本机 `config-state.json`（0600）；存量机器从 `claude.json` 受管 MCP 头按 `agent_id` 前缀自校验回填 |
| 停机 | 终止在跑子会话；未被 ACK 的消息随租约过期自动回收，下轮重试 |
| 失败隔离 | claude 路径解析不到或单 Agent 探视失败，都只跳过该 Agent，不影响采集与其他 Agent |

`peek` 是服务端对收件箱的加性查询模式，只返回可见消息/待领取行、不领取、不等待唤醒；Agent 正常拉取的行为不变。

#### 2.2.2 派发闸门 G1–G4 与退避（2026-11-09 实装，M3.10-2）

2026-11-08 并行派工事故后，调度循环在探视命中之后、spawn 之前过一道闸门链：**挡下 ≠ 取消**，条件消失后下一轮照常派发。

| 闸门 | 判定 | 挡下行为 |
| --- | --- | --- |
| G1 | 同一 Agent 已有会话在跑（内存 busy 集） | 直接跳过（既有行为） |
| G2 | Agent 的 cwd 有活跃 Claude Code 会话在写：`~/.claude/projects/<dir映射>/<uuid>.jsonl` 的 mtime 较上轮采样前进；启动首轮无基线时按 `AW_BUSY_SESSION_WINDOW_MIN`（默认 15min）窗口兜底 | 不派发，work 派发路径上报挂起原因 `cwd_session_active` |
| G3 | cwd 工作区脏：`git -C <cwd> status --porcelain` 有输出；探测失败（非 git 目录等）按 unknown 放行并 WARN | 不派发，上报 `dirty_worktree` |
| G4 | 全机活跃会话数（含交互会话）≥ `AW_MAX_MACHINE_SESSIONS`（默认 2） | 不派发（软挡，不写原因行） |

- **挂起上报**：`POST /api/work/hold`（Agent Bearer，幂等）——控制台只在 reason NULL→非 NULL 的首跳写 `worker_inbox.reason` 并向协作群播报一次（卡片写明「条件消失后自动恢复派发，无需人工干预」），重复上报不刷屏；领取派工即清空 reason，重投后再挂可再播。a2a 派发被挡不上报（a2a 收件箱无 reason 行）。
- **退避**：同一 Agent 连续被挡 `AW_DISPATCH_BACKOFF_ROUNDS`（默认 5）轮 → 探视间隔退避 5min；空闲轮与放行轮清零计数，退避到期自动恢复。
- 采样纪律：会话活跃采样每轮至多一次（首个过闸门的 Agent 触发，同轮复用），空闲轮零 I/O；轮末换基线，两轮比 mtime 前进判「仍在写」。

#### 2.2.3 工作唤醒的批次交付语义（2026-11-09 实装，M3.10-3）

work 唤醒提示词按批次化交付改造，六条纪律（上限数值由 `AW_BATCH_MAX_ITEMS`（默认 8）运行时注入提示词，不是写死文案）：

1. `work_inbox` 领取**全部**待处理行，单批最多 N 件，超出留在收件箱等下一批（防超大 PR 不可评审）；
2. 逐件 `work_read` + `task_create(work_item_id)` + `work_ack`（审计粒度保留，每件独立绑定任务）；
3. 同批全部事项在**同一个**语义化分支上修复，按件分 commit（`fix: #<N> 标题`）；
4. 只提**一个** PR，body 逐行列 `Fixes #<N>`（GitHub 合并即逐 issue 关闭，并触发各关联事项合并即自动验收收口——批量 PR 在路由层逐事项扇出，2026-11-09）；
5. 确实修不了的单件 `work_handback` 退回，**其余照批交付**——不因一件卡整批；
6. 开工前自查 `git status --porcelain`：若闸门放行后工作区已被占用（竞态窗口），**不领取不动手**，回复「工作区被占用」结束回合，行保持 pending 由下一轮闸门重新把关（设计取舍：查在领取之前，行不进租约等待，恢复全自动；若查在领取后则需等租约过期回收，且已 ack 的件要靠重排兜底）。

## 3. 断点续读

断点三元组：`(path, inode, offset)`。

```
读取前                       读取后
┌──────────────┐            ┌──────────────┐
│ inode = 1234 │            │ inode = 1234 │
│ offset = 8192│ ──读取──▶  │ offset = 9216│
└──────────────┘            └──────────────┘
        │
        └─ 若当前 inode ≠ 记录 inode ──▶ 判定文件轮转，offset 归零
```

| 情况 | 处理 |
|------|------|
| 文件变短（`size < offset`） | 判定截断或轮转，offset 归零重读 |
| inode 变化 | 判定轮转，offset 归零重读；旧 inode 的残留缓冲照常投递 |
| 读到半行 | 不提交该行，offset 停在行首，下次续读 |
| 文件暂不存在 | 记录状态，等待下次轮询，不报错退出 |

**提交纪律**：只有在控制面 ACK 后才推进 offset。宁可重复投递，不可丢事件；重复由控制面幂等吸收。

## 4. 推送协议

`POST /api/ingest`，`Content-Type: application/json`，`Authorization: Bearer <machine_id>.<secret>`（口径见 [01](./01-后端服务设计.md) §3.1）。

```json
{
  "collector_id": "macmini-01",
  "agent_project": "lokta-acore-manager",
  "stream_id": "claude-session:b20e60f5",
  "batch": [
    {
      "seq": 10241,
      "inode": 1234,
      "offset": 9216,
      "kind": "turn",
      "occurred_at": 1761800000000,
      "payload": { "...": "原始事件" }
    }
  ],
  "sent_at": 1761800000500
}
```

| 字段 | 作用 |
|------|------|
| `collector_id` | 采集器身份，控制台据此区分机器 |
| `agent_project` | 本流所属 Agent 的 cc-connect 项目名；控制台按 `(collector_id, agent_project)` 解析到 `agent.id`（`collector_id` 即 `machine.id`，等价于 `(machine_id, agent.project)`） |
| `stream_id` | 逻辑流（一个会话文件一条流） |
| `seq` | 本流内单调递增；按文件字节偏移编码（×100），空间远超 int4，服务端列一律 BIGINT（0008 裁决）；去重键是 `(collector_id, stream_id, seq)`，不能只用 `(stream_id, seq)` |
| `inode` + `offset` | 控制台回存为 ACK 断点，用于核对 |
| `kind` | 事件类型，控制台按此路由到不同解析器 |

**响应**：`200 { "acked_seq": 10241, "rejected": 0 }`。控制台处理到哪条就 ACK 到哪条，允许部分成功。`rejected` 是本批被跳过的坏项数（见下）。

**坏项隔离**：一条内容存不下的事件（校验失败，或 PostgreSQL jsonb 拒收的字符）不该把整条流堵死——重试多少次都是同样结果。控制台分两类处理：

| 失败类型 | 判定 | 动作 |
|---------|------|------|
| 毒丸项 | 业务校验失败，或 PG 错误码属数据类（22x / 23x） | 跳过该条，记一条 `ingest_rejected` 事件留痕（原 kind、seq、失败原因），批次继续，ACK 越过该条 |
| 瞬时错误 | 连接中断、死锁等 | 整批停下，返回已提交的最大 `acked_seq`，采集器退避重试，事件不丢 |

单批最多跳 5 条坏项；超过说明是系统性故障，整批停下等重试，不静默丢数据。

**payload 可存化**：PostgreSQL jsonb 拒收 NUL 与孤立代理项（`22P02 unsupported Unicode escape sequence`），而工具结果预览等字段可能原样带二进制内容。控制台落库前把这两类字符换成 U+FFFD，保证事件内容可存；被替换的位置在 payload 里留有替换符，不静默改写语义。

**鉴权**：`Authorization: Bearer <machine_id>.<secret>`。控制台按 `machine_id` 取 `collector_secret_hash` 做常量时间比对；不匹配一律 401 且**整批拒收**，不部分入库。请求体不做签名——重放由 `(collector_id, stream_id, seq)` 幂等吸收（见 §5）。

**会话归因（唯一口径）**：采集器读 `~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl`，拿 `session-uuid` 反查 `~/.cc-connect/sessions/*.json` 的 `agent_session_id` 或 `past_agent_session_ids`（同一份档案的两个字段，会话轮换后旧 id 仍在档），得出 cc-connect 项目名填入 `agent_project`。join 的键是 UUID 不是路径——`/dir` 换 cwd 不影响归因。

| 档 | 条件 | 动作 |
|----|------|------|
| 1 | 命中当前或历史 session id，只命中一个项目，且该项目已登记 | 正常推送 |
| 2 | 命中多个项目 | 该流**不推送**，留在 spool；计入 `unattributed_streams`（真歧义，需人工裁） |
| 3 | 未命中任何 cc-connect 会话状态（终端直跑、历史已清） | 不推送，只写本地日志；**不计入** `unattributed_streams` |
| 4 | 命中项目但控制台未登记 | 不推送，留在 spool；计入 `unattributed_streams`（漏登记或名字写错） |

采集器从 `AW_AGENT_PROJECTS` 读取本机已登记的项目名列表（由安装 / 登记脚本按控制台 `agent_project` 表写入；登记变化时重写 plist 并 `kickstart -k`）；档 2/4 的流因此能在本地就被拦住，不必每轮推上去换一个 400。

**已登记口径**：指控制台 `agent_project` 表，**不是** cc-connect `config.toml`——本机实测后者只登记 4 个项目而会话状态有 6 个，拿它当注册表会漏。

**不存在第二通道**：采集模块与 Agent 进程不共享环境变量，「启动器注入 `AW_AGENT_ID` 让采集模块读」不成立；按目录名反推又会被 `/dir` 打散。归因只有这一条路，对不上就如实记成未归因，不许猜。

#### 4.0.1 派发会话的本地归因登记（2026-11-09 实装，M3.10-5）

aw-node 自己 spawn 的 headless 会话**不在 cc-connect 会话档案里**——`~/.cc-connect/sessions/*.json` 只记 cc-connect 起的会话，调度器起的会话 uuid 从不登记。按上面的唯一口径，这类流必然落档 3（不推送、只写本地日志），于是控制台侧**一条 `agent_run` 都不落**（2026-11-08 事故时段实测 0 行：派工看起来发生了，对话、Token、进展证据全空）。

修法不是给采集器开第二通道，而是**在派发侧把归因登记补齐**，让派发会话也走上同一条归因口径：

| 环节 | 做法 |
| --- | --- |
| 会话 id | spawn 前由 aw-node 预生成 uuid（`randomUUID()`），随 `claude --session-id <uuid>` 传给 CLI——CLI 原生支持该参数，会话文件按此命名，归因的 join 键仍是 uuid |
| 登记 | spawn **之前**就把 `uuid → project` 写进采集器本地的**活引用注册表**（`dispatchSessions`），登记时即生效；登记晚一步就会留出「会话已在写、归因还没接上」的窗口 |
| 叠加 | 注册表以 `overlayAttributionIndex` 叠加在 cc-connect 索引之上：命中取两者并集；`projects()` / `sessionCount()` 也一并合并 |
| 活引用而非 TTL | 叠加必须**活引用**：若走 60s TTL 刷新索引，档 3 的「跳过不推送」会把会话开头一段事件直接判成断点跳到 EOF，这段数据永久丢失——宁可多占内存也不延迟登记 |
| 归档 | 项目名取控制台 config-sync 下发的 `AppliedAgentState.project`，与 ingest 侧按 `(machine_id, project)` 匹配 Agent 的键一致，否则归因到了项目也落不成 `agent_run` |

终端直跑（真·档 3）仍是「不推送、只写本地日志」，不受本机制影响——登记只覆盖 aw-node 自己起的会话。

以下两条是实测事实，不是异常分支：

- `~/.cc-connect/sessions/*.json` 只是**指针与回放副本**（`agent_session_id` + 少量 history），不含 token usage 与工具调用；token 用量与产出必须从 `~/.claude` 的 jsonl 读。
- 本机实测（S5，2026-10-31，本机即 macmini）：66 个 cc-connect 会话 id（16 当前 + 50 历史）对 74 条 jsonl 流，38 条可归因（11 命中当前 id + 27 仅命中 past id）、28 个悬空指针、0 条多项目歧义；36 条未归因流里 18 条是 `/private/tmp` 的试验会话，真实项目未归因约 18 条。只认当前 id 会漏掉 27 条，所以历史 id 必须一起认。档 2/4 是常态，控制台收到解析不了或未登记的 `agent_project` 必须整批 400，不静默归属。

## 5. 缓冲与重试

```
采集 ──▶ 内存队列 ──▶ 本地 spool 文件 ──▶ 推送
                          ▲                  │
                          └──── 失败回写 ────┘
```

| 项 | 约定 |
|----|------|
| 先落盘再推送 | 事件先写 spool，推送成功后再标记已确认 |
| spool 格式 | 按行 JSONL，文件按日期滚动，单文件上限 32MB |
| 重试 | 指数退避 1s → 2s → 4s … 上限 60s，带 ±20% 抖动 |
| 上限 | spool 总量上限 512MB；超过后丢弃最旧的、未确认事件并告警——宁可丢旧数据，不可写满磁盘 |
| 幂等 | 重试携带同一 `seq`；控制台按 `(collector_id, stream_id, seq)` 去重，重复不重复入库。去重窗口 7 天，过期后可重放——超出窗口还迟到的事件按新事件处理 |
| 顺序 | 单流内严格顺序投递；多流之间并行 |

## 6. 心跳与健康

- 每 60s 发送一次心跳：`{ collector_id, uptime, pending_bytes, unattributed_streams, cpu, mem, last_error, streams: [...], active_streams: [...] }`。`unattributed_streams` 是 §4 档 2（多项目歧义）与档 4（项目未登记）滞留的流数；纯终端直跑的档 3 不计入，否则任意 CLI 会话都会把指标打成红色。
- `active_streams`（M3，L2 观测续命）：自上一跳以来**读到新字节**的流，由扫描轮标记、心跳轮取走上报；控制台整包覆盖 `machine.active_streams`，据此豁免这些流上 running run 的兜底收敛。取走即排水——心跳失败丢一跳不致命：流继续写会被下轮扫描重新标记，流停写则本就不该再豁免。
- 控制面按 `collector_id` 更新 **`machine.last_seen_at`**（不是 `agent_run.last_seen_at`——机器活着不等于 Agent 在跑）；超过 5 分钟未更新标记「心跳超时」，超过 30 分钟标记「离线」。
- 采集器自身不判断 Agent 状态，只上报事实；状态判定在控制面。

## 7. 安全

| 面 | 措施 |
|----|------|
| 传输 | 经 frp 的 HTTPS；不接受明文 HTTP |
| 鉴权 | Bearer 采集器密钥；控制台侧只存 `collector_secret_hash` |
| 最小权限 | 采集模块只读被采集目录、不监听端口、不执行外部命令；调度模块仅执行已登记的 Claude Code 唤醒命令 |
| 密钥 | 控制台签发一次性 enroll token，安装脚本据此换取机器 ID 与长期采集密钥；长期密钥明文只在兑换响应出现一次，随后仅存在于 aw-node 的 env / launchd plist，控制台库只存哈希。令牌与密钥均不进日志，缺失或重放即拒绝 |
| 日志 | 记事件与计数，不记消息正文与凭证 |

## 8. 部署

**目标形态（2026-11-03 裁决）**：每台执行机只有一个 `aw-node` 可执行产物、一个 launchd 服务与一份配置，采集和 Claude Code 调度作为内部模块运行。旧 `aw-proxy.mjs`、独立 `aw-dispatch`、enroll wrapper 和双 launchd 服务不再进入新基线（2026-11-05 已从仓库移除，连同 SQLite 迁移目录与 `better-sqlite3` 依赖）。

```bash
# 首次加入：需要一次性 enroll token
curl -fsSL https://aw.example.com/artifacts/install.sh | sh -s -- --url https://aw.example.com
# 覆盖安装：已加入过的机器不需要 token（--mode upgrade 可显式指定，auto 为默认）
curl -fsSL https://aw.example.com/artifacts/install.sh | sh -s -- --url https://aw.example.com --mode upgrade
# 一次性 enroll token 由安装脚本交互式隐藏输入；Agent 代跑时从 stdin 或
# AW_ENROLL_TOKEN 环境变量传入，不把令牌写在命令行中
```

**取件口（2026-11-06 修订）**：`/artifacts/install.sh` 由控制台直接下发仓库内的 `scripts/install-aw-node.sh`（匿名可读，只下发脚本本身）；aw-node 二进制与 `checksums.txt` **控制台先取、GitHub Release 兜底**。控制台可在 `workspace/artifacts` 镜像一份执行面产物并按 `/artifacts/:name` 匿名直读（文件名白名单，不做目录浏览），安装脚本默认 `--source auto`：先取控制台镜像，取不到再回退 GitHub Release（`collector-v*` tag 发布同名产物）；`--source console|github` 可强制单一来源。**产物与校验和必须同源同批**：控制台镜像的 `checksums.txt` 与二进制由 `scripts/publish-aw-node-artifacts.sh` 一次生成，脚本按同源下载后自校验 SHA-256 再落盘安装，混源比对会拿两次构建的摘要互校。

修订原因（实测）：执行机所在网络可能到不了 GitHub，实测本机网络即 `curl github.com` 不可达，GitHub Release 取件在新机器上直接失败。控制台是执行机必然可达的一侧（安装脚本本来就从它取），把产物镜像一份即可让新机器只从控制台取件；GitHub Release 保留为发布渠道与兜底，不改架构分层。

**站点给出可复制的下载地址（2026-11-06）**：控制台 `/setup` 第 2 步与总览页「添加执行机」折叠区展示同一份接入面板——一键安装命令、一次性 enroll token（单独展示，不进命令行）、分平台产物直链与大小/sha256，每项都可一键复制；产物清单由匿名接口 `GET /api/bootstrap/artifacts` 提供（只含公开文件名、大小、校验和与对外地址 `AW_PUBLIC_URL`，不含凭据），产物缺失时面板提示回退 GitHub Release。

**首次加入自动化**：用户在控制台选择「添加执行机」后，控制台签发一次性、短有效期的 enroll token，并在 `/setup` 单独展示（不进安装命令行，不进 shell history）。安装脚本按提示隐藏读取令牌，换取机器 ID 与长期采集密钥，识别主机与系统、安装唯一 aw-node、写入 launchd 并启动自检；用户不需要先手工登记 collector_id、主机名、OS、项目名或编辑 plist。令牌只能使用一次，过期或重放均拒绝，控制台与安装日志不得记录令牌或长期密钥。

**机器登记界面入口下线（2026-11-06 裁决）**：`POST /api/machines` 与 `POST /api/aw-node/enroll` 签发的是同一份采集器凭据（同一个 `machine.collector_secret_hash` 列），手工登记是 enroll 流程的前身——主流水线（`/setup`、接入向导、`scripts/install-aw-node.sh`）都不调用它。保留手工登记只有风险没有收益：手工登记行可能被 §「重新 enroll 的身份复用」判定复用并轮换掉刚展示的明文密钥，或因 hostname/os 不一致产生重复机器行。因此**总览页下线「机器登记」按钮，注册 Agent 弹窗的空机器提示改指「接入执行机」向导，API 保留**供 e2e / 运维兜底。

**重新 enroll 的身份复用（2026-11-06 裁决）**：重装、密钥丢失或安装脚本重跑都会再走一次 enroll，若每次都新建机器行，同一台机会在库里堆出多行（实测 MacBook 重复 enroll 后出现 3 行，控制台清单因此出现幽灵机器），且旧行上的 Agent 绑定会与新行脱钩。控制面因此按「同主机名 + 同系统 + 已无存活上报（`last_seen_at` 为空或超过心跳超时 5 分钟）」判定复用候选：命中则**沿用原机器 ID 并轮换密钥**（旧密钥立即失效），采集器版本同步刷新，Agent 绑定与机器身份一起保留；未命中才新建机器行。仍在正常心跳的机器不会被复用，避免同名不同机互相顶掉身份。

**覆盖安装（2026-11-06 裁决）**：升级与重装**不需要一次性 enroll token**。机器身份已落在 `~/.aw-node/credentials.json`（`0600`），`aw-node install` 直接复用它重装 launchd 服务，既不重新登记机器，也不新建机器行、不断开 Agent 绑定。安装脚本据此给出一条命令覆盖安装的路径：`--mode auto`（默认）按凭据文件是否存在判定走覆盖安装还是首次加入，`--mode upgrade` / `--mode enroll` 可强制。首次加入才需要一次性 token。

```bash
# 覆盖安装（已加入过的机器）：不换机器身份、不需要 token
curl -fsSL https://aw.example.com/artifacts/install.sh | sh -s -- --url https://aw.example.com --mode upgrade
```

**覆盖安装的三条不变量**：

- **保留既有环境变量**：重装要读回既有 plist 的 `EnvironmentVariables` 并原样带过去，用户自己加的 `GH_TOKEN`、`AW_EXTRA_PROJECTS` 等不能被 install 自己掌控的键覆盖掉；install 掌控的键（`AW_INGEST_URL` / `AW_COLLECTOR_ID` / `AW_COLLECTOR_SECRET` / `AW_STATE_DIR`）由本次参数决定，未显式传入的项目列表与 backfill 开关沿用既有值。
- **先删后拷替换二进制**：直接覆盖已签名的二进制会留下失效签名，launchd 拉起时进程被 SIGKILL（exit 137），表现为「刚装上就消失」。必须先 unlink 再拷贝。
- **装载前摘干净同名服务**：launchd 的拆除是异步的，`bootout` 返回后服务仍在域里收尾，立刻同名 bootstrap 必然撞 `5: Input/output error`；必须轮询到它真正从域里消失再装载（见下条 launchd 装载语义）。

**诊断命令的配置来源（2026-11-06 修订）**：`status` / `doctor` 要看的是「已安装服务在用的那套配置」，不是终端进程 env 的缺省值。终端里跑 doctor 时进程 env 通常是空的，`AW_INGEST_URL` 会缺省回退到 `127.0.0.1:8787`，于是自检去检查一台根本没装控制台的机器——安装脚本末尾的自检正是这样假失败的。因此诊断命令先回退到 launchd plist 的 `EnvironmentVariables`，进程 env 仍然优先；安装脚本额外显式传 `AW_INGEST_URL`，使自检指向本次安装的地址。注意 Bun 运行时自动加载**当前工作目录**下的 `.env` 且不覆盖已存在的环境变量：在带 `.env` 的仓库目录里跑 doctor，`.env` 的 `AW_INGEST_URL` 会盖过 plist 值——这是刻意的优先级（显式环境 > 本地 .env > 已安装配置），不是缺陷。

**自动发现与配置下发**：aw-node 在本机读取 cc-connect 的项目、目录、Agent 和渠道元数据，通过机器 Bearer 上报控制台；控制台不直接读取执行机文件系统。用户在 `/setup` 确认项目与主责 Agent 后，控制台先创建身份与非敏感配置，aw-node 再调用 `POST /api/aw-node/config`。**ACK 前每次配置请求都轮换并返回最新 secret 和 config_version，旧 secret 立即失效，支持响应丢失后的安全重试；ACK 后不再返回明文。** aw-node 以备份 + 原子写入应用最新配置并回传版本与生效状态，Agent Bearer 只写入目标机 `0600` 配置，不写 aw-node plist、日志或代理链路；用户无需执行第二次安装命令。

**飞书 bot 名解析与缓存（2026-11-05 裁决）**：发现扫描用 cc-connect 项目本地的 `app_id` / `app_secret` 换 `tenant_access_token` 再取 `bot/v3/info`，把非敏感的 `feishu_bot_name` / `feishu_bot_open_id` 随发现上报写入 Agent 身份。凭证不出机器：secret 只在内存参与换取 token，不进上报、日志或落盘。bot 名变更稀少（数月一次），故 token 按应用缓存约 90 分钟、bot 身份按项目缓存 7 天；现取失败时沿用上一次成功值而非闪回项目名（发现去重哈希不因取名失败而抖动）。控制台总览页提供「刷新 bot 名」手动入口：记 `machine.bot_refresh_requested_at`，aw-node 在 config 拉取（≤60s）时收到 `refresh_bot_names` 标记即作废身份缓存并立即重取重报，标记消费即完成，命令丢失由用户重点补发。

- **包内容**：GitHub Release 发布 `aw-node-macos-arm64` / `aw-node-macos-x64` 与 `checksums.txt`，控制台下发 `install.sh`（安装脚本本身）并可镜像同名产物；不含 MCP proxy、第三方 MCP 适配器或独立调度服务。
- **安装结果**：一个 `com.agent-workbench.aw-node` LaunchAgent，持有采集与调度共用配置；同机第二个实例必须由锁拒绝，避免重复采集和重复唤醒。
- **Agent 控制工具**：控制台生成 Claude Code / WorkBuddy 的远程 MCP 配置，aw-node 自动下载并写入受管运行时配置，Agent 再直连控制台 `https://aw.example.com/mcp`；不写 aw-node plist，也不由 aw-node 代理。
- **WorkBuddy**：使用官方 automations 轮询自己的 Assignment/Input，不增加本地服务，不逆向其内部 API。
- **升级**：替换产物后 `launchctl kickstart -k`，断点与 spool 保持不动；重复执行安装等价于升级。覆盖安装不需要一次性 enroll token，也不换机器身份（见下条覆盖安装裁决）。
- **密钥**：机器采集密钥与 Agent Bearer 分属两套配置，均不进入日志或命令行历史。

launchd plist 要点：

```
Label            com.agent-workbench.aw-node
ProgramArguments [<aw-node-path>, run]
RunAtLoad        true
KeepAlive        true
StandardOutPath  ~/.aw-node/aw-node.log
StandardErrorPath ~/.aw-node/aw-node.err
EnvironmentVariables  AW_INGEST_URL / AW_COLLECTOR_ID / AW_COLLECTOR_SECRET / AW_AGENT_PROJECTS
```

**launchd 装载语义（2026-11-06 修订）**：装载不只认 `gui/<uid>` 一个域。`launchctl` 对「域不可达」「同名服务已占用」「同名服务正在拆除」三种情况一律回 `5: Input/output error`，无法据此区分原因，因此 `aw-node install` 按 `gui/<uid>` → `user/<uid>` 顺序逐域尝试：先探测域是否可达（不可达就跳过，`user/<uid>` 覆盖无图形登录会话的机器），同名服务还挂着时先 `bootout` 并**等它真正从域里消失**（launchd 的拆除是异步的，bootout 返回后立刻同名 bootstrap 必然撞 EIO），随后带重试地装载；装载前校验二进制可执行与 plist（`plutil -lint`）。全域失败时错误信息给出可用域、校验结果与逐条手动重试命令，不再只回 launchctl 原文。凭据在装载前已落盘，装载失败可直接重跑 `aw-node install`，不必重新签发 enroll token。

**新增一台机的上线清单**（顺序不可跳）：

1. 用户在控制台选择「添加执行机」，获得一次性 enroll token（单独展示，不进命令行）；系统不要求先填写机器信息。
2. 在目标机执行一次安装命令，安装脚本按提示隐藏读取令牌，自动完成令牌兑换、机器登记、aw-node 安装、launchd 写入和自检，控制台显示机器上线。
3. aw-node 在本机读取 cc-connect 并上报项目、目录、Agent 与渠道元数据，控制台据此预填；用户只确认主责 Agent。发现不了时才填写项目名、仓库地址和工作目录。发现扫描的候选配置路径：显式指定（`AW_CC_CONNECT_CONFIG`）优先，**未设置或空列表一律回退默认候选路径**（`~/.cc-connect/config.toml` 与 `/opt/homebrew/etc/cc-connect/config.toml`）——`loadConfig` 对未设置的环境变量给出空数组,回退判定必须把空数组与未指定同义处理（2026-11-05 修复:曾因只判 `undefined` 导致扫描恒空、上报恒 422）。
4. 系统创建各 Agent 的稳定 `key`、默认项目角色与**不含明文 Bearer**的待下发远程 `/mcp` 配置；aw-node 在 `POST /api/aw-node/config` 中取得最新 secret 后自动写入配置并回传版本与生效状态，再验证 A 的 Bearer 不能读取或操作 B 的任务、信箱或 WorkItem。
5. 需要 WorkBuddy 时配置官方 automations；其 Run/对话/Token 在控制台显示「未接入 / —」，不以缺数据阻断初始化、A2A 或 Assignment。
6. 观察 10 分钟：心跳连续、`pending_bytes` 回落、无重复采集、无重复唤醒、无 `last_error`，才算上线。

## 9. 与 M3.8 验收的对应

| 交付标准 | aw-node 支撑点 |
|----------|--------------|
| 首屏 3 秒答出谁在跑 | 采集模块心跳 + 运行事件实时推送 |
| 任一任务能回答卡在哪 | 事件按 `seq` 有序、不丢块 |
| 两台机数据正确归因 | 每机独立 `collector_id` 与单实例锁，断点互不干扰；WorkBuddy 三项空态除外 |
| 离线消息不重复执行 | `(collector_id, stream_id, seq)` 与 worker_inbox 幂等 |
