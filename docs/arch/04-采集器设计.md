# 采集器设计

> 创建日期: 2026-10-29
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。入库结构见 [02-数据服务设计.md](./02-数据服务设计.md)。

## 1. 定位

每台运行 Agent 的机器部署一个采集器，贴近数据源做增量读取，把事件推到控制面。控制面不直接访问其他机器的文件系统。

| 项 | 约定 |
|----|------|
| 形态 | 独立 Node 进程，与主仓库共享 `src/shared` 类型，独立构建产物 |
| 驻留 | launchd（`KeepAlive=true`），开机自启，崩溃自动拉起 |
| 方向 | 只推不拉；控制面不反向访问机器 |
| 状态 | 断点、缓冲都落在本机 `workspace/collector/`，不依赖内存 |

**为什么不做中心化轮询**：控制面若直接读远端文件，需要开放 SSH 或共享目录，权限面远大于「单向 HTTPS 推送」。

采集器只是**本地执行面**的一部分（见 [00](./00-总体架构设计.md) §2.1）：同一台机上还有 MCP proxy 与 Claude Code 配置托管。它们由同一个本地组件安装与托管，但职责分开——采集器只读取与上报，不做判定，也不修改 Agent 行为。

## 2. 采集对象

| 来源 | 内容 | 增量依据 |
|------|------|----------|
| Claude Code 会话文件 | 每轮对话、工具调用、token 用量 | 文件追加写入，按字节偏移读 |
| cc-connect 运行日志 | 消息收发、投递结果、异常 | 同上 |
| 本机进程与系统指标 | CPU、内存、Agent 进程存活 | 周期快照，不做增量 |

采集器**只读**，不修改被采集文件，也不向 Agent 注入任何内容。

CPU / 内存**只随心跳上报，不入库、不建表**：它们服务于「这台机是不是快撑爆了」的即时判断，不是分析数据。若将来需要趋势，再单独加 `metric_snapshot` 并另定保留策略，不在这版预埋。

## 3. 断点续读

断点三元组：`(path, inode, offset)`。

```
读取前                       读取后
┌──────────────┐            ┌──────────────┐
│ inode = 1234 │            │ inode = 1234 │
│ offset = 8192│ ──读取──▶  │ offset = 9216│
└──────────────┘            └──────────────┘
        │
        └─ 若当前 inode ≠ 记录 inode ──▶ 判定文件轮转，offset 归零
```

| 情况 | 处理 |
|------|------|
| 文件变短（`size < offset`） | 判定截断或轮转，offset 归零重读 |
| inode 变化 | 判定轮转，offset 归零重读；旧 inode 的残留缓冲照常投递 |
| 读到半行 | 不提交该行，offset 停在行首，下次续读 |
| 文件暂不存在 | 记录状态，等待下次轮询，不报错退出 |

**提交纪律**：只有在控制面 ACK 后才推进 offset。宁可重复投递，不可丢事件；重复由控制面幂等吸收。

## 4. 推送协议

`POST /api/ingest`，`Content-Type: application/json`，`Authorization: Bearer <machine_id>.<secret>`（口径见 [01](./01-后端服务设计.md) §3.1）。

```json
{
  "collector_id": "macmini-01",
  "agent_project": "lokta-acore-manager",
  "stream_id": "claude-session:b20e60f5",
  "batch": [
    {
      "seq": 10241,
      "inode": 1234,
      "offset": 9216,
      "kind": "turn",
      "occurred_at": 1761800000000,
      "payload": { "...": "原始事件" }
    }
  ],
  "sent_at": 1761800000500
}
```

| 字段 | 作用 |
|------|------|
| `collector_id` | 采集器身份，控制台据此区分机器 |
| `agent_project` | 本流所属 Agent 的 cc-connect 项目名；控制台按 `(collector_id, agent_project)` 解析到 `agent.id`（`collector_id` 即 `machine.id`，等价于 `(machine_id, agent.project)`） |
| `stream_id` | 逻辑流（一个会话文件一条流） |
| `seq` | 本流内单调递增；去重键是 `(collector_id, stream_id, seq)`，不能只用 `(stream_id, seq)` |
| `inode` + `offset` | 控制台回存为 ACK 断点，用于核对 |
| `kind` | 事件类型，控制台按此路由到不同解析器 |

**响应**：`200 { "acked_seq": 10241 }`。控制台处理到哪条就 ACK 到哪条，允许部分成功。
**鉴权**：`Authorization: Bearer <machine_id>.<secret>`。控制台按 `machine_id` 取 `collector_secret_hash` 做常量时间比对；不匹配一律 401 且**整批拒收**，不部分入库。请求体不做签名——重放由 `(collector_id, stream_id, seq)` 幂等吸收（见 §5）。

**会话归因（唯一口径）**：采集器读 `~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl`，拿 `session-uuid` 反查 `~/.cc-connect/sessions/*.json` 的 `agent_session_id` 或 `past_agent_session_ids`（同一份档案的两个字段，会话轮换后旧 id 仍在档），得出 cc-connect 项目名填入 `agent_project`。join 的键是 UUID 不是路径——`/dir` 换 cwd 不影响归因。

| 档 | 条件 | 动作 |
|----|------|------|
| 1 | 当前或历史 session id 命中，且只命中一个项目 | 正常推送 |
| 2 | 未命中，或命中多个项目 | 该流**不推送**，留在 spool；心跳计 `unattributed_streams` |

**不存在第二通道**：采集器是独立进程，读不到 Agent 进程的环境变量，「启动器注入 `AW_AGENT_ID` 让采集器读」不成立；按目录名反推又会被 `/dir` 打散。归因只有这一条路，对不上就如实记成未归因，不许猜。

以下两条是实测事实，不是异常分支：

- `~/.cc-connect/sessions/*.json` 只是**指针与回放副本**（`agent_session_id` + 少量 history），不含 token usage 与工具调用；成本与产出必须从 `~/.claude` 的 jsonl 读。
- 本机实测 58 个 Claude 会话里 38 个能命中指针、20 个不能（终端直跑或历史已清理）；能命中的 38 个里，27 个只在 `past_agent_session_ids` 出现——只认当前 id 会漏掉大半。另有 28 个指针指向的文件已不存在。所以第 2 档是常态之一，控制台收到解析不了的 `agent_project` 必须整批 400，不静默归属。

## 5. 缓冲与重试

```
采集 ──▶ 内存队列 ──▶ 本地 spool 文件 ──▶ 推送
                          ▲                  │
                          └──── 失败回写 ────┘
```

| 项 | 约定 |
|----|------|
| 先落盘再推送 | 事件先写 spool，推送成功后再标记已确认 |
| spool 格式 | 按行 JSONL，文件按日期滚动，单文件上限 32MB |
| 重试 | 指数退避 1s → 2s → 4s … 上限 60s，带 ±20% 抖动 |
| 上限 | spool 总量上限 512MB；超过后丢弃最旧的、未确认事件并告警——宁可丢旧数据，不可写满磁盘 |
| 幂等 | 重试携带同一 `seq`；控制台按 `(collector_id, stream_id, seq)` 去重，重复不重复入库。去重窗口 7 天，过期后可重放——超出窗口还迟到的事件按新事件处理 |
| 顺序 | 单流内严格顺序投递；多流之间并行 |

## 6. 心跳与健康

- 每 60s 发送一次心跳：`{ collector_id, uptime, pending_bytes, unattributed_streams, cpu, mem, last_error, streams: [...] }`。`unattributed_streams` 是 §4 归因第 2 档滞留的流数，非零即说明有 Agent 的 `project` 没登记或写错。
- 控制面按 `collector_id` 更新 **`machine.last_seen_at`**（不是 `agent_run.last_seen_at`——机器活着不等于 Agent 在跑）；超过 5 分钟未更新标记「心跳超时」，超过 30 分钟标记「离线」。
- 采集器自身不判断 Agent 状态，只上报事实；状态判定在控制面。

## 7. 安全

| 面 | 措施 |
|----|------|
| 传输 | 经 frp 的 HTTPS；不接受明文 HTTP |
| 鉴权 | Bearer 采集器密钥；控制台侧只存 `collector_secret_hash` |
| 最小权限 | 只读被采集目录；不监听端口；不执行外部命令 |
| 密钥 | 由控制台 `POST /api/machines` 签发，明文只在下发时出现一次，随后仅存在于采集器侧 env / launchd plist；控制台库只存哈希。不进日志；启动时校验存在，缺失即拒绝启动 |
| 日志 | 记事件与计数，不记消息正文与凭证 |

## 8. 部署

采集器由本地执行面组件统一安装与托管（写 plist、bootstrap、升级、配置漂移检测）；下面的 plist 内容用于验收对照与故障排查。

launchd plist 要点：

```
Label            com.example.agent-workbench.collector
ProgramArguments [node, <repo>/collector/dist/main.js]
RunAtLoad        true
KeepAlive        true
StandardOutPath  workspace/collector/collector.log
StandardErrorPath workspace/collector/collector.err
EnvironmentVariables  AW_INGEST_URL / AW_COLLECTOR_ID / AW_COLLECTOR_SECRET
```

- 首次部署：写入 plist → `launchctl bootstrap gui/$UID` → 验证 `/healthz` 与控制面收到心跳。
- 升级：替换产物后 `launchctl kickstart -k`，断点与 spool 保持不动。
- 只在一台机上验证通过后再铺第二台。

**新增一台机的上线清单**（顺序不可跳）：

1. **按该机实际 Agent 数逐个注册**（`POST /api/agents`，一台机上有几个 Agent 就注册几次），每个 Agent 的一次性 `secret` 写入**它自己的运行环境**，不进 plist——plist 只放采集器的 `AW_COLLECTOR_*`，两套密钥互不通用。照旧只注册一个，其余 Agent 调用 MCP 工具会全部 401。注册时必须填 `project`（cc-connect 项目名，同机唯一）与 `feishu_app_id`（可空）；`project` 漏填或与 cc-connect 里的名字不一致，该 Agent 的会话会全部落到归因第 2 档，总览里看不到它。
2. 在 `machine` 登记 `collector_id` 与密钥哈希，并**人工确认项目归属**——自动登记容易把开发机认成生产机。
3. 写 plist，`AW_INGEST_URL` 指向 `https://aw.example.com/api/ingest`，密钥只走 `EnvironmentVariables`。
4. `launchctl bootstrap gui/$UID`，验证 `/healthz` 可用且总览出现该机。
5. 观察 10 分钟：心跳连续、`pending_bytes` 回落、无 `last_error`，才算上线。

## 9. 与 M3 验收的对应

| 交付标准 | 采集器支撑点 |
|----------|--------------|
| 首屏 3 秒答出谁在跑 | 心跳 + 运行事件实时推送 |
| 任一任务能回答卡在哪 | 事件按 `seq` 有序、不丢块 |
| 两台机会话数据齐全 | 每机独立 `collector_id`，断点互不干扰 |
| 离线消息不重复执行 | `(collector_id, stream_id, seq)` 幂等 |
