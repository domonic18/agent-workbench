# 数据服务设计

> 创建日期: 2026-10-29
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。本册定义存储形态、表结构与一致性纪律。

## 1. 存储架构全景

```
PostgreSQL — 同机 Docker Compose，仅内部网络
  身份域   agent · machine
  业务域   work_item · work_item_event · task · task_event · agent_run · timeline_event
  协调域   work_trigger · work_thread · thread_subscription · worker_inbox
  A2A 域   a2a_thread · a2a_message · outbox · a2a_dead_letter
  授权域   capability · capability_audit · tool_call_log
  知识域   knowledge_entry · knowledge_chunk · knowledge_vec
  token 域 token_usage · usage_limit
  系统域   schema_migration · ingest_receipt · session · console_credential · login_failure · idempotency_record · scope_revision
  检索     pg_trgm（关键词/模糊）· pgvector（语义）
       │
       ▼
workspace/ 文件
  postgres/    PostgreSQL 持久卷（不映射宿主机端口）
  console.lock 单实例锁
  knowledge/   全新 Markdown 目录（文本真相源，可进 Git、可直接编辑）
  backups/     pg_dump 一致性备份
  collector/   aw-node 采集断点与 spool（各机本地，不入库）
```

**单一事实源**：业务状态一律在 PostgreSQL；Markdown 知识正文是唯一例外——文本真相源在文件，元数据与索引是派生。两者都不使用黑板，不做投影。M3.8 从空数据库与空知识目录开始，旧 SQLite 和旧知识文件只移到运行路径之外归档，不扫描、不导入、不双写。

## 2. 命名与类型约定

| 项 | 约定 |
|----|------|
| 表名 | 小写下划线、单数（`task` 而非 `tasks`） |
| 主键 | `id TEXT PRIMARY KEY`，前缀 ULID：`agt_` / `mac_` / `wrk_` / `wie_` / `wtr_` / `wth_` / `sub_` / `wib_` / `tsk_` / `run_` / `msg_` / `thr_` / `cap_` / `kb_` |
| 时间 | `*_at BIGINT`，Unix 毫秒 UTC；禁止本地时区（保持现有 API 数值契约） |
| 数量 | `*_tokens BIGINT`，非负整数；**禁止浮点** |
| 采集计数 | 采集器 `seq` / `offset` 按文件字节偏移编码（×100），会话日志超 ~21.5MB 即越过 int4；承载它们的列一律 `BIGINT`（0008 裁决，2026-11-05 真实链路触发；服务端自生成的 `task_event.seq` / `work_item_event.seq` 仍为 `INTEGER`） |
| 枚举 | `TEXT` + `CHECK` 约束，枚举值集中定义在 `shared/constants` |
| 布尔 | `BOOLEAN`，不再使用 INTEGER 0/1 |
| JSON | `JSONB`；外部输入先经 zod 校验，查询使用 PostgreSQL `->` / `->>`，不使用 `json_extract` |
| 软删除 | 仅知识条目使用 `deleted_at`；业务记录不做软删除 |

**ID 不用自增整数**：ULID 可按时间排序，且跨采集器、跨机器生成不会冲突。

## 3. 核心表清单

### 3.1 任务域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `task` | `id, work_item_id NULL, title, assigner, assignee, project, parent_task_id NULL, round, rework_count, stage, status, origin, deadline_at, output, started_at, ended_at, total_tokens` | 一行一任务；`work_item_id` 关联业务事项；`stage` 是当前环节，`status` 是生命周期；`parent_task_id` 是任务链路上游；`total_tokens` 是归属到该任务的 token 合计（投影，可重算） |
| `task_event` | `id, task_id, seq, kind, payload_json, occurred_at` | 任务时间线；`seq` 在任务内单调 |

`task.status` 枚举：`pending` / `running` / `blocked` / `review` / `done` / `cancelled`。
`task.stage` 枚举：`intake`（接单）/ `plan`（方案）/ `exec`（执行）/ `review`（评审）/ `deliver`（交付）/ `closed`（归档）。
`task.origin` 枚举：`feishu` / `a2a` / `work_item`。`work_item` 表示由已归属业务事项承接而来；**没有 `console`**——控制台不手动建单，确定性 Router 也不代替 Agent 建单。
`task_event.kind` 枚举：`created` / `stage_changed` / `handoff` / `blocked` / `resumed` / `rework` / `completed` / `failed`。

**业务项目口径**（2026-10-31 裁，对应需求 §9-12 #6）：`task.project` 只能取 `src/config` 里业务项目清单的值，`task_create` 填清单外的值返回 422，不做「先存后归并」——一旦允许自由文本，同项目的不同写法会立刻把按项目统计打散。清单随仓库版本化，增删走一次提交。

**产出物口径**（2026-10-31 裁，对应需求 §9-12 #2）：`task.output` 只接受两种形态——知识条目标识 `kb_<ULID>`，或 `http(s)://` 开头的 URL。本地路径、空串、其它 scheme 一律 422。理由：路径只在本机有意义，人和下游 Agent 都拿不到；知识条目与 URL 都能被人点开、被下游引用。

**建单与归属**（2026-10-30 口径，对应需求 §1.2）：

- 任务由**执行方 Agent** 创建，`assignee` 恒为自己，**创建后不可变**；禁止代建他人任务。
- `work_item_id` 在创建时可关联一个已存在且项目一致的工作事项，创建后不可改；未纳入事项体系的既有 Task 允许为 `NULL`，不得为补全视图伪造事项。
- `origin` 是**直接入口**（活从哪来），不是记录方：人经飞书下的活为 `feishu`，经 A2A 接的活为 `a2a`，由工作事项协调而来为 `work_item`；原始外部来源仍由工作事项与 Trigger 保存。
- `assigner` 在 `origin=feishu` 时是人的 `open_id`，由 Agent 自报，可信度低于宿主注入的 `from`；`task_event(created).payload` 记 `reported_by`（Agent id），供 M4 区分「人派活」与「Agent 自报」。
- 跨 Agent 交接**不转移归属**：接收方另建自己的任务，只把新任务指向上游，绝不改上游的 `assignee`。
- `agent_run.task_id` **可空**：单人私聊的活通常只有 run 没有 task（需求 §1.2-A），总览必须能展示这类 run，不得因缺 `task_id` 丢弃。

**链路（`parent_task_id`）**：可空、**创建后不可变**。只有两种来源，靠 `handoff` 事件里的 `relation` 区分：

| relation | 何时产生 | 谁来连 |
|----------|----------|--------|
| `a2a` | 接收方 ACK 一条 `request` / `escalate` | 服务端在同一事务里自动连，不靠 Agent 自报 |
| `continuation` | 同一 Agent 收下上游产出、另起一条任务继续（B 拿到 A 的文档后再找 C） | `task_create` 显式带 `parent_task_id` |

服务端校验：父任务存在、不能是自己、调用方是父任务的 `assignee`、不构成环。两种来源都写 `task_event(kind='handoff', payload={relation, from_task_id, msg_id?, thread_id?})`，事件落在**下游**任务上。

**上溯即链**：沿 `parent_task_id` 逐级上行就是整条链，不设长度上限，端点直到底（`parent_task_id IS NULL`）。链头可能是 run 而非任务（A 在私聊里直接实现、没有建单），此时**如实止步，不补建任务**——补出来的节点没有 run、没有 token 消耗，是假数据。

**返工可追溯**：`status` 从 `review` 退回 `running` 时 `rework_count += 1` 并写一条 `rework` 事件（带 `reason` 与 `round`）。

**任务一次交付通过率**（需求 §9-12 #5）：`status=done` 且 `rework_count=0` 的任务数 ÷ 全部 `status=done` 的任务数，不含 `cancelled`。这就是原「一发通过率」的「一轮就交付被接受」，与建单通道无关；`round` 是 A2A 往返轮次，不参与该口径，不得用 `round=1` 代替。

`task.round` 是**投影**，不是独立真相：一条任务可能同时开着多条线程（发给不同 Agent），因此取该任务所有线程 `round` 的最大值，无 A2A 时为 0。`round`（A2A 往返轮次）与 `rework_count`（被打回次数）含义不同，不得互相替代。

### 3.2 运行域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `agent_run` | `id, agent_id, machine, project, task_id, work_item_id NULL, status, started_at, last_seen_at, ended_at` | 一次 Agent 执行；可经 Task 或在无 Task 时显式关联工作事项 |
| `timeline_event` | `id, run_id, turn_id, block_id, ord, block_rev, offset, kind, payload_json` | 运行事件流，支撑总览与下钻 |

`timeline_event` 的四维坐标（借鉴版本化时间线思想，独立实现）：

| 字段 | 语义 | 不变量 |
|------|------|--------|
| `block_id` | 块身份，创建时分配 | 重放与实时使用同一 id |
| `ord` | 块内全局顺序 | 在同 `turn_id` 内唯一且递增 |
| `block_rev` | 该块的新鲜度 | 旧 `block_rev` 不得覆盖新内容 |
| `offset` | 增量文本位置 | 为 `NULL` 表示整块快照 |

**事项关联**：`agent_run.work_item_id` 只由可信的任务关联或明确的路由/运行绑定产生，不从目录或消息文本猜测。若同时存在 `task_id` 与 `work_item_id`，二者的事项归属必须一致；不一致即拒绝绑定并告警。无 Task 的日常 Run 仍允许两项均为空。

**run 边界**（2026-10-31 裁，对应需求 §9-12 #3）：一段 run = Agent 进程的一次生命周期。进程启动开新 run；同一进程内相邻事件间隔 **≥ 30 分钟**时切分新 run（旧 run 置 `ended_at`，新 run 顶替）。30 分钟是硬阈值，不做自适应——总览要的是「现在谁在跑」，口径必须可复现。进程退出即结束 run。

判定在控制面，不在 aw-node：采集模块只上报 `(stream_id, seq, occurred_at, kind)`，控制面按 `agent_id` 维护「当前 run」并决定是否新开。同一 Agent 多进程并存时，各进程各成一段 run，不合并。

写入纪律：客户端缺失块只能由「快照重取」修复，不做内容拼接猜测。

> 命名纪律：`block_rev` 是**块内**新鲜度，SSE 帧里的 `revision` 是**作用域级**投影版本（`overview` / `task:<id>`）。两者作用域不同，禁止互相赋值或比较；序列化时字段名必须区分。

### 3.3 A2A 域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `a2a_thread` | `id, initiator_task_id, initiator_agent, responder_agent, created_at` | 一问一答的容器；`UNIQUE(initiator_task_id, responder_agent)` |
| `a2a_message` | `id, thread_id, task_id, round, reply_to_msg_id NULL, from_agent, to_agent, intent, summary, expect, deadline_at, refs_json, auth_ticket, ack_at, created_at` | Agent 间往返消息，内容真相源 |
| `outbox` | `id, idempotency_key, channel, delivery_class, task_id NULL, msg_id NULL, kind, payload_hash, payload_json, status, attempts, lease_token, lease_until, available_at, last_error, created_at` | 对外投递状态机，只管运输 |
| `a2a_dead_letter` | `id, msg_id, from_agent, to_agent, task_id, reason, payload_json, created_at` | 过期未 ACK 的死信 |

**线程（`thread_id`）**：首条消息时服务端按 `(发起方任务, 收件方 Agent)` 建线程，同一组合后续消息复用它。`round` 由服务端在事务内取 `max(round)+1`，客户端自增的值一律忽略——重发、乱序、多端并发都会让客户端计数器漂移。
**线程状态不落库**，按消息与投递记录现算：存在未 ACK 的 `request` / `escalate` → `awaiting_reply`；最后一封是发起方已 ACK 的 `reply` → `completed`；超过 `deadline` 仍无回复 → `expired`；其余 `open`。这样只维护一份真相，不会出现「消息已完结、线程还挂着等待」。

`outbox.idempotency_key`：`TEXT NOT NULL UNIQUE`，由调用方生成——控制台内部投递（飞书卡片、每日汇总）用 `task_id:round:kind:payload_hash` / `daily:{date}:{kind}` / `cap:{cap_id}:{event}`；Agent 发起的 A2A 直接把客户端带来的 `Idempotency-Key` 原样入库（`round` 由服务端分配，客户端拼不出复合键）。两种都满足「由调用方生成」。不依赖数据库对 `NULL` 的唯一性语义，通知类消息也必须使用完整且非空的幂等键。

`outbox.channel`：`push`（飞书）/ `pull`（A2A 信箱），决定 `delivered` 的判据与是否会进入 `uncertain`。
`outbox.delivery_class`：`business`（失败围栏任务）/ `notification`（只重试，不围栏）。

**`a2a_message.task_id` 指发件方自己的任务**：同一线程里一问一答的两个 `task_id` 可以不同；两端任务的关联靠 `a2a_thread.initiator_task_id`（谁发起）与下游任务的 `parent_task_id`（谁交给谁），本表不引用收件方的任务 id，也不因对端建单而改写。

**内容与运输分离**：`a2a_message` 存业务内容与 `round`，`outbox` 只记录运输状态；重投复用同一行并累加 `attempts`，不新建记录。
索引：`INDEX(status, available_at)` 支撑扫描；`INDEX(msg_id)` 支撑 ACK 回写；`INDEX(thread_id, round)` 支撑线程展示。`task` 侧另加 `INDEX(parent_task_id)`，支撑上溯与「谁接手了我的任务」。

### 3.4 授权域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `capability` | `id, subject, target, action, scope_json, ttl_seconds, status, ticket_id, task_id, issued_at, expires_at, revoked_at, created_at, updated_at` | 一次授权申请与凭证 |
| `capability_audit` | `id, capability_id, action, actor, detail_json, occurred_at` | 全量审计，append-only |
| `tool_call_log` | `id, run_id, agent_id, task_id, tool, args_hash, level, verdict, reason, capability_id NULL, duration_ms, occurred_at` | 闸门判定审计，append-only；只存 `args_hash`，不存参数明文。`kb.search` 也记在这里（`tool='kb.search'`），是验收「知识第二次不重复解释」的观测点 |

`capability.status`：`pending` / `issuing` / `active` / `expired` / `revoked` / `rejected`。
`issuing` 是「已批准、正在调 Teleport 签发」的中间态。Teleport 是外部 HTTP，「改审批状态」与「签发凭证」**无法同事务**，只能用 saga：先置 `issuing` → 签发成功置 `active`；签发失败置 `rejected` 并告警。`issuing` 超过 60s 未落地，由后台作业按 `ticket_id` 对账收敛，绝不留在中间态。
凭证本身不落库明文；库里只存 `ticket_id` 与有效期，真实证书由 Teleport 持有。
`capability_audit` / `tool_call_log` 的 append-only 由 PostgreSQL 触发器兜底（`UPDATE` / `DELETE` 直接 `RAISE EXCEPTION`）：保留期清理若确需删数据（`tool_call_log` 180 天），必须新增迁移显式调整触发器并留评审记录，不允许运行期作业静默改写历史。`tool_call_log` 只覆盖控制台自有控制类 MCP，不代表第三方 MCP 或原生工具。

### 3.5 知识域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `knowledge_entry` | `id, path, title, summary, category, status, source_task_id, source_agent_id, content_hash, embedding_status, updated_at, deleted_at` | 元数据镜像；正文在 Markdown 文件 |
| `knowledge_chunk` | `id, entry_id, chunk_no, content` | 分块文本，可整库重建 |
| `knowledge_vec` | `chunk_id ↔ knowledge_chunk.id, embedding vector(768)` | pgvector 普通表；按实际查询规模建立合适向量索引 |

`knowledge_entry.status`：`draft` / `candidate` / `active` / `archived`。只有 `active` 参与检索；`candidate` 只能经 `kb_write` 工具（[01](./01-后端服务设计.md) §5.2）写入，其 `status` 由服务端强制为 `candidate`，必须经人在知识屏采纳（`POST /api/knowledge/:id/adopt`）才转 `active`，避免 Agent 自己教自己。
`source_task_id` / `source_agent_id` 记录来源；手工条目留空。

**向量使用 pgvector**：`knowledge_vec.chunk_id` 与 `knowledge_chunk.id` 对齐，`embedding` 使用 `vector(768)`，chunk 增删与向量替换在同一事务维护。关键词召回使用 `pg_trgm` 索引，不再建立 FTS5/vec0 虚拟表。
`embedding_status`：`pending` / `ready` / `failed`，供重建队列与知识屏徽标使用。

**真相源是文件**：`knowledge_entry` 只是便于查询与展示的镜像，删除索引不影响文件。重建时只扫描新 `workspace/knowledge/`，比对 `content_hash`，只重嵌入变化项；旧知识归档目录不在扫描范围内，也不做首次导入。

`index.md` / `log.md` 为受保护文件：控制台 API、Agent 写入工具、批量操作三条路径都拒绝改写。

**外部编辑的发现**：真相源是文件，就意味着有人会绕过控制台直接改文件。不使用 inotify（Docker 挂载与网络卷上不可靠），改为启动时全量比对 + 运行期每 5 分钟扫描目录，比对 `content_hash` 与 `mtime`；有变化即入重建队列，变化过的条目 `embedding_status` 先置 `pending`，避免检索命中旧内容。

### 3.6 token 域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `token_usage` | `id, agent_id, task_id NULL, run_id, provider, model, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, source, sequence, receipt_hash, occurred_at` | token 用量事实，append-only |
| `usage_limit` | `id, agent_id, daily_token_limit, warn_percent, hard_stop, is_active` | 按 Agent 的日用量上限；`agent_id` 唯一，改上限原地更新 |

`token_usage` 幂等：`UNIQUE(agent_id, run_id, source, sequence)`；同键不同 `receipt_hash` 视为冲突并报错，不静默覆盖。
`token_usage` 不存金额、不存价表版本：一期**不做计价**（2026-10-31 改判，需求 §9-6）。四种 token 维度分开存；`总 token = input + output + cache_read + cache_creation`，展示时可按维度拆开，不把合计写成唯一事实。
模型名按上报原文存（`glm-5.3-flash` / `deepseek-flash` / `kimi-for-coding` 都是网关别名），不做别名归一——没有价表，归一不带来收益，反而会丢掉网关侧的真实差异；`<synthetic>` 是内部记账伪模型，不写 `token_usage`。**WorkBuddy 首版没有 Run、对话或 Token 采集记录，相关字段保持 `NULL` / 界面显示「未接入」，不得写成 0 或用 Task 自报伪造。**

**不设预留**：token 只能从采集器事后得到，调用前无法准确预估；硬停以「当日已用 token 合计」为判据，接受采集延迟窗口内的少量超出。`usage_limit` 的语义只有两条：**未配置 = 不限**；配置了但读不出当日用量 = `deny`（fail-closed）。

**用量归属有意从简（2026-10-30 裁决）**：不设 Agent 主动报账通道，也不做逐环拆分。

- 写入方**只有一个**：token 事实只由 aw-node 采集模块上报产生，控制台落 `token_usage`；不设第二条报账通道，避免双写。
- 归属口径：**一个 run 至多归属一条任务**。`agent_run.task_id` 在 run 内首次 `task_create` 时由服务端回填，此后不覆盖；同一 run 里若又开了第二条任务，第二条不重复计 token（其产出仍可追溯）。`task.total_tokens` 是归属到该任务的 `token_usage` 之和，可重算，不单独累加。
- 归属不上的 run 保留 `task_id=NULL`，只计入 Agent / 项目维度——总览的语义是「这台机今天用了多少 token」，不是「这条任务精确用了多少」。链上每一环本就是独立任务、独立 run，因此 D1 要求的「独立 token 消耗」天然成立，不需要为它加机制。

### 3.7 身份域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `machine` | `id, hostname, os, collector_version, collector_secret_hash, last_seen_at, status, discovery_json, discovery_received_at, config_status` | aw-node 所在机器；`id` 即 `collector_id`；`discovery_json` 保存本机上报的 cc-connect 发现结果，`config_status` 表示配置待下发/已下发/已生效 |
| `agent` | `id, key, machine_id, project, display_name, runtime, secret_hash, feishu_app_id, status, allowed_targets_json, bootstrap_status, mcp_config_json, config_version, config_ack_at, created_at` | Agent 注册表；`key` 是 Git 项目注册表引用的稳定键，`secret_hash` 只存哈希；`mcp_config_json` 是待下发运行时配置，不存明文 Bearer；`runtime` 是运行时分类标签（`claude_code`/`workbuddy`/`codex`/`deepseek`） |

- `agent.machine_id` → `machine.id` 外键；Agent 与机器是多对一。**`machine_id` 可空**：为空 = 无 aw-node 的外部运行时（WorkBuddy/Codex/DeepSeek harness），直接拿 Agent Bearer 打 `/mcp`，控制台不采集其 run/对话/Token（见 [03](./03-前端设计.md) §4.0）；非空 = 采集器绑定的 `claude_code`，经 aw-node 调度。**行为判别只看 `machine_id` 是否为 NULL**，不按 `runtime` 分支。
- `agent.runtime` 是**允许列表式的分类标签**（CHECK 约束），不是行为开关；新增运行时 = 追加 CHECK 值 + 一处 `src/shared/constants.ts` 常量 + 一处前端标签，行为逻辑零分支。
- `allowed_targets_json` 是**委派白名单**，默认 `[]` = 不可向任何 Agent 发 A2A（default deny）。由控制台会话维护；Agent 自己的 Bearer 无权修改该字段，否则「谁能找谁」由被约束方自定，白名单形同虚设。
- **两套密钥不通用**：`agent.secret_hash` 供控制台 `/mcp`；`machine.collector_secret_hash` 供 aw-node 采集模块调用 `/api/ingest`。轮换互不影响；首版不引入 `run_token`。
- 普通注册/轮换时明文 `secret` 只在响应出现一次；bootstrap 项目确认只创建身份和非敏感配置，**秘密在 aw-node 的 `POST /api/aw-node/config` 中按配置请求轮换并返回最新值，旧值立即失效以支持重试，ACK 后不再返回明文**。所有路径随即只存 `secret_hash`，轮换即覆盖哈希，旧密钥立即失效，不设并行有效期。
- `agent.id` 由服务端生成（`agt_` + ULID），**与飞书的任何 ID 无关**；`agent.key` 是不可变的稳定键，供 Git 项目注册表将 `target_role` 解析到 Agent——机器无关 Agent（WorkBuddy / Codex 等）注册时由注册方显式给出，占用即 409；机器绑定 Agent 由初始化确认流程按项目名派生，不接受自报。飞书 `app_id` 只存为可换的渠道属性，不参与鉴权或路由。
- `(machine_id, project)` 唯一，注册时校验（机器无关 Agent 不参与该约束，只按 `id` 唯一）。`project` 存 **cc-connect 项目名**，是采集归因的落点（见 [04](./04-采集器设计.md) §4），只能取 `src/config` 里 cc-connect 项目清单的值，注册时从清单选、不自由输入；它与 `task.project`（业务项目）同名不同义——一个 Agent 会跨多个业务项目干活，`agent.project` 始终不变。
- **业务项目与角色也在 Git 项目注册表维护**：`project.primary_agent` 等角色指向 `agent.key`，RouteRule 只保存 `target_role`，启动时校验引用，派工时校验 Agent 已注册且启用；不另建数据库角色编辑器。
- 归因只认 ID 关系，不认目录：一条会话的 jsonl 目录在创建时固定，`/dir` 之后不会搬走；同一 Agent 的会话因此散落在多个目录里，按目录反推会把归属打散。
- 这是鉴权链起点：`capability.subject`、`agent_run.agent_id`、`token_usage.agent_id` 都必须能解析到 `agent.id`，未注册一律拒收。

### 3.8 系统域

| 表 | 关键列 | 说明 |
|----|--------|------|
| `schema_migration` | `version, name, applied_at, checksum` | 迁移台账 |
| `one_time_token` | `id, kind, token_hash, status, machine_id NULL, expires_at, consumed_at, created_at` | 一次性 bootstrap/enroll 令牌；`kind = bootstrap_admin / aw-node_enroll`，`status = active / consumed / expired`，库中只存哈希；enroll 兑换时绑定 machine_id |
| `ingest_receipt` | `collector_id, stream_id, seq, received_at` | 采集去重；`UNIQUE(collector_id, stream_id, seq)` |
| `feishu_event` | `event_id, event_type, received_at` | 飞书入站去重；`event_id` 主键，保留 7 天 |
| `feishu_command` | `event_id, open_id, chat_id, raw_text, command, outcome, reply_text, created_at` | 白名单指令审计；长期保留，用于回答「为什么回不支持」 |
| `session` | `id, created_at, last_seen_at, expires_at` | 登录会话 |
| `console_credential` | `id, password_hash, created_at, updated_at` | 控制台登录凭据，**单行**（`id = 1`）；只存 scrypt 哈希，不存明文 |
| `login_failure` | `source, failures, locked_until, updated_at` | 登录失败锁定；`source` 主键，达 5 次写 `locked_until`，锁过期或计数超窗口后读取时清行 |
| `idempotency_record` | `scope, key, resource_id, created_at` | 写接口幂等；`UNIQUE(scope, key)`，重放返回首次资源 id |
| `scope_revision` | `scope, revision, updated_at` | 投影版本水位；`scope` 主键（`overview` / `task:<id>` / `work_item:<id>`），每个投影表写入经触发器自增，读模型据此判断缺口 |

`scope_revision` 的递增放在**触发器**而非服务层：`revision` 是「投影表变了」的派生水位，任何写入路径（服务写、采集入库、修复脚本）都必须留下痕迹，服务层显式递增必然漏记。触发器只做 upsert，同一事务内多次变更也只在提交时可见，不会提前暴露中间版本。无投影变更的作用域不建行，读取时按 0 处理。

`console_credential` 不存在时，控制台进入 bootstrap mode，只开放 `/healthz`、`/setup` 与指定 bootstrap 接口。首次启动在本机输出一次性 `bootstrap_admin` token（`one_time_token` 只存哈希），用户在 `/setup` 输入 token 并设置管理员口令后，才写入 `console_credential` 并解锁完整控制台。`CONSOLE_INIT_PASSWORD` 仅作可选无人值守种子，不是启动前提；已存在凭据时直接进入登录模式。

`one_time_token` 的过期与消费必须在同一事务中处理：首次有效兑换将 `active` 改为 `consumed` 并绑定 machine_id，过期或重放不签发任何机器或运行时密钥。发现结果保存在 `machine.discovery_json`，待下发运行时配置保存在 `agent.mcp_config_json`；配置版本与 ACK 时间用于预检确认，不表示 WorkItem 或 Assignment 已创建。

`ingest_receipt` 与采集器共用同一去重键 `(collector_id, stream_id, seq)`，保留 7 天窗口而非「每流只留最后一条」——只留末条无法挡住乱序重放，而乱序是采集常态。

`feishu_event` 只登记白名单事件，用于短路飞书重推；非白名单消息回执「无权限」后**不落库**，不留正文与发送者记录。同样保留 7 天。

`feishu_command` 只记白名单用户的指令，与 `feishu_event` 分开：前者是长期审计（含原文与回执，原文截断到 4000 字符），后者是 7 天去重窗口，混放会让审计随去重清理一起消失。

### 3.9 工作协调域

工作协调域连接外部业务事实与既有 Task / Run，但不把二者合并成一张「大任务表」，也不复用 A2A 信封伪装系统派工。

| 表 | 关键列 | 说明 |
|----|--------|------|
| `work_item` | `id, parent_work_item_id NULL, project, kind, title, expected_result, scope_json, status, stage, attention, origin_trigger_id, authorization_kind, authorization_ref NULL, policy_version, next_action, latest_summary, last_progress_at, progress_revision, output, validation_json, acceptance_ref NULL, created_at, updated_at, ended_at` | 一件需要产生业务结果的事；`expected_result / scope_json / authorization_* / policy_version` 在创建时形成不可变 Mandate 快照 |
| `work_item_event` | `id, work_item_id, seq, kind, trigger_id NULL, evidence_refs_json, payload_json, occurred_at` | 事项永久时间线；记录路由、派工、退回、实质进展、待验收与人工接受 |
| `work_trigger` | `id, source, source_event_id, kind, actor_json, project NULL, thread_refs_json, payload_json, refs_json, authorization_ref NULL, disposition, reason_code, rule_id NULL, rule_version NULL, work_item_id NULL, target_agent_id NULL, occurred_at, received_at` | 已归一事实及其唯一确定性处置；`UNIQUE(source, source_event_id)` 幂等，不保存猜测性 project hint |
| `work_thread` | `id, source, external_kind, external_key, project, status, last_trigger_at, created_at` | Bug、PR、CI 流程或外部话题的稳定连续身份；`UNIQUE(source, external_kind, external_key)` |
| `thread_subscription` | `id, work_thread_id, work_item_id, task_id NULL, mode, created_by, policy_version, created_at, revoked_at` | 后续事件归属与上下文；`mode=owner/context`，撤销不删历史 |
| `worker_inbox` | `id, kind, work_item_id, trigger_id NULL, target_agent_id, task_id NULL, status, idempotency_key, lease_token, lease_until, payload_json, reason NULL, created_at, updated_at` | 控制面到 Worker 的 Assignment / Input；共享租约、重投与幂等，但不是 A2A 或 WorkItem 完成状态 |

**枚举与状态分离**：

- `work_item.status = open / done / cancelled`；`stage = intake / align / execute / review / verify / release`。`attention = none / person / blocked / acceptance / stalled`，回答当前是否需要人以及为何需要，不复制 Task 或 Run 的状态。
- `authorization_kind = none / explicit / confirmed / rule`。`none` 只能用于观察或待人确认；`explicit` 用于可信的人显式请求，`confirmed` 用于人对候选的确认，`rule` 用于书面项目规则允许的推进。`authorization_ref` 指向可审计依据，`none` 之外不得为空。
- `work_trigger.disposition = received / continued / routed / needs_person / ignored`；`reason_code` 记录 `no_project / no_route_rule / route_ambiguous / duplicate / owner_continued` 等确定性原因。`rule_id + rule_version` 只来自 Git 配置，一期没有 `route_evaluation` 或在线模型状态。
- `worker_inbox.kind = assignment / input`；运输状态为 `pending / claimed / acked / handed_back / failed`。Assignment ACK 必须携带承接 Agent 自己创建且关联同一 WorkItem 的 `task_id`；Input ACK 只表示消费，二者都不等于 WorkItem 完成。

**关系与不变量**：

1. 一个工作事项可有多个 Task、Run 和业务 Thread；一个 Task 至多属于一个工作事项。`parent_work_item_id` 只表达业务关系，不替代 Task 的 `parent_task_id`。
2. 工作事项可以在没有 Task 时处于需求澄清、等待或待验收；Run 也可以没有 Task。禁止为让关系整齐而补建空 Task 或假 Run。
3. 一个业务 Thread 至多一条 `revoked_at IS NULL AND mode='owner'` 的订阅，用 PostgreSQL 部分唯一索引保证；可有多个 context 订阅，但 context 不产生执行扇出。
4. 订阅只决定归属和首选续接 Task，不复制或扩大 Mandate。Worker 对超范围 Trigger 执行 Handback；确需换 owner 时，旧 owner 撤销、新 owner 建立、退回原因与事项事件在一个事务内完成，旧 owner 可保留 context。
5. `work_item.latest_summary` 是可重写的派生摘要，`validation_json` 只存验证摘要与引用；原始 Trigger、事项事件、正式文档、Task/Run 和外部产物才是事实依据。摘要不一致时可重建，不能反向覆盖原始记录。
6. **真实 Bug 的完成分两段**：关联可访问 PR 且当前 head SHA 的必需 CI 全部通过后，只进入 `attention=acceptance`；原 Bug 机器人提交结构化 `bug.accepted` 后才允许 `status=done`，并写 `acceptance_ref`。`bug.returned` 在同一 WorkItem 上记录理由、返回执行并生成 `kind=input` 的返工项，不新建重复事项。
7. A2A 回执 ACK、上游 Task 自动收口、PR 合并、CI 通过、Run 结束或 Agent 自报完成都不能单独使 WorkItem 完成。生产发布始终是独立人工动作。
8. `last_progress_at` 与 `progress_revision` 只在实质进展事件到达时更新；心跳、日志追加、重复通知和 token 增加不得推进它们。等待人、明确阻塞与异常停滞由不同 `attention` 值表达。

**上下文引用**：`refs_json` / `evidence_refs_json` 只存稳定 ID、来源、摘要和必要的读取定位，不把长文复制进每张表。读取方沿 `Trigger → Thread → 工作事项 → Task/Run → 原始依据` 逐跳召回，并重新执行对应访问控制。引用可访问性变化要如实显示，不能因摘要还在就声称原始证据仍可读取。

**事务边界**：Trigger 去重、Thread 建联、确定性路由、Mandate、`worker_inbox`、事项事件和外部副作用入队在应用服务的一个事务内写入；提交后才允许适配器执行。Assignment/Input ACK、Handback 与 owner 换绑同样在一个事务内完成。路由不调用模型，因此没有评估租约、迟到模型结果或 `route_evaluation` 恢复流程。

## 4. 事件日志与投影

- `timeline_event` / `task_event` / `work_item_event` / `token_usage` / `capability_audit` 都是 **append-only**，只插入不更新。
- 总览、事项与任务列表走**投影**：`work_item`、`task`、`agent_run` 的末态列在事件写入的同一事务内更新，读路径不扫事件。
- 投影可重建：给定事件日志，能重新计算 `work_item.stage/attention`、`task.stage`、`agent_run.status`、累计 token；`latest_summary` 也可从正式事实重建。重建脚本只在修复时使用。
- 每次投影更新递增所属作用域的 `revision`（`overview`、`task:<id>` 或 `work_item:<id>`），SSE 帧携带该值；`work_item.progress_revision` 只计实质进展，与 SSE revision 不同，禁止混用。
- `revision` 存在 `scope_revision`，由投影表上的触发器自增；读取方先取水位再读投影，避免「读到旧投影却配了新版本」。

## 5. 一致性纪律

| 场景 | 做法 |
|------|------|
| 连接 | 控制台使用有上限的 PostgreSQL 连接池；数据库仅在 compose 内部网络监听，健康检查必须执行真实读写探针 |
| 写事务 | 应用服务显式开启事务；需要串行变更的聚合使用行锁或条件更新（CAS），不得在事务内等待模型、飞书、GitHub、CI 或 Teleport |
| 确定性路由 | RouteRule/work_kind 从 Git 配置加载并带版本；路由、Mandate、worker_inbox 与事项事件在一个事务落地，无模型评估或迟到结果 |
| 外部副作用 | 与领域状态同事务写入 Outbox / 适配器队列，提交后执行；未知结果按通道进入对账，不回写假成功 |
| 单控制实例 | PostgreSQL 支持并发连接，但本项目仍以 `console.lock` 保证单控制台实例，避免重复后台作业；后台重活使用独立连接与作业锁 |
| 读并发 | 允许只读连接并发；长查询不得阻塞写事务，投影读不扫描完整事件流 |
| 重活 | 索引重建、`pg_dump`、批量清理走 worker_thread 或子进程；主连接不执行成批大事务，单事务不超过 1000 行 |
| 外键 | 全部声明，删除父记录前必须先处理子记录 |
| 约束 | 状态枚举、token 数非负、时间单调等尽量落到 `CHECK`；append-only 与 revision 触发器只做技术不变量，不藏业务路由 |

## 6. 索引与检索

- **关键词/模糊**：在标题、摘要和分块正文上使用 `pg_trgm` 索引与相似度/模式查询；保留 1~2 字中文查询的 LIKE 兜底，不依赖 PostgreSQL 默认英文分词。
- **语义**：`pgvector` 存 `vector(768)`；嵌入失败时保留原条目并标记 `embedding_status=pending/failed`，不写空向量。
- **检索合并**：先 `pg_trgm` 关键词召回，再 `pgvector` 向量召回，按 `(entry_id, chunk_no)` 去重后重排。
- **降级**：嵌入服务不可用时只走关键词与 LIKE，返回结果标注 `degraded: true`，不假装语义检索成功。

## 7. 迁移管理

- 目录 `src/store/migrations-pg/`，文件 `0001_pg_bootstrap.sql`、`0002_xxx.sql` 递增。
- 迁移**forward-only**：禁止修改已应用文件；修正用新迁移。
- 每个迁移在事务内执行，成功后写入 `schema_migration`（含 checksum）；checksum 不符即启动失败。
- 启动时自动执行未应用迁移。**迁移前不自动备份**（2026-11-05 裁决）：控制台容器内无 pg 客户端，自动 `pg_dump` 需要跨容器编排；当前环境未投入使用，重建库成本低于维护该链路。投产前若需要，用 `make backup` 手动先备份再升级，或由外部 CI 在发布前统一执行。
- **forward-only 只约束新 PostgreSQL 的 schema 演进**，不表示存在 SQLite → PostgreSQL 数据迁移。M3.8 从空库建基线，不做旧库 ETL、双写或兼容回退；旧 SQLite 只读归档。

## 8. 备份与恢复

- 备份 = 对运行中的 PostgreSQL 执行 `pg_dump --format=custom`，产物落 `workspace/backups/`；不能只复制正在写入的持久卷文件。
- 备份保留最近 14 份，超出按时间删除；定期用 `pg_restore` 恢复到临时数据库并做表计数与关键查询验证。
- 落地脚本 `scripts/backup.sh`（`make backup`）：备份与 `--verify`（把最新一份恢复到临时库核对表计数后销毁临时库）都经 compose 的 postgres 服务执行，dump 由标准输出直接落到宿主机文件，不在容器内留副本。
- 恢复 = 停控制台 → 恢复到目标 PostgreSQL → 校验 → 重启；旧 SQLite 不参与恢复或回退。
- 新 Markdown 知识目录随目录一起备份；它是文本，可另行进 Git。旧知识归档不进入新备份链。

**备份是明文**：库里有 `session` 表、`agent.secret_hash` 与 `console_credential.password_hash`，备份文件等同凭据材料。因此 `workspace/backups/` 目录权限 `0700`、文件 `0600`，不上传任何外部存储；恢复后立即吊销全部会话（`DELETE FROM session`），要求重新登录。口令哈希是慢哈希，离线爆破成本高于明文，但仍按凭据对待。

## 9. 保留与清理

| 数据 | 保留策略 |
|------|----------|
| `timeline_event` | 90 天；超期归档到按月文件后删除 |
| `task_event` / `work_item_event` | 永久（体量小） |
| `work_item` / `work_thread` / `thread_subscription` | 永久；撤销与结束保留历史，不物理删除 |
| `work_trigger` | 永久保留规范化事实、RouteRule ID/版本、处置原因与引用；不存猜测性项目提示或在线模型评估 |
| `worker_inbox` | 永久保留派工、ACK、Handback 与租约结果；审计与返工追溯依赖它 |
| `a2a_message` / `a2a_dead_letter` | 永久（审计与返工追溯依赖它） |
| `token_usage` | 永久（用量追溯依据） |
| `capability_audit` | 永久 |
| `tool_call_log` | 180 天；`deny` / `require_approval` 的判定永久保留（放行记录可清理） |
| `session` | 过期即删 |
| `ingest_receipt` | 7 天窗口，按 `received_at` 滚动删除 |
| `one_time_token` | `active` 过期即拒用；过期未消费记录可清理，`consumed` 永久保留用于机器加入审计 |
| `login_failure` | 锁过期或失败计数超窗口后，下次读取时清行 |
| `idempotency_record` | 永久（仅控制台写接口使用，人工操作量级） |
| `scope_revision` | 永久（每作用域一行，只覆盖当前水位，不随变更累积） |

**下钻不依赖 `timeline_event` 的 90 天**：任务详情的时间线来自 `task_event`（永久），`timeline_event` 只承载运行过程的细粒度事件流（总览与运行下钻用）。90 天外的任务仍能看「卡在哪、谁打回、打了多久」，只是看不到逐 token 的细节。

清理作业在每天凌晨执行，单事务、限量（每次最多 1000 行，与 §5 一致），避免长锁。
