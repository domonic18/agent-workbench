## 8. 复审结论

**M1.5 / M2 / M2.5 的拆任务阻塞项已清零**：注册表、入站通道、投递形态、闸门落点、第二台机、知识采纳与检索链路六项都有可执行落点。P1 中影响数据与事务的三项（幂等键、去重键、签发 saga）已在写第一行代码前定稿。

剩余风险不在设计而在**验证口径**：

1. 闸门只覆盖 MCP 通道；第四轮曾改为两条通道、两层拦截，**2026-10-31 用户裁决撤销原生工具通道（M2-6 取消）**。验收只按 MCP 通道取证，不宣称「100% 拦截」；终端直跑、绕开托管启动的会话单列为范围外。
2. 用量事件（原 `cost_event`，现 `token_usage`）写入方在复审时未定，总览的用量区块可能长期是空态——第三轮已关闭，见下。
3. 知识库允许直接改文件，索引新鲜度依赖 5 分钟轮询——「知识第二次不重复解释」的验收要在轮询窗口之外测。

这三项必须在对应里程碑开工前落定，否则会以「功能做了但验收做不了」的形式返工。

> 第三轮（2026-10-30）关闭第 2 条：用量事件（`token_usage`）写入方定为采集器，且刻意不做逐环拆分，口径见 §9-R3-6。

## 9. 第三轮：A2A 线程与链路（2026-10-30）

触发：复核需求 §2.4「三方链式」时发现，第二轮落的 `handoff` 事件只连相邻两个 Agent——B 自己身上的两条任务之间没有边，从 C 上溯会停在 B2，链是断的。

| # | 发现 | 处置 | 落点 |
|---|------|------|------|
| R3-1 | 一问一答没有容器；`round` 由客户端自增，重发、乱序、多端并发都会让它漂移 | 新增 `a2a_thread`，服务端按 `(发起方任务, 收件方)` 建线程并在同一事务内分配 `round`；线程状态**不落库**，按消息与投递记录现算 | 01 §5；02 §3.3 |
| R3-2 | 只有「跨 Agent」一种边，同一 Agent 的续接（B1→B2）没有建模 | 新增 `task.parent_task_id`（可空、创建后不可变）；`handoff` 事件用 `relation` 区分 `a2a` / `continuation`；上溯即链，不设长度上限 | 02 §3.1；03 §4.2 |
| R3-3 | 交接靠 Agent 自报，漏报即断链 | 改为 ACK `request` / `escalate` 时必须带**自己**的 `task_id`，服务端同事务连边并写事件；`reply` / `notify` 的 ACK 不收，否则反向再连一条边会成环 | 01 §5.1 |
| R3-4 | 需求 §2.4 写「接收 A 产出时自建」，与 §1.2「发 A2A 前必须先有任务」矛盾 | 改为「向 A 发起索取时自建」，并点明 B1→B2 是同 Agent 续接 | 需求 §2.4 |
| R3-5 | 需求 §2.4 验收要求「一路点到 A 的实现任务」，但 A 可能只有 run 没有任务 | 改为「点到链上最早的任务；上游只有 run 时如实止步，不补建」 | 需求 §2.4 |
| R3-6 | 逐环用量没有来源 | **有意从简**：只由采集器写；一 run 至多归属一条任务；归属不上就留 `NULL`，不加 Agent 报账通道 | 02 §3.6 |
| R3-7 | 需求 A7 / C4 要求前端明示可见性边界，03 没有对应文案 | 总览常驻一行、任务列表页脚一行，两处都写明「不是全量」 | 03 §4.1 / §4.2 |
| R3-8 | 00 §6 数据流写「飞书消息 → 通信契约校验 → 任务」，与 01 §8.1「入站不建单」相反 | 改为「卡片回调 → capability / 指令 → 回执」，任务只由 Agent 经 MCP 创建 | 00 §6 |
| R3-9 | 计划层冲突：M1.5 声明「没有 `POST /api/tasks`」却又有建单用例；M2.5 没有工具面，Agent 无处建单、无处发信 | M1.5-5 改为「指令解析与回执」并明写不产生任务；新增 **M2.5-0** 承载五个 MCP 工具与 `decide()` 接入 | M1.5.md；M2.5.md |

**判据**：链式样本上溯得到 `C ──a2a── B2 ──continuation── B1 ──a2a── A`，两种关系各自标注正确；`reply` 方向不产生边；重复 ACK 幂等。

## 12. 第六轮：播报式协作与通道实验（2026-11-02）

触发：M2.5-8 真机验收中群内容外泄、多余唤醒、mention 解析失真、权限悬起四类问题集中暴露，停止打补丁，对「群 @ 唤醒」机制做系统级重审与通道实测。裁决：**群=状态投影+人类入口，路由/交互=控制台+执行面**（详见 01 §8.2，落地为 M2.5-9）。

| # | 实验 / 发现 | 结论 | 落点 |

| R6-1 | 群 @ 唤醒机制实证：cc-connect 群级投递不按 @ 路由（@ 2 个 bot 第 3 个也醒，每轮 5 万+ input tokens）；守纪靠 LLM 自觉；mention 名字按接收方应用作用域渲染，同一消息在不同 bot 视角 @ 的对象不同；headless 会话卡权限墙永久悬起 | IM 语境不为路由而生，路由判定必须移出群消息通道 | 01 §8.2；M2.5-9 |

### 14.4 对第七轮 US-01 缺口的承接

第七轮剩余的设计缺口现已形成目标契约：专用 Bug 机器人的结构化提交生成 `bug.submitted` Trigger；按机器人去重键和原始反馈关联工作事项；负责修复的 Agent 仍自行创建 Task 并关联 `work_item_id`；PR、评审、CI 与测试验证通过业务 Thread 连续回链；最终结果经原 Bug 机器人适配器回告。需求歧义、无法复现、架构取舍回到人，生产发布仍单独确认。

这表示**架构设计缺口已补**，不表示连接器、表迁移、Agent 工具或真实闭环已经实现。US-02 与 US-12 也在 00、01、03 获得对应目标与链路，但同样须以后续真实业务验收为准，不能凭文档更新改判场景完成。

### 14.5 后续实现必须验证的反例

- 同一外部事件重推、同一线程连续评论、模型超时后迟到响应，不得重复开工或覆盖新策略。
- owner 续接不得扩大范围；context 订阅不得产生执行；Thread 换绑必须有退回理由与审计。
- 采集文本中的「请修复 / 请发布」不得成为授权；巡检候选未经确认不得修改；生产发布不得由任何完成状态触发。
- 无 Task 的 Run、无 Run 的待澄清事项都可展示；Run 结束、PR 合并或 CI 成功不能单独完成工作事项。
- 模型不可用时事件保留且可恢复；正常等待不告警，同一停滞无新证据时不重复打扰。

本轮只修改需求承接所需的架构正文与评审记录，未修改开发里程碑、任务状态或排期。

## 16. 第十轮：数据与协同架构重基线（2026-11-03）

触发：讨论 Super-agent 的 Router/Worker、卡兹克的 Rules 实践以及实际部署复杂度后，发现旧方案同时存在 SQLite 扩展焦虑、每会话 stdio proxy、执行机组件偏多、Source Memory/规则/模型共同路由难以排障，以及 A2A ACK 与业务验收边界不清。用户逐项裁决后形成以下新基线。

### 16.1 被 supersede 的旧方案与现行替代

| 旧方案（本文历轮记录） | 现行裁决 |
|---|---|
| SQLite + better-sqlite3、FTS5 + sqlite-vec | PostgreSQL 与控制台同机 Docker Compose，仅内部网络；`pg_trgm + pgvector`；备份 `pg_dump/pg_restore` |
| 旧 SQLite 业务数据与 Markdown 知识迁移/保留运行 | **全部重新开始**：新空库、新空知识目录；旧文件只移到运行路径外归档，不扫描、不导入、不双写 |
| 每会话 stdio MCP proxy，全量 MCP 闸门 | 控制台同一 HTTP 服务提供 Streamable HTTP `/mcp`，直接替换；仅 `task/a2a/kb/work` 自有控制工具；本机第三方 MCP、原生工具与终端直跑出界 |
| 执行机采集器 + 独立 dispatch + proxy | 每机一个 `aw-node`（采集 + Claude Code 调度），不做安全判定；WorkBuddy 用官方 automations，首版 Run/对话/Token 显示「未接入 / —」 |
| proxy 注入 RunContext / AW_GRANTS | Agent Bearer + 服务端归属校验；首版不引入 `run_token`，不开放高风险资源工具；`decide()` 与审计集中在控制台 |
| Fast Path + Slow Path + `route_evaluation` | **单一确定性 Router**：鉴权去重 → Thread owner → 唯一 Git RouteRule → `needs_person`；一期无在线模型路由、无 `route_evaluation` |
| Source hint / Memory 参与派工 | Source Agent 只整理事实；项目不明先澄清，不输出猜测 hint；RouteRule/work_kind 与项目角色映射 Git 版本化，目标解析到稳定 `agent.key` |
| A2A ACK / parent auto_close 被理解为业务验收 | 保留上游 Task 验收与自动收口，但它不等于 WorkItem 人工接受；真实 Bug 以 PR + 当前 head CI 进入待验收，由原 Bug 机器人接受才 done，退回到原事项返工 |
| proxy 前置 Token 硬停覆盖 MCP 通道 | 只拒绝新的自有控制工具调用与 Assignment，不冒充第三方工具或进程急停；WorkBuddy Token 首版不参与计量 |

### 16.2 保留并复用的既有基础

- A2A 信封、单 owner 多 context、租约、ACK、幂等、死信与 Outbox 运输原则继续有效；系统派工使用独立 `worker_inbox(kind=assignment/input)`，不让 `system/router` 伪造普通 A2A。
- 谁干活谁建单：Assignment ACK 必须绑定承接 Agent 自己创建且属于同一 WorkItem 的 Task；Input ACK 只表示消费，二者都不完成 WorkItem。
- Handback 按单条 Trigger 退回；owner 换绑事务化并保留理由，旧 owner 可保留 context。
- Teleport CE + tbot 的短时证书、审批 saga 与 `ticket_id` 审计对账保持不变；Teleport proxy 不是被移除的 MCP proxy。
- Super-agent 的 WorkItem/Mandate、Thread 直通、Inline & Spill、Chain of Recall 和低打扰原则保留；卡兹克 Rules 只保留确定性分派思想，不照搬混合 cwd/skill/并发/通知的大配置。

### 16.3 实施顺序与验收反例

实施拆为 M3.8（3 项）与 M3.9（2 项）：

1. M3.8-1 文档与裁决收口；
2. M3.8-2 PostgreSQL 无行为变化迁移（全新开始）；
3. M3.8-3 控制台远程控制 MCP + 每机单 aw-node；
4. M3.9-1 确定性 Git Router + WorkItem + worker_inbox；
5. M3.9-2 真实 Bug 接受/退回 E2E。

必须实际验证：旧 SQLite/知识不导入；停止 PostgreSQL 后健康检查失败且不回退；A 的 Bearer 不能操作 B；第三方 MCP 不出现在 `tools/list`；同机第二个 aw-node 不产生重复副作用；重复事件不重复开工；旧 SHA 的绿色 CI 与当前 SHA 的红色 CI 都不能待验收；真实 CI 失败与原 Bug 机器人退回后才能以接受收尾。历史 A2A 验收不冒充新真实 Bug 业务验收。

### 16.4 首次使用端到端自动装配（2026-11-03 确认）

首次使用按四步完成，不把内部架构概念转化为用户的配置负担：

1. **初始化控制台**：无管理员凭据时只开放 bootstrap mode，首次启动在本机输出一次性 `bootstrap_admin` token。用户在 `/setup` 输入 token 并设置管理员口令后创建会话、解锁完整控制台；`CONSOLE_INIT_PASSWORD` 仅为可选无人值守种子，frp 复用既有部署配置。
2. **添加执行机**：控制台签发一次性 enroll token，安装脚本以独立 token 鉴权兑换机器 ID 与采集密钥、安装 aw-node、写 launchd 并自检，不要求控制台会话。过期或重放不签发任何密钥；令牌和密钥不进命令行或日志。
3. **添加项目**：aw-node 在本机读取 cc-connect 并通过机器 Bearer 上报项目、目录、Agent 与渠道元数据，控制台据此预填；控制台不直接读取执行机文件系统。用户只确认主责 Agent，系统创建 agent.id/key 与**不含明文 Bearer**的待下发运行时配置；秘密在后续 aw-node 配置请求中按轮换返回最新值，ACK 后不再返回明文。
4. **启用 Bug 工作流**：系统生成默认 `bug_fix` RouteRule、Mandate 与证据模板，aw-node 调用 `POST /api/aw-node/config`，**ACK 前每次请求轮换并返回最新 secret 和 config_version，旧 secret 立即失效以支持响应丢失重试，ACK 后不再返回明文**；aw-node 以备份 + 原子写入应用最新配置并回执，用户无需第二次安装。随后按数据库、机器、采集、MCP、Agent、角色、Bug Source、GitHub/CI 分项预检并给出修复入口。

`/setup` 只负责引导，不是第五块主导航，也不是规则编辑器。初始化状态由 `bootstrap/status` 与配置 ACK 共同支撑；一次性 token 只存哈希、TTL 与消费状态。首次验收必须证明：无需手工编辑 RouteRule/plist/数据库配置即可完成装配；过期/重放 token 不签发密钥；配置不完整不会显示已就绪或创建空 Assignment；WorkBuddy 三项过程数据留空不阻断初始化。完成后直接衔接真实 Bug 闭环，用户日常只负责反馈与接受/退回。

## 17. 第十一轮：控制台产品化重构（2026-11-06）

用户对控制台提了三条问题，判断均成立：不像生产级可用的 Web 系统；下载安装流程粗糙；Agent 概览信息不足且被测试 Agent 淹没、无法 CRUD。经确认，本轮做**全量重构**，以下为用户裁决。

| 裁决 | 内容 | 影响 |
|------|------|------|
| V1 | 视觉**自研生产级基线**，不等 Ardot 原型 | **推翻** 2026-11-01「前端视觉对齐 Ardot」的方向；Ardot 文件在仓库外，本次不引。`03` §10 新增设计基线与组件基元章 |
| V2 | **全量**重构：总览 / 任务 / 授权 / 知识 / 登录页 / 首次使用落地页，并**新增「接入执行机」页** | `03` §3 路由表加 `/onboarding`；四屏信息架构不变 |
| V3 | Agent 管理**留在总览页**（卡片升级为管理表格 + 编辑抽屉），**不新增第五块主导航** | 守住「四屏不变」；`/onboarding` 是总览的下钻页，与 `/tasks/:id` 抽屉同级 |
| V4 | Agent 删除 = **硬删除并级联清理关联行**（不是软停用） | 新增 `agent_tombstone` 墓碑表与 `AFTER DELETE` 水位触发器；`01` §4.2 落档 |

**保留不变的结论**：

- **不引第三方 UI 组件库**仍然成立（`03` §2）。被推翻的是「四屏规模不值得有设计系统」这一前提，不是「自建组件」这一做法；基元共 15 个，仍在 20 个以内。图标取自 `lucide-react`——图标不是组件库。
- **不改 A2A / WorkItem / 授权判定等后端语义**。本轮新增的三个 Agent 路由只做档案编辑、删除影响预览与硬删除，不碰既有判定链。
- **主导航仍是四屏**。新增的是下钻页，不是第五块导航。

**级联删除的分档口径**（`01` §4.2）：`destroyed` 随事务删除（含该 Agent 参与的**整条 A2A 线程**）、`detached` 引用置空但事实保留（触发与知识条目）、`retained` 原样保留（任务与 append-only 审计）。`task.assignee` 等纯文本列靠墓碑显示「已删除 Agent X」，不留裸 id。

**测试 Agent 清理**：一次性删除 16 个联测遗留 Agent（`s9-outsider` ×6、`s10-a/b-*` ×10 等），库内 Agent 从 27 降到 8（7 台机器绑定的真实 Agent + `a2a-real`）；根治手段是给 `e2e/s8`、`s9`、`s10`、`m41` 四个脚本加收尾清理，脚本自建的 Agent 跑完即删。
