## 1. 项目定位

把散落在飞书群、黑板表格、本地脚本里的多 Agent 协作，收进一个**可看、可控、可计量**的工作台，并在此基础上形成**事件驱动的自主交付与经营协调系统**。系统管理的中心不是 Agent 是否忙碌，而是一件事是否持续产生可验证的业务结果。

- **产品形态**：控制台 + 飞书双面并存。控制台管「状态与权力」，飞书管「说话与拍板」；控制台不做 IM，Agent 详情只读展示已采集对话。
- **核心用户**：持有多个 Agent（WorkBuddy / cc-connect + Claude Code）的个人开发者，当前唯一用户。
- **管理对象**：以工作事项与不可变 Mandate 承载目标、授权、上下文、进展和结果；Assignment/Input/Handback 负责系统派工、续接和退回；Task 记录具体 Agent 的责任，Run 记录真实执行过程，彼此不互相冒充。
- **可见性分运行时**：Claude Code 展示实际采集的 Run、对话与 Token；WorkBuddy 首版只展示业务事实，Run、对话和 Token 显示「未接入 / —」，不伪造为 0 或离线。
- **一期四屏**：总览 / 任务 / 授权 / 知识。工作事项在总览与任务详情中呈现，不新增对话页或第五块主导航。
- **不替换运行时**：Claude Code、cc-connect、WorkBuddy 与 Squadsight 是既有资产，本项目补协调、控制与事实记录，不重建其执行或评审能力。

### 1.1 架构设计目标

以下目标承接「一人公司」愿景和 P0 场景 US-02、US-01、US-12、US-15。它们是终态设计约束，**不直接改变现有开发里程碑**；实现顺序仍以计划文档为准。

| 目标 | 架构含义 | 可验收结果 |
|------|----------|------------|
| G1 以结果为中心 | 工作事项独立于单次对话、Task 和 Run 存续；完成必须有产出、验证依据与人工接受 | 真实 Bug 以来源 → PR → 当前提交 CI → 原 Bug 机器人接受/退回全程追溯，进程或 A2A 结束不等于事项完成 |
| G2 事件驱动持续推进 | 外部变化先归一为 Trigger；已知 Thread 的后续事件直通原事项，新工作只按 Git 版本化 RouteRule 派工，未知或冲突交人 | 需求与架构对齐后，常规 PR、CI、修复和验证推进不等待人逐步催促；每次派工可由规则 ID 与版本解释 |
| G3 节约人的注意力 | 正常推进保持安静；需要人时一次给出背景、证据、选项、影响和建议 | 人能区分正常、等待、需要自己、待验收和异常停滞，无需重读全部对话 |
| G4 模型与宿主分工 | Source Agent 与执行 Agent 负责语义理解和专业工作；状态、权限、项目策略、预算、路由和不变量由确定性宿主执行 | 模型不能在线派工、越权、绕过三轮评审、改变项目评审策略或批准生产发布 |
| G5 可靠且可恢复 | 事件去重、事务写入、持久化副作用、租约、重试上限、死信和恢复共同保证闭环 | 重启、网络失败或模型超时不会丢事件、重复开工或把未知结果写成成功 |
| G6 上下文按需召回 | 常用上下文内联，长文与历史保留摘要、引用和读取入口；沿 Trigger → Thread → 工作事项 → Task/Run 逐跳追溯 | 切换项目或续接任务不需注入全部历史，原始依据仍可定位 |
| G7 权限与成本内建 | 每次续接都复核原 Mandate 与当前项目策略；Token 硬停只作用于自有控制工具与新 Assignment，人工闸门和审计不被路由绕过 | 人反馈 Bug 与 Agent 巡检保持不同修复权限；生产发布始终单独确认；不宣称第三方工具或进程急停 |
| G8 单机可演进 | 保持模块化单体、单 PostgreSQL 实例和现有运行时；确定性 Router 是内部职责，不是新的全能 Agent 或分布式平台 | 不为引入概念而增加 Temporal、云原生集群或 OS 级沙箱；PostgreSQL 也不暴露公网或建设高可用集群 |

**主动性的边界**：系统可以在明确请求、已确认事项或书面项目规则内持续推进；可以后台核实和准备建议，但不得把「投机执行」解释为可擅自修复巡检问题、扩大需求范围或发布生产。

图中 `aw-node` 是执行机唯一新增常驻进程，内含采集与 Claude Code 调度两个模块；它不做安全判定。协作群四条播报的生成 / 投递机制见 [01](./01-后端服务设计.md) §8.2。

**边界约定**：

1. 控制台容器内监听 `0.0.0.0:8787`，compose 仅在宿主机 `127.0.0.1:8787` 发布端口，frpc 经内部服务名 `console:8787` 访问；不处理 TLS，公网暴露全部由 frp 承担。
2. frpc 需**两条独立规则**：`aw.example.com → 8787`（http）与 `tp.example.com:8443 → 443`（tcp，给 Teleport proxy）。本项目只交付配置片段，不运维 frps。
   - Teleport 为什么不用 443：frps 的 443 已被 `*.example.com` 通配证书的 HTTPS vhost 占用（`dev.example.com` 等站点在此），而 Teleport proxy 自带 TLS、需要 **TCP 透传**，不能与 TLS 终止的 vhost 共享端口。故用独立 tcp `remotePort = 8443`（2026-10-30 裁决）。
3. Teleport CE 独立于控制面进程，控制台只消费其签发的凭证与审计事件；Teleport CE 为 **AGPL-3.0**，以独立进程/容器运行，不与本项目代码链接。
4. 每台运行 Agent 的机器只部署一个 `aw-node`，采集模块只能通过 `/api/ingest` 单向推事件，调度模块负责 Claude Code 唤醒；WorkBuddy 使用官方 automations 轮询。
5. 控制面进程必须单实例：启动时获取 `workspace/console.lock`，已有活进程持锁则拒绝启动。PostgreSQL 只监听 compose 内部网络，不映射宿主机或公网端口。
6. frpc 规则 ① 的生产形态固定指向 compose 服务名 `console:8787`；规则 ② 始终指向 Teleport proxy 的 443，仅公网侧端口为 8443。远程 MCP 复用规则 ① 的 `/mcp`，不增加端口或隧道。
7. **控制台机器人只有一个**，与各 Agent 自己的飞书机器人互不相干。Agent 的机器人是它们各自的身份（7 个 Agent 就是 7 个），控制台不通过飞书订阅或读取它们的消息——需求 §1.2 明确机器人之间互相不可见；Agent 详情只展示本地执行会话的实际采集结果，不因此获得额外飞书可见性。控制台只持有一个自建应用的凭据，用于发审批卡片与收回执；多接一个 bot 就多一套 `APP_ID` / `APP_SECRET`。
8. **三平面划分见 §2.1**：展示面不承担任何约束判定；控制约束集中在控制面与 Teleport 等资源边界。展示面**保持 B/S**，不引入桌面客户端——手机访问、飞书 iframe 免登、推广零安装三条硬约束，桌面端一条都满足不了。
9. **管控只覆盖控制台自有的控制类 MCP**：`task / a2a / kb / work` 经控制台 `/mcp` 鉴权、判定并审计；本机第三方 MCP、Claude Code 原生工具与终端直跑均不在项目管控边界内（2026-11-03 裁决）。一期不做 OS 级沙箱，不能把这些未覆盖通道计入拦截率。

### 2.1 三平面划分

系统按「谁执行约束」分三层，而不是按「前后端」划分：

| 平面 | 形态 | 部署 | 承担 | 不承担 |
|------|------|------|------|--------|
| 展示面 | B/S：浏览器（手机 / 电脑 / 飞书 iframe） | 无安装 | 渲染、提交、订阅 SSE | **任何约束判定** |
| 控制面 | 服务端（Fastify + PostgreSQL） | 同机 Docker Compose | 能力判定、远程控制类 MCP、委派白名单、可见性过滤、审计、账本、确定性路由、**协作播报与上游 Task 验收收口** | 直接接触 Agent 进程与本机文件 |
| 执行面 | 每台机一个 `aw-node` + WorkBuddy 官方客户端能力 | launchd / WorkBuddy automations | 采集、Claude Code 唤醒、WorkBuddy 轮询 | 制定或执行托管安全策略；代理第三方 MCP；拦截原生工具 |

三条推论：

1. **展示面保留 B/S。** 手机可访问、飞书网页应用 iframe 免登（M4）、公司推广零安装，三条都是硬约束；桌面客户端一条都满足不了，还要多维护一套签名与分发。
2. **约束集中在控制面与资源边界。** 浏览器和执行机都不在托管安全判定链路上；自有 MCP 在控制台过 `decide()` 并留审计，SSH/DB 由 Teleport 短时证书约束。第三方 MCP、原生工具和终端直跑明确不计入管控覆盖。
3. **执行面只为真实本地能力而存在。** 采集会话文件和启动 Claude Code 会话必须靠近执行环境，因此保留一个 `aw-node`；不为了形式上的三平面再给它增加 proxy 或安全闸门。

**分层纪律**：

- 依赖方向只能向下。路由层禁止直接访问数据库。
- 领域层不引入 HTTP / 飞书 SDK 类型，保证可脱离进程单测。
- 外部系统（飞书 / Teleport / 采集器 / Bug 机器人 / GitHub / CI）一律通过适配器接入，接口在领域层定义。
- 确定性 Router 是应用服务内的纯规则组件，不调用模型、不持有执行凭证；RouteRule 与 `work_kind` 来自 Git 版本化配置，路由结果必须记录规则 ID、版本和处置原因。

### 3.1 工作组织模型与确定性 Router

| 对象 | 回答的问题 | 与其他对象的关系 |
|------|------------|------------------|
| **工作事项 `work_item`** | 哪件业务事情需要产生什么结果 | 聚合来源、目标、授权、进展、产出和验证；可关联多个 Task、Run、Thread，也可在尚无 Task 时处于澄清或等待状态 |
| **授权 `mandate`** | 为什么可以做、允许做到什么程度 | 创建 WorkItem 时固化预期结果、范围、约束、授权依据和策略版本；后续续接不隐式扩权 |
| **派工与续接 `assignment / input`** | 谁需要承接新工作，或处理哪条后续事实 | 通过 `worker_inbox` 持久化；Assignment 先派工，承接 Agent 后建自己的 Task，Input 交给当前 owner |
| **退回 `handback`** | 哪条后续事件超出范围或归属错误 | 按单条 Trigger 退回并记录理由；需要时事务化更换 owner，旧 owner 可保留 context |
| **任务 `task`** | 哪个 Agent 承担哪一份具体责任 | 仍由执行方 Agent 创建和维护；通过 `work_item_id` 归属事项，不用任务代替整件业务事情 |
| **运行 `agent_run`** | 哪一次真实执行发生了什么 | 仍可无 Task；可经 Task 或显式关联归属工作事项，进程退出只结束 Run，不自动结束事项 |
| **业务线程 `work_thread`** | 同一个 Bug、PR、CI 流程或外部话题的连续事件在哪里 | 以来源与外部键稳定关联；不同于只承载 Agent 信封往返的 `a2a_thread` |
| **触发 `work_trigger`** | 哪个外部或内部事实可能推动工作 | 持久化、去重并保留来源；观测事件与业务 Trigger 分开，不因被采集就获得工作授权 |
| **订阅 `thread_subscription`** | 后续事件应续接哪件既有工作 | 将业务线程绑定到工作事项，可选记录首选 Task；只提供归属与上下文，不授予新权限 |
| **工作收件箱 `worker_inbox`** | 哪项派工或后续输入等待哪个 Agent 处理 | 以 `kind=assignment/input` 共用租约、重投和幂等；Assignment ACK 绑定承接方自己的 Task，Input ACK 只表示消费，都不等于事项完成 |

**确定性 Router** 是控制面内的一组纯规则，不是常驻全能 Agent，也不直接执行代码：

1. **先校验与去重**：完成 Source 身份、格式、项目、预算和授权检查；同一外部事件只接收一次。
2. **Thread owner 直通**：命中有效订阅的事件直接进入原工作事项并形成 Input；context 只提供信息，不产生执行权。
3. **RouteRule 派新工**：未归属事件必须命中唯一 Git 版本化规则，由 `work_kind` 决定执行 Skill、Mandate 与证据要求，由项目注册表把 `target_role` 解析为已注册 Agent。
4. **未知即交人**：无项目、无规则或规则冲突统一 `needs_person` 并记录原因；一期不调用在线模型路由，也不读取 Source Agent 的私人 Memory 作为派工依据。
5. **不替代责任主体**：Bug 机器人继续负责自然语言反馈、拆分、去重与提交；Squadsight 继续负责阻塞式 PR 评审；承接 Agent 仍自行创建 Task。

详细事件流见 [01](./01-后端服务设计.md) §9，表关系见 [02](./02-数据服务设计.md) §3.9，授权不变量见 [05](./05-授权与闸门设计.md) §6.5。

## 4. 技术选型总览

| 层次 | 技术 | 状态 | 理由 |

## 6. 核心数据流

五条主链路：采集（只推）、飞书（出入口，不建 Task）、Agent（MCP 工具）、业务事件（Trigger 驱动事项）、协作（播报式 A2A，2026-11-02 裁决）。

```
会话文件（Claude Code / cc-connect）
        │ 增量读取（inode + offset）
        ▼
本机 aw-node ──POST /api/ingest──▶ 归一化 + 幂等去重
        │                              │
        │ 失败进本地 spool             ▼
        │                        事件日志（append-only）
        │                              │
        │                              ├──▶ 读模型投影（总览 / 任务）
        │                              ├──▶ SSE 实时帧（带 revision）
        │                              └──▶ token 账本（用量事件）
        ▼
    重试 / ACK
```

```
飞书（控制台机器人）
  ├─ 入：卡片回调 / 指令消息 ──▶ 来源 token + open_id 白名单 + event_id 去重
  │                              ├─ 审批动作 ──▶ capability（**不建单**）
  │                              └─ 指令 ──▶ 解析后回执；未命中回「不支持」，不转发
  └─ 出：发件箱（状态机）──▶ 卡片 / 通知 ──▶ 回执 / 未知 / 失败
                                                  │
                                                  └──▶ 对账与人工裁决
```

```
Agent（Claude Code / WorkBuddy）
   │ HTTPS + Agent Bearer + Streamable HTTP MCP
   ▼
控制台 /mcp ──decide() + 服务端归属校验 + 审计
   │  工具：task_create / task_update / a2a_* / kb_* / work_*
   │
   ├──▶ task / task_event（谁干活谁建单）
   ├──▶ a2a_message + outbox（对端拉取）
   ├──▶ knowledge_entry（只写 candidate，采纳须人工）
   └──▶ capability（授权必须挂 task_id）

第三方 MCP 不经过此端点，也不计入项目管控覆盖。
```

```
项目 Agent 宿主 / 专用 Bug 机器人 / GitHub / CI / 控制台指令 / 内部领域事件
        │ 来源适配器：认证、schema、外部 ID 去重、敏感信息收敛
        ▼
work_trigger（持久化事实）
        │
        ▼
确定性 Router：鉴权 / 去重 / 授权 / 预算 / Thread owner / RouteRule
        │
        ├─ 已有 owner ──▶ 原工作事项 + Input + 原授权复核
        │
        ├─ 唯一规则 ──▶ WorkItem + Mandate + Assignment + 审计
        │
        └─ 未知 / 冲突 ──▶ needs_person + reason_code（不调用模型）
```

工作事项、路由依据与 `worker_inbox` 在同一事务中落库，外部通知或执行适配器调用通过既有发件箱在提交后执行。Router 不代替 Agent 建 Task；承接 Agent 读取 Assignment 后仍通过 `task_create` 创建自己的任务并关联 `work_item_id`，再以 ACK 确认承接。

**可见性边界**：控制台机器人收不到人与其他机器人的飞书私聊，机器人在飞书里也互相不可见（见需求 §1.2）。所以「Agent 干了什么」只有两个来源：采集器推的 run（过程）与 Agent 自报的 task（账目）；本地会话采集只能扩大已采集内容的只读展示，不能宣称全量飞书可见。跨 Agent 协作一律经 A2A，不依赖群内转述。

```
协作（A2A · 播报式，2026-11-02 裁决）
A 会话(工作)        控制面(事实源+播报)          aw-node(每机·按收件箱唤醒)      协作群
   │ task_create         │                            │                          (控制台bot+人)
   │ a2a_send(request) ─▶│ 落库 + outbox(pull)        │                           │
   │                     ├──〔交接〕push ───────────────────────────────────────────▶│
   │                     │                            ├─拉到 B 有消息 → spawn 会话  │
   │                     │      B 六步: inbox→task_create→ack(同事务挂 parent)      │
   │                     ├──〔接单〕push ◀── ack ──────────────────────────────────  │
   │                     │      B 执行本职 → a2a_send 回执(reply,原线程)              │
   │                     │      B task_update 关单(pending→running→done)             │
   │                     ├──〔完成〕push ◀── done ─────────────────────────────────  │
   │                     ├─拉到 A 有消息(reply) → spawn 会话                          │
   │                     │      A 审阅回执 → ack(=上游 Task 验收，非 WorkItem 人工验收)  │
   │                     ├──同事务: 下游全终态+回执全已确认 → parent 链自动收口       │
   │                     │                (pending→running→done, actor=system)       │
   │                     ├──〔验收〕push ──────────────────────────────────────────▶│
```

播报全部经发件箱 push 通道（幂等键 `collab:{uuid}`，失败退避重试）；唤醒不经过群——调度器只认收件箱，群内零 bot 轮次。详见 [01](./01-后端服务设计.md) §8.2。

## 8. 架构铁律

1. **单一事实源**：没进控制台库 = 没发生；不使用黑板。投影与摘要必须可重建，不得成为第二事实源。
2. **控制面不承担 IM**：飞书只做输入输出口。
3. **可靠性靠状态机 + 持久化 + 幂等键**，不靠重试与轮询兜底。
4. **外部输入边界校验，失败即拒**（fail-closed），不做静默降级。
5. **系统密钥仅存 env，主体凭据只存哈希**：会话签名、飞书凭据、采集器/Agent 的共享密钥原文只在 env 或各自运行环境；Agent / 采集器密钥由控制台签发，库中只存 `secret_hash`，明文仅签发时返回一次。登录口令**不入 env 长期保存**，无管理员凭据时进入 bootstrap mode，以一次性 `bootstrap_admin` token 在 `/setup` 设置口令后以 scrypt 哈希写入 `console_credential`；`CONSOLE_INIT_PASSWORD` 仅为可选无人值守种子，此后校验只读库。一次性 token 同样只存哈希、TTL 与消费状态，日志记事件不记敏感值。
6. **凭证短时化**：15 分钟 TTL，自动续期，吊销以自然过期为主。
7. **迁移 forward-only**：禁止手改已应用迁移。
8. **事项与执行分离**：Task/Run 结束以及 A2A 回执 ACK 都不自动等于 WorkItem 完成；Bug 以 PR + 当前提交 CI 通过进入待验收，只有原 Bug 机器人的人工接受才使其完成。
9. **路由唯一且可解释**：新工作只按 Thread owner 或 Git 版本化 RouteRule 落地，记录规则 ID、版本与原因；一期没有在线模型路由。模型在执行与 Source 理解中的输出也不能越权或改变项目策略。
10. **续接不扩权**：Thread 订阅只提供归属与上下文；消息正文、Source Memory、模型判断和历史授权都不能隐式扩大权限。
11. **正常保持安静**：通知必须对应人需要采取的行动或可消费的结果；心跳、日志增长和模型活动不等于实质进展。
12. **先复用再增设基础设施**：在单机和单用户规模下，不因引入 Router / Watchdog 概念而引入 Temporal、集群或替换现有 Agent 运行时。
