# 后端服务设计

> 创建日期: 2026-10-29
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。数据表结构见 [02-数据服务设计.md](./02-数据服务设计.md)。

## 1. 服务总览

控制面是**单进程模块化单体**：HTTP/SSE/远程 MCP、领域逻辑、后台作业与采集接入共享一个 PostgreSQL 事务域。PostgreSQL 与控制台在同机 Docker Compose 中运行，仅监听内部网络。

| 模块 | 职责 | 不负责 |
|------|------|--------|
| `server/routes` | 参数校验、鉴权、序列化 | 业务规则、事务 |
| `domain/*` | 工作事项与任务状态机、订阅归属、授权与聚合规则 | HTTP、飞书 SDK 类型、自由文本模型裁决 |
| `domain/routing` | Thread owner、Git RouteRule 匹配、项目角色解析与处置原因 | 在线模型路由、直接执行工具、绕过授权、代替 Agent 建 Task |
| `reliability` | 事件日志、发件箱、幂等、对账、租约恢复 | 业务语义 |
| `store` | PostgreSQL 访问与迁移 | 业务判断 |
| `adapters` | 飞书、Teleport、Bug 机器人、GitHub、CI 等 Source 协议 | 领域决策 |

**事务边界只有一个**：应用服务层开启事务，仓储只构造查询。路由层不得直接读写数据库。

## 2. 进程与生命周期

- 容器内监听 `0.0.0.0:8787`，compose 仅在宿主机 `127.0.0.1:8787` 发布；frpc 通过内部服务名 `console:8787` 访问并承担公网 TLS。
- **单实例**：启动时以 `O_EXCL` 创建 `workspace/console.lock` 并写入 pid；锁存在且 pid 存活则拒绝启动，避免两个控制台重复运行后台作业。PostgreSQL 虽支持多写者，本项目仍明确只运行一个控制面实例。
- 启动顺序：加载 env → 获取单实例锁 → 连接 PostgreSQL → 执行 forward-only 迁移 → 恢复未完成作业（发件箱对账、索引重建队列、`worker_inbox` 租约与未完结工作事项）→ 注册 HTTP/SSE/`/mcp` → 开始监听。
- 关闭：停止接收新请求 → 等待在途事务（上限 10s）→ 落盘并关闭库。
- 健康检查 `GET /healthz` 返回 `{ status, version, db, uptime }`；数据库不可写时返回 503。
- 进程崩溃由 launchd 拉起；重启后必须能从库中恢复，不依赖内存状态。

## 3. 认证与会话

一期为口令登录；二期（M4）引入飞书免登，但**免登只覆盖只读**，吊销凭证、删除条目等敏感操作仍要求二次确认，不因换登录方式而放宽。

| 项 | 约定 |
|----|------|
| 口令存储 | 库中 `console_credential` 单行，只存 scrypt 哈希（N=16384 / r=8 / p=1，16 字节随机盐）；不存明文，日志不记口令 |
| 口令初始化 | 无凭据时进入 **bootstrap mode**：仅 `/healthz`、`/setup` 与指定 bootstrap 接口开放。首次启动在本机输出一次性 bootstrap token，用户在 `/setup` 输入该 token 并设置管理员口令，服务写入 scrypt 哈希后创建会话并解锁完整控制台。`CONSOLE_INIT_PASSWORD` 仅作可选无人值守种子，不是启动前提；已存在凭据时直接进入登录模式 |
| 会话 | 服务端签发随机 session id，HttpOnly + SameSite=Lax Cookie，默认 12 小时 |
| 校验 | 除 `/healthz`、`/api/auth/login`、`/api/ingest`、首次 `/api/bootstrap/admin` 与 `/api/bootstrap/status` 及 aw-node 的 `/api/aw-node/enroll` 外，业务接口全部要求控制台会话。`/api/aw-node/discovery` 与 `/api/aw-node/config*` 使用兑换后的机器 Bearer，不使用控制台会话 |
| CSRF | 浏览器非 GET 请求校验 `Origin` 与自定义头 `X-Requested-With`；缺失或跨站一律 403。Cookie 不作为唯一凭据，写操作另需 `Idempotency-Key`。`/api/aw-node/enroll` 使用一次性 token 而非 Cookie，不参与 CSRF Cookie 校验；discovery/config 使用机器 Bearer 与幂等键，不共用浏览器会话 |
| 失败处理 | 登录失败统一返回 401，不区分「口令错」与「不存在」；同一 IP 连续失败 5 次锁定 10 分钟（取需求 v0.7 口径，见下方注）；成功登录清零计数 |
| 来源白名单 | **只看 `Host`**：必须是 `127.0.0.1:8787` 或 `aw.example.com`。`X-Forwarded-For` **不作准入依据**——frpc 在容器内转发，来源是 docker bridge 地址且头可被伪造；`XFF` 只写审计日志，用于排查谁打过这个端口 |
| 敏感操作 | 吊销凭证、删除知识条目要求重新输入口令（M4 后改为二次确认，仍不放行免登直通） |

> `/api/ingest` 不使用控制台会话，改用采集器密钥；`/mcp` 使用 Agent Bearer。两套密钥互不通用。

> **与需求的两处口径（2026-10-30 收口，消除「两个值并存」）**：
> ① 锁定窗口取**需求 v0.7 的 10 分钟**（原本文档写 5 分钟，无依据，属笔误级漂移）。锁定只作用于登录接口，已登录会话不受影响；因 frp 会把外部来源收敛到单一出口 IP，锁定在该形态下实际是「全局锁」，故必须配成功即清零，不能累积。
> ② 会话寿命**刻意收紧为 12 小时**，不采纳需求的 7 天滑动：控制台能签发 Agent 密钥、能批授权，会话越长暴露面越大；手机端 12 小时内重新输一次口令，代价可接受。此差异为有意为之，代码按 12 小时实现。
> ③ 来源判定只信 `Host`。`Host` 也能被伪造，但它在本形态下有实际约束力：宿主机仅通过 `127.0.0.1:8787` 发布控制台，公网流量必须经 frp 且 frp 按域名分流；同时它挡住了 DNS rebinding（恶意网页用自有域名解析到 127.0.0.1 时，`Host` 不是白名单值）。`XFF` 连这层约束都没有，拿它做准入只会得到一个看起来严格、实际无效的检查。

### 3.1 通道与鉴权对应

| 通道 | 调用方 | 凭据 | 失配时 |
|------|--------|------|--------|
| 控制台 HTTP | 人（浏览器） | 会话 Cookie + CSRF 头 | 401 / 403，写操作另需 `Idempotency-Key` |
| aw-node `/api/ingest` | aw-node 采集模块 | `machine_id` + `secret`（Bearer），库中只存 `collector_secret_hash` | 401，**整批拒收**，不部分入库 |
| 首次 `/api/bootstrap/admin` `/api/bootstrap/status` | 首次管理员与 `/setup` | **分段鉴权**：初始化前使用本机输出的一次性 `bootstrap_admin` token；设置管理员后创建会话，后续 `bootstrap/status` 与其他业务接口一样使用控制台会话，不再使用 token | token 无效/重放 401；会话缺失或失效 401，不创建第二套初始化凭据 |
| aw-node `/api/aw-node/enroll` | 首次安装脚本 | 一次性 enroll token，库中只存 `token_hash`、TTL 与消费状态；无 Cookie/控制台会话 | 过期、重放或不匹配均 401/410，不签发机器密钥 |
| aw-node `/api/aw-node/discovery` `/api/aw-node/config*` | 已兑换的 aw-node | 兑换后的 `machine_id + secret`（Bearer），不使用 Cookie；`config` 按 `config_version` 轮换恢复，`config/ack` 另需幂等键，不把配置签发当普通幂等重放 | 401/403；配置归属不匹配时拒绝 |
| 远程 MCP `/mcp` | Agent 运行时 | `agent_id` + `secret`（Bearer），库中只存 `secret_hash` | 401；跨 Agent 拉取或操作 403 |
| 飞书长连接（消息事件与卡片回调） | 飞书开放平台 | 出站 WebSocket，由应用凭据认证；不接收公网回调 | 时间窗外的丢弃；非白名单 `open_id` 拒绝；`event_id` 去重 |
| 资源访问（B / C 类） | Agent | Teleport 短时证书 | 不经控制台 HTTP，证书无效即连接被拒 |

**本方案不做请求体 HMAC，理由是两者互斥**：HMAC 验证需要服务端持有原始密钥，而「库中只存哈希」恰恰要求服务端不留可用的密钥材料。要么把密钥以可还原形式存库（哈希白存），要么放弃 HMAC。选后者——库和备份泄露时拿不到可用凭据，这是更强的一条。

重放不靠签名，靠**幂等与去重**：写接口必须带 `Idempotency-Key`；`/api/ingest` 以 `(collector_id, stream_id, seq)` 去重；A2A 以 `msg_id` 去重。传输层由 frp 提供的 HTTPS 承担，明文不下线。

## 4. API 设计

业务 API 统一前缀 `/api`，JSON 收发，错误体 `{ error: { code, message, detail? } }`。Agent 的 MCP 入口独立为 `POST /mcp`（Streamable HTTP），复用同一控制台进程、frp HTTP 规则和 Agent Bearer，不新增服务或端口。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/healthz` | 健康检查 |
| POST | `/mcp` | Agent 远程 Streamable HTTP MCP；仅控制台自有控制工具，Agent Bearer |
| POST | `/api/auth/login` / `logout` | 口令登录 / 退出 |
| GET | `/api/overview` | 总览聚合：Agent 列表 + 运行与用量指标 + 工作事项的正常 / 等待 / 需要人 / 待验收 / 异常停滞分类 |
| GET | `/api/agents` | Agent 注册表：机器、项目、状态、最近心跳 |
| POST | `/api/agents` | 注册 Agent（返回一次性 `secret`，仅此一次可见） |
| POST | `/api/agents/:id/rotate` | 轮换 Agent 密钥（旧密钥立即失效） |
| PUT | `/api/agents/:id/targets` | 维护委派白名单 `allowed_targets_json`（仅控制台会话；Agent 自身 Bearer 调用 403） |
| POST | `/api/machines` | 登记机器并以同样方式签发采集器密钥（一次性明文） |
| POST | `/api/machines/:id/rotate` | 轮换 aw-node 采集密钥（旧密钥立即失效） |
| POST | `/api/bootstrap/admin` | 首次 bootstrap mode 专用：校验一次性 bootstrap token，设置管理员口令并创建会话，解锁完整控制台 |
| GET | `/api/bootstrap/status` | 返回当前初始化步骤、各组件状态与下一步；**初始化前由 bootstrap token 鉴权，管理员创建后由控制台会话鉴权**，`/setup` 据此决定强制路由 |
| POST | `/api/bootstrap/enroll-token` | 首次添加执行机：控制台会话签发一次性短 TTL enroll token，库中只存哈希 |
| POST | `/api/aw-node/enroll` | 安装脚本凭 enroll token 兑换机器 ID 与长期采集密钥；一次性使用，重放拒绝，敏感值不写日志 |
| POST | `/api/aw-node/discovery` | aw-node 用机器 Bearer 上报本机 cc-connect 发现的项目、目录、Agent 与渠道元数据 |
| GET | `/api/bootstrap/discovery` | 控制台会话读取 aw-node 已上报的发现结果，供初始化预填；不直接读取执行机文件系统 |
| POST | `/api/bootstrap/agents` | 控制台会话确认项目与主责 Agent，创建 agent.id/key、项目角色及**不含明文 Bearer**的待下发配置；此时只准备身份，不提前生成秘密 |
| POST | `/api/bootstrap/complete` | 控制台会话确认默认 bug_fix，生成 Git RouteRule/Mandate/证据模板并执行预检，完成初始化 |
| POST | `/api/aw-node/config` | aw-node 用机器 Bearer 拉取运行时配置；**ACK 前每次请求都轮换并返回最新 secret 与新 config_version，旧 secret 立即失效，支持响应丢失后的安全重试；ACK 后仅返回非敏感配置，不再返回明文** |
| POST | `/api/aw-node/config/ack` | aw-node 上报配置已写入/已生效及版本，供预检确认，不视为 WorkItem 或 Assignment |
| POST | `/api/bootstrap/preflight` | 按数据库、机器、采集、MCP、Agent、角色、Bug Source、GitHub/CI 返回分项检查与修复提示 |
| GET | `/api/tasks` | 任务列表，支持状态 / 项目 / 承接方过滤与分页 |
| GET | `/api/tasks/:id` | 任务详情：含关联能力（`capability` 摘要，不返证书内容）与 token 汇总（该任务 `token_usage` 合计与明细条数），抽屉一次取齐 |
| GET | `/api/tasks/:id/events` | 任务时间线（快照 + 游标增量） |
| GET | `/api/tasks/:id/a2a` | A2A 往返线程（按 `thread_id` 分组、组内 `round` 升序，附投递状态与线程状态） |
| GET | `/api/work-items` | 工作事项列表，按项目、阶段、注意力状态与来源过滤；只读 |
| GET | `/api/work-items/:id` | 工作事项详情：目标、授权依据、当前阶段、下一步、关联 Task/Run/Thread、产出与验证摘要 |
| GET | `/api/work-items/:id/events` | 工作事项永久时间线（快照 + 游标增量），包含来源、路由决策与实质进展证据 |
| GET | `/api/capabilities` | 待批 / 生效 / 历史三视图 |
| POST | `/api/capabilities` | 提交授权申请 |
| POST | `/api/capabilities/:id/approve` | 批准（生成凭证） |
| POST | `/api/capabilities/:id/reject` | 拒绝 |
| POST | `/api/capabilities/:id/revoke` | 吊销 |
| GET | `/api/knowledge` | 条目列表与检索 |
| GET/PUT | `/api/knowledge/:id` | 条目读取 / 编辑 |
| POST | `/api/knowledge/:id/adopt` | 候选采纳：`candidate` → `active`，触发索引重建 |
| POST | `/api/knowledge/rebuild` | 整库重建索引 |
| POST | `/api/ingest` | aw-node 采集模块推送事件（Bearer 采集器密钥） |
| GET | `/api/stream` | SSE 实时帧（控制台会话） |

**约定**：

- 分页统一 `?limit=&cursor=`，不用 offset 翻页。任务列表的 `cursor` 为 `<createdAt>:<id>`；任务事件流(`/api/tasks/:id/events`)的 `cursor` 为 `seq`，缺省 0 返回全量快照。
- 任务详情与事件流均要求控制台会话，并返回 `task:<id>` 作用域的 `revision`；客户端拿到 `revision=N` 即表示数据不早于 N。
- 写操作必须携带 `Idempotency-Key`；重复键返回首次结果，不重复执行。
- 所有时间返回 RFC3339 UTC；前端负责本地化。
- 所有计数返回整数（token 一律 `*_tokens` 整数），禁止浮点；一期不做计价，不返回金额。
- A2A 线程只读：`GET /api/tasks/:id/a2a` 返回「`initiator_task_id = :id` 的线程」以及「该任务作为某条 `a2a_message.task_id` 出现过的线程」——接收方因此也能在**自己**的任务详情里看到完整往来。线程按 `thread_id` 分组、组内消息按 `round` 升序；每条消息附 `outbox` 的最新投递状态（多次重投只返回一行）；`ack_at` 为空表示对端尚未确认；线程状态（`open` / `awaiting_reply` / `completed` / `expired`）由服务端现算，不落库。`auth_ticket` 只返回凭证标识，不返回任何证书内容。响应同时返回 `task:<id>` 作用域 `revision`，客户端拿到 N 即表示数据不早于 N。
- 工作事项接口只读，不提供人工建 Task、模型对话或生产发布入口；事项由已授权 Trigger 与领域规则产生，Task 仍只由执行 Agent 创建。任务详情中的 `work_item_id` 可跳到事项详情，事项详情也可定位关联任务与已采集 Run。
- Agent 身份只来自 `agent_id + secret`，不读请求体里的 `agent_id`；库中只存 `secret_hash`。普通注册/轮换明文仅在响应出现一次；bootstrap 配置在 ACK 前按请求轮换并返回最新 secret，ACK 后不再返回明文。

**首次初始化与自动装配**：bootstrap 应用服务负责协调管理员初始化、一次性 enroll token、aw-node 发现结果上报、项目/角色确认、运行时配置下发与回执、默认 `bug_fix` 装配和分项预检，不新增独立进程。无管理员凭据时只能进入 bootstrap mode；一次性 bootstrap token 只用于设置管理员，不能与 enroll token 混用。

**跨机发现与配置下发**：控制台不直接读取执行机文件系统。aw-node 在本地读取 cc-connect 配置后上报发现结果，控制台据此预填项目；用户确认后，控制台先创建 Agent 身份与非敏感配置，aw-node 再用机器 Bearer 调用 `POST /api/aw-node/config`。**ACK 前每次配置请求都轮换并返回最新 secret 和 config_version，旧 secret 立即失效，因而响应丢失后可安全重试；ACK 后只返回非敏感配置，不再返回明文。** aw-node 以备份 + 原子写入应用最新配置并回传版本与生效状态，浏览器不需要接触或转交 Bearer，用户无需第二次安装。预检失败必须返回具体组件和修复提示，不得显示已就绪，也不得创建空 Assignment。

### 4.1 Agent 身份签发（M1-6 定稿）

| 项 | 约定 |
|----|------|
| 密钥形态 | 每 Agent **一枚**独立随机密钥：32 字节 CSPRNG → base64url（43 字符）。**不用非对称密钥对**——一二期 Agent 与服务端之间只有控制台发起的 HTTP 拉取，单向、无第三方写入，密钥对换来的「服务端不落可用凭据」在这里没有增量：对称密钥只存哈希已经做到；却要多付一套签名规范化与公钥分发。等真出现不可信第三方接入再换 Ed25519 |
| 签发入口 | 普通注册/轮换只有控制台用户（会话）能调 `POST /api/agents` 或 `POST /api/agents/:id/rotate`，生成 `agent_id`（`agt_` + ULID）与 `secret`，**响应即唯一一次明文**；bootstrap 项目确认时只创建身份，秘密改为 **aw-node 的 `POST /api/aw-node/config` 在 ACK 前每次请求都轮换并返回最新 secret，旧 secret 立即失效以支持响应丢失重试，ACK 后不再返回明文**。两条路径都随即只存哈希，之后任何日志、审计、错误响应与普通配置响应都不再出现明文 |
| 入库 | `agent.secret_hash` 使用与控制台口令、采集器密钥同一套 **scrypt 自描述哈希格式**；库与日志均不保存明文，算法参数变更时保持旧值可校验 |
| 校验 | `Authorization: Bearer <agent_id>.<secret>`；按 `agent_id` 取哈希 → 常量时间比较（`timingSafeEqual`）。**不存在与不匹配返回同一个 401 `UNAUTHORIZED`**，不暴露某个 Agent 是否注册过 |
| 轮换 | `POST /api/agents/:id/rotate`：覆盖哈希并记 `rotated_at`，旧密钥**立即**失效，不设并行有效期；只能由人在控制台发起 |
| 吊销 | `status='disabled'`，下一次请求即 401；行保留不删，否则审计与 `a2a_message.from` 的历史引用会断 |
| 丢失 | 明文不可找回，只能轮换。这写进前端提示，避免用户以为能「查看密钥」 |
| 采集器同构 | `machine.collector_secret_hash` 用同一套签发 / 比对 / 轮换逻辑，**两套密钥不通用**（见 [02](./02-数据服务设计.md) §3） |

## 5. A2A 通信契约

Agent 间消息是结构化信封，缺必填字段**直接拒收**并回执缺失项。

```json
{
  "v": "1.0",
  "msg_id": "msg_01J...",
  "thread_id": "thr_01J...",
  "task_id": "tsk_01J...",
  "round": 3,
  "reply_to": "msg_01J...",
  "from": "agent:workbuddy",
  "to": "agent:codex",
  "intent": "request",
  "summary": "需要补一份接口契约",
  "expect": "一份 OpenAPI 片段",
  "deadline": "2026-10-30T12:00:00Z",
  "refs": ["kb_01J..."],
  "auth": { "ticket_id": "cap_01J..." }
}
```

以上是服务端落地后的信封；客户端提交时只给业务字段（`task_id` / `thread_id?` / `reply_to?` / `to` / `intent` / `summary` / `expect` / `deadline` / `refs` / `auth`）。`msg_id`、`round`、`from` 一律由服务端生成；`thread_id` 首条由服务端分配，之后客户端回传它即可续同一线程。

| 字段 | 规则 |
|------|------|
| `v` | 协议版本，未知版本拒收 |
| `msg_id` | 服务端生成，全局唯一；客户端重试用 `Idempotency-Key` 去重，拿到同一个 `msg_id` |
| `thread_id` | **服务端分配**。不带时按 `(发起方任务, 收件方)` 复用已有线程，没有则新建；带了必须存在且调用方是线程参与方 |
| `task_id` | 必须指向**发件方自己的**已存在任务；不存在拒收，不做隐式建单 |
| `round` | **服务端按线程分配**（`max(round)+1`，同事务内计算），客户端给值一律忽略；不靠客户端自增避免乱序与跳号 |
| `reply_to` | 可选，必须是同线程内的 `msg_id`；跨线程引用拒收 |
| `from` / `to` | 必须命中已注册 Agent，不接受自由文本 |
| `intent` | 枚举：`request` / `reply` / `notify` / `escalate` |
| `summary` / `expect` | 非空且长度受限，禁止空泛描述 |
| `deadline` | `request` / `reply` / `escalate` 必填；`notify` 可免。过期未 ACK 转死信并回执发件方，不静默丢弃 |
| `auth` | 涉及受控资源时必填，指向有效凭证 |

**身份不由消息自述**：`from` 由宿主在投递时注入并校验，Agent 无法通过文本参数扩大自己的身份或权限。

**任务归属与交接**：`task_id` 恒指发件方自己的任务，两端任务靠 `parent_task_id` 相连（表结构见 [02](./02-数据服务设计.md) §3.1）。跨 Agent 交接不靠 Agent 自报：接收方 ACK 一条 `request` / `escalate` 时必须带自己的 `task_id`，服务端在同一事务里写下游任务的 `parent_task_id` 与一条 `handoff` 事件（`relation='a2a'`）；不代建、不改对方任务的 `assignee`。

**线程与链路是两件事**：线程（`thread_id`）回答「这一问一答在哪」，链路（`parent_task_id`）回答「这条任务是谁交给我的」。同一 Agent 的续接（B 收下 A 的产出、再向 C 发起）由 `task_create` 带 `parent_task_id` 显式声明，服务端写 `relation='continuation'` 的 `handoff` 事件。只有跨 Agent 的边能由 ACK 推出，同一 Agent 的边推不出来——这就是两种关系必须分开记的原因。

### 5.1 投递形态（信箱拉取）

A2A 消息不直连对端 Agent，统一落控制台 `a2a_message`，由对端**拉取**。这样跨机、离线、NAT 后的场景都适用，不需要为每台机开入站端口。

```
发送方 ──写 a2a_message + 发件箱(同事务)──▶ 控制台库
                                              │
对端 Agent ──MCP a2a_inbox(cursor, wait=25s)──▶ 取走
                                              │
对端 Agent ──MCP a2a_ack(msg_id)──▶ 出箱置 delivered
```

| 环节 | 约定 |
|------|------|
| 入队 | 发送方写入 `a2a_message` 与发件箱同一事务；返回 `msg_id` 与 `round` |
| 拉取 | 长轮询：有消息立即返回；无消息挂起到 25s 后返回空数组，客户端立刻重连 |
| 归属 | 只返回 `to` = 本 `agent_id` 且未 ACK 的消息；跨 Agent 拉取直接 403 |
| 确认 | 对端处理完必须 ACK；未 ACK 的消息在租约过期后重新可见（at-least-once） |
| 交接 | ACK `request` / `escalate` 时必须带**自己**的 `task_id`（缺失 422）；服务端同事务写 `handoff` 事件并置该任务 `parent_task_id`。`reply` / `notify` 的 ACK 不收 `task_id`——反向再连一条边会成环 |
| 幂等 | 对端按 `msg_id` 去重；控制台侧不因重复拉取推进 `round` |
| 判据 | `delivered` **只以 ACK 为准**，拉走不等于投递成功；拉取通道因此不产生 `uncertain` |
| 死信 | `deadline` 过期仍无 ACK → 出箱 `failed` 并写入 `a2a_dead_letter`，回执发送方「已过期，请重新发起」 |
| 豁免 | `notify` 可免 `deadline`（无截止即不过期）；`request` / `reply` / `escalate` 必填 |
| 唤醒 | **每台执行机一个 `aw-node`**：调度模块对本机各 Claude Code Agent 拉 `inbox?wait=0`，有工作才 spawn headless 会话；同机实例锁防止重复采集与重复调度。WorkBuddy 不经过 `aw-node`，使用官方 automations 轮询自己的 Assignment/Input |

> aw-node 采集模块是「只推不拉」，A2A 是「只拉不推」，方向相反，不得复用同一套信令。`uncertain` 只保留给 push 通道（飞书）。

### 5.2 远程控制类 MCP（2026-11-03 改判）

Agent 通过控制台同一 HTTP 服务提供的 **Streamable HTTP `/mcp`** 使用控制工具，直接替换 stdio proxy，不保留双模兼容层：

| 候选 | 结论 | 理由 |
|------|------|------|
| 控制台 Streamable HTTP `/mcp` | **选定** | Claude Code 与 WorkBuddy 只需 URL + Bearer；复用现有 frp HTTP 规则，执行机不再有 proxy |
| 每会话 stdio proxy | **取消** | 每会话包装、PATH/cwd 与升级成本高；控制工具本身不依赖本机执行环境 |
| `/api/stream`（控制台 SSE）复用 | 否 | 它是浏览器水位通道，不是 MCP 协议；A2A 仍由 Agent 主动拉取 |

首版只暴露控制台自有工具，不代理、不转发本机第三方 MCP，也不把 Claude Code 原生工具纳入管控：

| 工具 | 级别 | 说明 |
|------|------|------|
| `task_create` | L1 | 创建自己的 Task，`assignee` 恒为 Bearer 对应的 Agent；可声明 `parent_task_id` / `work_item_id`，服务端校验归属 |
| `task_update` | L1 | 只能更新自己的 Task，状态跃迁过领域状态机 |
| `a2a_send` | L1 | 写 `a2a_message + outbox` 同事务；收件方在委派白名单内 |
| `a2a_inbox` | L0 | 长轮询取件，只返回本 Agent 的消息 |
| `a2a_ack` | L1 | 确认处理；Task 交接与上游验收语义保持 §5.1，不等于 WorkItem 人工验收 |
| `kb_search` | L0 | 返回带出处的知识片段，记录检索审计 |
| `kb_write` | L1 | 写 Markdown + `knowledge_entry` 镜像，状态强制 `candidate`，来源任务必须属于本 Agent |
| `work_read / work_inbox / work_ack / work_handback` | L0/L1 | M3.9 增加；读取或处理本 Agent 的 Assignment/Input，身份与事项归属由服务端校验 |

**身份与判定都在控制台**：Bearer 只证明 Agent 身份；`from`、`assignee`、任务归属、A2A 白名单和 WorkItem 归属均由服务端校验，模型提交的 `agent_id` 等自述字段一律丢弃。`decide()` 与工具审计在控制台应用服务内执行，不再经过本地 proxy，也不引入 `run_token`。当前不开放依赖 Run/Task 上下文的高风险资源工具。

**建单仍由 Agent 发起**，控制台没有人工建 Task 入口；知识仍只能写 `candidate`，采纳只能由人完成。远程 MCP 只改变接入位置，不改变这些领域不变量。

## 6. 发件箱状态机

所有对外投递（飞书消息、A2A 跨机消息）统一走发件箱，保证「发出去了」这件事有状态。**`worker_inbox` 不是 Outbox 的新 channel**：它保存控制面 Assignment/Input 的承接、消费与 Handback，复用租约和幂等原则；Outbox 仍只负责 A2A 与外部通知运输，不为系统派工伪造 A2A 消息。

```
pending ──claim──▶ claimed ──▶ sending ──▶ delivered
   ▲                   │           │
   │                   │           ├──▶ retry_wait ──┐
   └───────────────────┴───────────┴──▶ uncertain    │
                                        │            │
                                        └──▶ failed ◀┘
```

| 状态 | 含义 | 出口 |
|------|------|------|
| `pending` | 已入库待领取 | 领取 → `claimed` |
| `claimed` | 持有租约 | 开始发送 → `sending`；租约过期 → `retry_wait` |
| `sending` | 已发出，等待结果 | 确认 → `delivered`；确定拒绝 → `failed`；未知 → `uncertain` |
| `retry_wait` | 等待重试窗口 | 到点 → `pending` |
| `delivered` | 终态（push 为回执成功，pull 为对端 ACK） | — |
| `failed` | 终态（确定失败 / 已进死信） | 人工重投 |
| `uncertain` | 结果不明（仅 push 通道） | 人工裁决为 `delivered` 或 `failed` |

**关键不变量**：

1. `idempotency_key TEXT NOT NULL UNIQUE`，由调用方生成、入队时写入；重复键直接返回已有记录。控制台内部投递用 `task_id:round:kind:payload_hash`、`daily:{date}:{kind}`、`cap:{cap_id}:{event}`；Agent 发起的 A2A 用客户端带来的 `Idempotency-Key` 原样入库（`round` 由服务端分配，客户端拼不出复合键）。
2. 领取用 `lease_token` 条件更新，token 单调递增；过期租约不能提交结果。
3. **投递分两类，围栏只加在业务投递上**：
   - **业务投递**（A2A `request`/`reply`/`escalate`）：`uncertain` 是任务级围栏，存在即不入队新消息、不判定完成，直到人工裁决。
   - **通知投递**（飞书卡片、每日汇总、提醒）：失败只重试；`uncertain` 不围栏任务，超过重试上限进 `failed` 并告警，任务照常完成。
4. 只有「确定拒绝」（内容违规、目标不存在、对端明确 4xx）才可判 `failed`；限流、超时、未知码一律按未知处理。
5. 过期回收：未进入 `sending` 的租约回 `retry_wait`；已进入 `sending` 的转 `uncertain`，不自动重放。pull 通道以 ACK 为判据，不产生 `uncertain`。回收由独立作业启动即扫、此后每 2s 执行，不挂在飞书推送作业上——未配置飞书时 pull 通道的未 ACK 消息同样按时重新可见。

## 7. 实时推送

- `GET /api/stream` 使用 SSE，事件类型 `snapshot` / `delta` / `heartbeat`；要求控制台会话。
- 订阅参数：`client_id` 必填（前端在 localStorage 生成，1~128 位字母 / 数字 / 下划线 / 短横线）；`scope` 可重复，缺省 `overview`，另接受 `task:<id>` 与 `work_item:<id>`；非法值 422。
- 每条帧携带 `(scope, revision)`：`scope` 为 `overview`、`task:<id>` 或 `work_item:<id>`；三者版本域独立，禁止互相比较。
- 客户端连接后先收 `snapshot`（含各订阅作用域的当前 revision），之后只收 `delta`。`delta` 只带新水位、不带投影数据，客户端据此失效查询后重拉 REST。
- `delta` 的 revision 严格递增；客户端发现缺口（收到 revision > 本地 + 1）应重新拉取快照，不做猜测性拼接。
- 心跳 20s 一次，防止 frp 与中间层断连。
- 并发上限按 **`client_id`** 计（前端在 localStorage 生成，连接时带上），单用户最多 10 个客户端；同一浏览器的多个标签页共享一条连接，服务端向各标签广播同一帧。超限返回 429。

## 8. 飞书连接器

控制台只做入口与出口，不承担对话。

| 方向 | 行为 |
|------|------|
| 出 | 审批卡片、协作群四条播报、任务升级通知、每日汇总；一律经发件箱，失败可对账（§8.2） |
| 入 | 卡片按钮回调 → 校验 `open_id` 白名单 → 转控制台动作 |

- 消息事件与卡片回调**都走飞书长连接（WebSocket）**，不需要公网回调地址、Verification Token 或 `Encrypt Key`（2026-10-31 裁决，修订同日早先的 HTTP + token 方案）；长连接由应用凭据认证，事件仍校验时间戳窗口与 `event_id`。
- 回调发起人 `open_id` 必须命中白名单（仅本人）；审批审计 `actor` 记审批人 `open_id`。
- 回调处理幂等：同一 `event_id` 只处理一次。
- 回调响应必须同步返回 `{ toast, card }`：`toast` 给点击人即时结果，`card` 就地替换为终态（去掉按钮，展示结果 / 审批人 / 到期时间）；非白名单、载荷非法、超时间窗只弹 `toast`，不改卡片。签发失败按实际结果展示「签发失败」，不能一律显示成功。裁决超过飞书响应窗口时，重试命中 `event_id` 幂等并以最新快照刷新卡片。
- 卡片按钮只做「跳转控制台」与「一键批准 / 拒绝」两类，不做多步表单。
- 飞书不可用时任务照常运行，通知进 `retry_wait`，恢复后补投。

### 8.1 入站消息通道（M1.5 飞书下派任务）

卡片回调只管审批，与消息事件共用同一条长连接；**发给控制台自己的指令**走飞书事件订阅 `im.message.receive_v1`。

> 控制台机器人只处理 @ 它、或私聊它的消息；发给其他机器人的消息它收不到（飞书按 @ 投递，且不转发机器人消息）。那些消息的建单由执行方 Agent 自报（§5.2），控制台不代建。

```
控制台消息事件 ──▶ 时间戳窗口 + 来源 token(可选) ──▶ event_id 去重
                                        │
                                        ▼
                            指令解析（查询 / 审批 / 重发通知）
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
                  可执行 → 处理并回执             不可识别 → 回执原因，不猜
```

| 项 | 约定 |
|----|------|
| 订阅方式 | 飞书长连接（WebSocket），消息事件与卡片回调共用；不需要公网回调地址与 Verification Token |
| 加密 | 不启用（2026-10-31 裁决）：`Encrypt Key` 留空，不做解密；长连接由应用凭据认证，两类事件都按时间戳窗与 `event_id` 校验 |
| 去重 | `event_id` 唯一索引；重复事件直接忽略，不重复处理 |
| 指令集 | 只处理显式登记的控制台指令（见下表）；未命中即回执「不支持」，不猜测意图、不转发给其他 Agent |
| 不建单 | 控制台入站**不产生任务**；任务由执行方 Agent 经 `task_create` 自报 |
| 归属 | 群 `chat_id` 只用于标识来源与回复落点，不再承担 `chat_id → 项目` 的建单映射 |
| 权限 | 仅白名单 `open_id` 可下指令；其他人回执「无权限」，不入库 |
| 回执窗口 | 按事件时间判断：24 小时内 `reply` 原消息，超出改用 `chat_id` 新建消息，避免引用失效。飞书 `reply` 接口本身没有 24h 限制，这条是产品策略；入站已限 24h，该分支只兜底延迟与边界 |
| 失败 | 解析异常回执可读原因并写审计；不建单、不转发、不让模型自由发挥 |

指令语法（命令名固定英文，不区分大小写；不做自然语言猜测）：

| 指令 | 语法 | 当前行为 |
|------|------|----------|
| 查询任务 | `/task list`、`/task <taskId>` | 读 `task` 摘要回执，列表最多 10 条；空库回「当前没有任务」 |
| 批准 | `/approve <taskId>` | 校验任务存在，回执「审批通道尚未接入（M2）」并写审计 |
| 拒绝 | `/reject <taskId> [原因]` | 同上，原因随回执带出 |
| 重发通知 | `/resend <taskId>` | 校验任务存在，回执「发件箱尚未接入（M2）」并写审计 |

- 非斜杠文本、未登记命令、已知命令的多余参数一律回「不支持」；缺参一次回全部缺失项。
- `taskId` 约束为 `[A-Za-z0-9._:-]{1,64}`；群消息正文中的 `@_user_N` 占位符在解析前剥离。
- 每条白名单指令（含不支持 / 参数错误）写 `feishu_command` 审计：原文、规范命令名、结果、回执，用于回答「为什么回不支持」。

### 8.2 协作群播报与唤醒（2026-11-02「播报式协作」裁决，替代 M2.5-8 的 @ 通知方案）

A2A 的请求 / 回复正文不进飞书，只走控制台；协作群降级为**状态投影 + 人类入口**：机器路由彻底移出 IM 语境，群播报由控制台确定性生成，Agent 唤醒改走执行面。

- **四条播报**：① 〔交接〕A2A `request` / `escalate` 落库成功；② 〔接单〕承接方 ack；③ 〔完成〕下游任务转 `done`；④ 〔验收〕根任务被系统收口。其他状态变化不发；正文一律无 `@`，不唤醒任何 bot。
- **谁发 / 怎么发**：控制台以**自身应用**（`FEISHU_APP_ID` / `FEISHU_APP_SECRET` + `FEISHU_COLLAB_CHAT_ID`）经发件箱 push 通道直发（`enqueuePush` kind=`collab_bulletin`，幂等键 `collab:{uuid}`），`send-worker` 投递、失败指数退避重试，`uuid` 交飞书幂等去重（交接取 `msg_id`，接单取 `a2a:ack:{msg_id}`，完成取 `task_done:<taskId>`，验收取 `task_closed:<taskId>`）。控制台不持有也不需要 Agent 的飞书凭据，不再需要 proxy 自报 bot 身份。
- **唤醒直达（每机单 aw-node）**：调度模块对本机 Claude Code Agent 拉 `a2a_inbox?wait=0`，有待处理消息才 spawn headless `claude -p`；MCP 配置直接指向控制台 `/mcp` 与 Agent Bearer。cc-connect 保留人类入口职责，`api.sock` 只有出站 send、无入站注入（2026-11-02 实测），故不做唤醒通道。WorkBuddy 使用官方 automations 轮询。
- **上游 Task 验收即收口**：承接方回执被发起方 ACK 只表示上游 Task 验收，控制台在同一事务沿 `parent_task_id` 链自动收口并发〔验收〕播报。**它不代表 WorkItem 人工验收，也不使真实 Bug 进入 done**；后者必须满足 §9.4 的 PR+CI 与原 Bug 机器人人工接受。
- **群内防唤醒**：播报无 `@`，持有 `include_bot` 权限的 bot 应用也只接收「@ 任意 bot」的消息，纯文本播报不可达；迁移完成后 Agent bot 退出协作群，群内仅控制台 bot + 人类，从成员层面根除群级唤醒。人类入口不变：在各 Agent 自己的项目群 @ 它，或协作群 @（迁移期）。
- **历史墙（存档，供排障）**：① `include_bot` 权限与 `open_id` 应用作用域（M2.5-8 验收二）；② cc-connect `allowed_tools` 与 `allow_from` 不热重载；③ 收件方协议姿势（ack 用自己 task_create 的任务 id、回执带 `thread_id`、关单走状态机）——三者均由控制台强校验兜底，CLAUDE.md 把报错翻译成正姿势。
- **关闭条件**：控制台未配 `FEISHU_COLLAB_CHAT_ID` 或飞书凭据时播报静默关闭（发件箱照常入队，配好后补投），A2A 与任务行为不变。

**运行时序（一次 A→B 委派的全生命周期，2026-11-02 真机验证）**：

```
A 会话(工作)        控制面                         aw-node(每机)                 协作群
   │                     │                              │                        (控制台bot+人)
   │ MCP task_create ───▶│ task 表(pending)             │                         │
   │ MCP a2a_send ▶│ a2a_message + outbox(pull)   │                         │
   │                     │ outbox(push):〔交接〕───────────────────────────────────▶│ 群内可见,无 @
   │                     │                              ├─ GET inbox?wait=0(B)    │
   │                     │◀── B 有消息,spawn headless ──┤                         │
   │                     │     B: a2a_inbox 领取(30s 租约)                         │
   │                     │     B: MCP task_create(下游,pending)                    │
   │                     │     B: MCP a2a_ack(:id) ── 同事务:                │
   │                     │        挂 parent_task_id + push〔接单〕────────────────▶│
   │                     │     B: (本职工作；自有控制 MCP 经控制台判定)              │
   │                     │     B: MCP a2a_send(reply,原线程+reply_to)        │
   │                     │     B: MCP task_update(:id) (pending→running→done)      │
   │                     │        └─ push〔完成〕─────────────────────────────────▶│
   │                     │        └─ closeAncestorsIfComplete: 未全确认→不收口      │
   │                     ├─ GET inbox?wait=0(A) ── A 有回执,spawn headless ──▶     │
   │                     │     A: a2a_inbox 领取 → 审阅结论                         │
   │                     │     A: MCP a2a_ack(:id)(=上游 Task 验收)          │
   │                     │        └─ 同事务: 下游全终态+回执全已确认                │
   │                     │           parent 链收口(pending→running→done,            │
   │                     │            task_event: actor=system/reason=auto_close)   │
   │                     │        └─ push〔验收〕─────────────────────────────────▶│
```

要点：① 每一步都有库内事实（task / a2a_message / outbox / task_event），播报只是事实的投影；② 收件箱领取带 30s 租约，会话中途死亡由发件箱对账回收后重新可见，调度器下一分钟重试；③ 群内只出现四条播报与人类发言，任何 bot 不因群消息起轮次。

**会话模型与上下文边界（2026-11-02 实验结论，后续架构讨论的前提事实，详见 06 §12-R6-7）**：

- 系统里同一个 Agent 存在**两条互不继承的会话线**：cc-connect 托管的飞书会话（`--resume` 续同一对话线，人类入口）与调度器 spawn 的 headless 会话（`claude -p` 每次全新，工作入口）。A 在 headless 会话里处理完委托后，飞书会话「不记得」该过程。
- 已知限制：cc-connect resume 会话不重读 CLAUDE.md，新写入的记忆文件也不自动进入进行中的对话。
- Agent 连续性由此改由三层承载：**控制台事实**（任务树 / a2a 回执 / output，经 aw MCP 工具可查）、**仓库产物**（任务涉及的文件）、**共享规范与记忆文件**（CLAUDE.md / memory，跨会话但仅新会话生效）。这是有意取舍：调度器会话无状态保证行为确定、省 token、不受历史对话污染。
- 会话连续性采用**约定式事实召回**：headless 与飞书会话都可通过远程 `work_read`、Task/A2A 和知识引用读取控制台事实；不合并两条会话线，也不依赖 headless 自报摘要文件。

## 9. 业务事件接入与持续协调

本节定义业务事实如何成为工作、既有工作如何续接，以及确定性规则在其中的唯一路由职责。它不改变 aw-node 采集「只推」、A2A「只拉」和控制台「不做 IM」的既有契约。

### 9.1 Source 适配与 Trigger 事实

业务事件必须由明确的 Source 适配器归一化，不提供一个任何来源都能匿名写入的通用 `/api/trigger` 入口。适配器可以使用已验证回调、出站轮询或进程内领域事件；具体传输由来源决定，不能为接事件而给执行机器新增入站端口。

| 来源 | 典型 Trigger | 接入与授权口径 |
|------|--------------|----------------|
| 项目 Agent 宿主（cc-connect / WorkBuddy） | `work.requested` / `work.aligned` | 只把宿主实际收到且能验证用户身份的显式需求与对齐结论形成 Trigger；不是控制台订阅其他飞书机器人，也不能把 Agent 自报或采集文本当作人的授权 |
| 专用 Bug 机器人 | `bug.submitted` / `bug.feedback_added` / `bug.accepted` / `bug.returned` | 接收其完成拆分、去重后的结构化提交，保留原始反馈、证据附件引用和机器人去重键；项目不清时由机器人先向人澄清，不提交猜测性 project hint；接受/退回必须来自原反馈线程的结构化动作 |
| GitHub / Squadsight | `pr.opened` / `pr.synchronized` / `review.submitted` / `pr.closed` | 仓库与安装实例白名单、外部事件 ID 去重；PR 编号与仓库共同定位业务 Thread。Squadsight 结论只按原职责接入，不由 Router 重演评审 |
| CI / 测试环境 | `check.completed` / `preview.ready` / `preview.failed` | 只关联已登记项目与工作流；成功或失败是验证事实，不自带合并、修复或生产发布权限 |
| 控制台机器人 | 审批回调、已登记指令 | 沿用现有长连接、白名单与 `event_id` 去重；只有登记动作能产生对应授权或状态变化，未命中仍回「不支持」 |
| 内部领域事件 | Task 阶段变化、Run 结束、Outbox 结果 | 在所属事务提交后转为内部 Trigger，用于进展关联和下一步判定；不能把 Agent 自报文本升级为人的显式授权 |

归一化 WorkRequest 至少包含 `source`、`source_event_id`、`kind`、`occurred_at`、`actor`、`project?`、`thread_refs`、`payload`、`refs`，以及可供宿主核验的 `authorization_ref?`。Source Agent 可以用自己的 Skill/Memory 澄清、拆分和去重，但不输出目标 Agent 或猜测性项目提示；`project` 只能来自明确上下文或人的确认。`(source, source_event_id)` 唯一；同一外部事件重推返回已有处置，不重复开工。`payload` 只保存审计所需的最小规范化内容，长文、截图和附件以 `refs` 引用，敏感值在入库前收敛。

**观测不是授权**：`/api/ingest` 的会话、进程、心跳与 token 事件默认只形成观测事实，不能直接创建可执行工作。即使采集内容中出现「请修改」「可以发布」等文本，也必须由可信 Source 与宿主授权规则另行确认，不能靠正文自称获得权限。

### 9.2 单一确定性 Router

所有 Trigger 只经过同一条确定性链路，顺序固定：

1. **准入**：验证 Source 身份、schema、项目/仓库白名单和 actor 可信度；失败记录 `reason_code`，不进入路由。预算与暂停只限制新 Assignment，不阻断 Trigger、CI 结果等事实的持久化与状态回写。
2. **去重**：按 `(source, source_event_id)` 幂等；同一事件重放返回首次处置，不重复创建 WorkItem、Assignment 或 Input。
3. **Thread owner 直通**：存在有效 owner 订阅时关联原工作事项并形成 `worker_inbox(kind=input)`；仍复核原 Mandate、当前策略和事项状态，context 不产生执行权。
4. **RouteRule 派新工**：未归属事件必须命中唯一 Git 版本化 RouteRule。规则只含 `source / kind / project? → work_kind / target_role`；`work_kind` 决定执行 Skill、Mandate 与证据要求，项目注册表把角色解析为已注册 Agent。
5. **未知即交人**：无项目、无规则或多条规则冲突统一 `needs_person`，记录 `no_project / no_route_rule / route_ambiguous` 等原因；一期没有在线 Slow Router、模型评估或基于 Source Memory 的派工。

RouteRule 与 `work_kind` 定义随 Git 评审和版本化，启动时校验并计算 `policy_version`。每次路由在 `work_trigger` 上保存 `disposition`、`reason_code`、`rule_id`、`rule_version`、`work_item_id` 与 `target_agent_id`，因此「为什么派给它」只有一个可重放的答案。人的一次性归属选择可形成事项事件；只有显式保存为规则时才影响后续事件。

Router 的落地结果、`worker_inbox` 与所需外部副作用在同一事务中保存，提交后才由发件箱或执行适配器处理。**入队不等于执行成功**。Router 不是 Agent，不使用 `a2a_send` 伪造发件任务，也不代替承接 Agent 调用 `task_create`。

### 9.3 Thread 订阅、上下文召回与退回

`work_thread` 以 `(source, external_kind, external_key)` 标识同一个 Bug、PR、CI 流程或外部话题。一个业务 Thread 至多有一个有效 owner 订阅；其他关联事项只能作为 context 订阅，避免一次评论扇出成多份执行。

- 订阅续接的是**上下文与原 Mandate 范围**，不是一次新的授权。后续事件形成 Input 后，Worker 判断属于原范围则继续；超范围或归属错误时按单条 Trigger `work_handback(reason)`，不得静默扩权。
- Handback 只释放该 Trigger 的当前归属，不等于退订整个 Thread。确需换 owner 时，撤销旧 owner、建立新 owner、保留退回理由与事项事件必须在一个事务中完成；旧 owner 可保留 context，禁止在两个事项间反复弹跳。
- `work_thread` 与 `a2a_thread` 分开：前者关联外部业务事实，后者保持 Agent 信封、`round`、拉取和 ACK 语义；二者可互相引用，但不合并表和状态机。
- 上下文采用 **Inline & Spill**：标题、当前目标、最近结论和必要约束可内联；长文、历史评论、截图、日志和完整文档只注入短摘要、ID 与读取入口。
- **Chain of Recall** 固定为 `Trigger → work_thread → work_item → task/run → 原始文档、消息或产物引用`。摘要只是派生便利，不是第二事实源；每跳都必须保留可定位引用。
- Agent 通过远程 `work_read` 读取自己承接的事项及允许引用；知道某个引用 ID 不等于有权读取其内容，仍须经过原 Source 的访问控制。

### 9.4 首个真实 Bug 闭环

首个业务验收使用一个真实 Bug，不用演示任务替代，也不要求先建设全部需求治理或主动巡检能力：

1. Bug 机器人完成澄清、拆分和去重后提交 `bug.submitted`；项目必须明确，原始人反馈且预期清楚时形成显式修复 Mandate。
2. 确定性 Router 命中 `bug_fix` 规则，创建 WorkItem、不可变 Mandate 与 `worker_inbox(kind=assignment)`。目标 Agent 通过 `work_read` 读取事项，自行创建 Task，再以 `work_ack(task_id)` 确认承接。
3. Agent 修复并提交 PR，仓库与 PR 编号关联业务 Thread；评审按项目策略执行，但评审结论不是统一的待验收前置条件。后续评论、补充反馈和 CI 事件形成 Input，超范围评论走 Handback。
4. **只有当前 PR head SHA 对应的必需 CI 全部通过**，且 WorkItem 已关联可访问 PR 时，事项才进入 `attention=acceptance`。旧 SHA 的绿色 CI、当前 SHA 的失败 CI 或 Agent 自报完成均不够。
5. 修复结果经原 Bug 机器人回告，人在原反馈线程选择「接受」或「退回修改」。`bug.accepted` 使 WorkItem 进入 `done` 并记录验收引用；`bug.returned` 在同一 WorkItem 上记录理由、返回执行并形成新的 Input，不另建重复事项。
6. A2A 回执 ACK、上游 Task 自动收口、PR 合并、CI 通过和结果回告都不等于人工接受。生产发布仍是独立人工动作，不因任何上述状态自动获得授权。

### 9.5 实质进展与停滞

进展巡检只承认能改变业务判断的证据：新需求/反馈已归属、需求或架构结论确认、Task 阶段变化、有效评审结论、CI/测试结果、可访问产出、人工决策或明确阻塞。进程心跳、会话日志增长、重复模型回复和 Token 增加本身都不是实质进展。

巡检按事项阶段与项目策略判断等待是否超时：等待人的事项不伪装成执行停滞；正常等待不通知；真正无进展时先记录 `stalled` 与证据，可请求一次状态或发出合并提醒，但不得自动修复巡检发现的问题、无限重试或反复打扰。进程存活仍由 launchd 与既有心跳负责，不能用业务 Watchdog 代替进程监督。

## 10. 后台作业

单进程内串行执行，禁止并发跑同一作业。

| 作业 | 触发 | 幂等保证 |
|------|------|----------|
| 索引重建 | 知识写入后延迟 2s 合并，或手动触发 | 以内容哈希比对，未变不重嵌入 |
| 发件箱对账 | 启动时 + 每 2s（与投递轮询同频） | 只处理租约过期项，状态转换带 CAS；独立于推送作业，未配置飞书也运行 |
| `worker_inbox` 租约回收 | 启动时 + 每 2s | 只回收过期租约；按 `id + lease_token` CAS，重投不重复建 Task 或 WorkItem |
| 工作事项进展巡检 | 每 60s | 按 `(work_item_id, progress_revision, rule)` 去重；只记录与提醒，不自动修复或发布 |
| 用量结算 | token 事件到达时 | `(source, sequence)` 唯一 + 内容哈希 |
| aw-node 心跳巡检 | 每 60s | 只标记离线，不追补数据 |
| 待批超时 | 每 10 分钟 | 条件更新 `WHERE status='pending' AND created_at < now-24h` → `rejected`，并通知 |
| 死信巡检 | 每 60s | 只扫 `deadline` 已过的未 ACK 消息，转 `a2a_dead_letter`，不自动重发 |

## 11. 错误码与幂等

| code | HTTP | 场景 |
|------|------|------|
| `UNAUTHORIZED` | 401 | 未登录或会话过期 |
| `FORBIDDEN` | 403 | 已登录但无权操作 |
| `VALIDATION_FAILED` | 422 | 必填缺失、枚举非法、长度越界 |
| `NOT_FOUND` | 404 | 资源不存在（不区分无权访问） |
| `CONFLICT` | 409 | 版本冲突、状态不允许该操作 |
| `RATE_LIMITED` | 429 | 登录失败过多、SSE 连接超限 |
| `UPSTREAM_UNAVAILABLE` | 503 | 飞书 / Teleport 不可达 |

- 校验失败返回**全部**缺失或非法字段，不只报第一个。
- 「不存在」与「无权访问」统一 404，避免枚举。
- 写接口全部要求 `Idempotency-Key`；缺失时 422，不猜测。
