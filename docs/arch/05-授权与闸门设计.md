# 授权与闸门设计

> 创建日期: 2026-10-29
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。表结构见 [02-数据服务设计.md](./02-数据服务设计.md) §3.4。

## 1. 三层模型

「Agent 能做什么」必须同时回答三个问题，缺一层都不成立：

| 层 | 问题 | 机制 | 缺口现状 |
|----|------|------|----------|
| 权限分层 | 谁能做什么 | 公开 / 登录 / 资源访问 / 资源修改 / 高危执行 | 控制台自有控制工具与 Teleport 资源边界分别判定 |
| 身份注入 | Agent 说自己是谁算不算数 | Agent Bearer 证明主体，服务端校验 Task/A2A/WorkItem 归属，文本参数无效 | 首版不引入 `run_token` |
| 调用策略 | 这一次调用该不该放行 | 分类 + 拦截 / 待批 / 放行 + 审计 | 仅覆盖控制台自有控制类 MCP；本机第三方 MCP 与原生工具出界 |

**身份不由 Agent 自述**：`from`、`assignee`、任务归属、A2A 白名单和 WorkItem 归属由控制台根据 Bearer 与数据库校验。Agent 传的 `agent_id`、`role` 不参与判定；Assignment ACK 还必须绑定承接 Agent 自己创建的 Task。

### 1.1 通道边界（A/B/C）

三类通道的分界不在「操作听起来多危险」，而在**凭证从哪来、经过谁、失败时怎么拒**：

| 通道 | 谁发起 | 经过哪个进程 | 凭证形态 | 失败如何拒 |
|------|--------|--------------|----------|-----------|
| **A 只读 API**（一期不实现，契约保留） | Agent 在任务内调工具；或控制台后台作业 | Agent → 控制台自有控制入口（`decide`）→ `adapters` 只读代理 → 外部 API | 无。只读凭据由控制台持有，**不下发给 Agent** | 控制台或上游拒绝 → 以工具错误返回，不降级为 Agent 直连；审计写失败即拒 |
| **B SSH / DB 读写** | Agent 在任务内申请，控制台审批 | Agent → 控制台能力审批 → tbot 签发证书 → Agent 持证书连目标机 | Teleport 短时证书（15 分钟，自动续期） | Teleport 不可达 → **拒绝签发**并标记任务阻塞；证书过期未续 → 连接自然失败，不补发长期密钥 |
| **C 高危不可逆** | Agent 提出，**人**批准 | Agent → 控制台挂起 → 审批卡片（飞书 / 控制台）→ 人确认 → 一次性票据 → 执行 | 一次性票据（绑定 `task_id`，单次有效） | 无人确认 → 300s 超时按 `deny`；票据重放 → 拒绝并告警 |

三条通道的共同前提：

1. **发起者是 Agent，判定者不是**。Agent 只能在任务上下文里提出调用，能不能执行由控制台 `decide()` 与资源边界判定，不由它自述。
2. **凭证按通道下沉**：A 类 Agent 拿不到任何凭证；B 类只拿到目标范围内的短时证书；C 类连证书都要人逐次确认。
3. **拒绝是默认答案**：任一环节不可达（Teleport、审批服务、审计库）都归为拒绝，不存在「先放行后补审计」。

> 控制台自身的 HTTP 会话（人 → 浏览器 → 8787）不属于 A/B/C：它没有资源凭证，鉴权口径见 [01](./01-后端服务设计.md) §3.1。

## 2. 能力模型

一次授权 = 一条 `capability` 记录：

| 字段 | 含义 | 约束 |
|------|------|------|
| `subject` | 谁用（Agent 身份） | 必须已注册 |
| `target` | 对什么（主机 / 数据库 / 云资源） | 必须命中资源白名单 |
| `action` | 做什么（读 / 写 / 执行） | 枚举，不接受自由文本 |
| `scope_json` | 细化范围（路径、命令白名单、库表） | 解析失败即拒绝 |
| `ttl_seconds` | 有效期 | 默认 900，上限 14400 |
| `ticket_id` | Teleport 凭证标识 | 真实证书不落库 |
| `task_id` | 归属任务 | 必须已存在且 `assignee` 为 `subject` 本人；审计可追溯 |
| `status` | `pending` / `issuing` / `active` / `expired` / `revoked` / `rejected` | 状态机单向；`issuing` 是「已批准、正在调 Teleport 签发」的中间态，超 60s 由对账作业收敛 |

TTL 以 **15 分钟为默认**，最长 4 小时；到期前由 tbot 自动续期，续期不改变 `capability` 的原始审批记录。

## 3. 通道分级

| 级别 | 场景 | 实现 | 凭证形态 |
|------|------|------|----------|
| A | 只读 API（云资源查询、监控） | 控制台自建只读代理，不下发凭证给 Agent | 无长期凭证 |
| B | SSH / 数据库读写 | Teleport 短时证书 | 15 分钟，自动续期 |
| C | 高危不可逆操作 | 人必须在场，逐次确认 | 一次性票据 |

**A 类一期不建**：一期没有任何任务需要读云资源 API，先只保留上面这条通道契约（凭证形态与失败口径），代理实现与至少一个真实上游留二期。不做半成品代理——没有真实上游的只读代理只是一个假的安全边界。M2/M3 的任务清单里不出现 A 类实现，二期开工时按本表补。

**生产资源零长期凭证**：所有 B/C 类访问都经 Teleport 签发，Agent 本地不保存**目标资源**的长期凭证。签发使用的私钥由 tbot 在本机生成并随短时证书使用——它是**机器身份**，按密钥管理（权限收敛、可吊销），不等同于长期资源凭证；一次性签发（`--oneshot`）不在本机留任何持久状态。

## 4. Teleport 集成

```
Agent 请求 ──▶ 控制台判定 ──▶ 审批通过 ──▶ tbot 签发 15 分钟证书
                                              │
                                              ▼
                                      Agent 持证书访问目标机
                                              │
                                              ▼
                                      Teleport 会话录制 → 审计事件
```

| 项 | 约定 |
|----|------|
| 角色 | Teleport CE 提供 auth + proxy；tbot 负责签发与续期；node agent 装在目标机 |
| 部署形态 | **独立容器、单机 all-in-one**（auth + proxy 同进程），作为 compose 里独立服务 `teleport`，与 `console` 同网络但互不 import；数据目录挂 `workspace/teleport/`（gitignore），不与会话库混放。18.7.3 已在本地 Docker 验证该形态（127.0.0.1 + 自签 CA 即可跑通签发与 SSH） |
| 版本 | 镜像 tag 钉死到具体补丁版（当前基线 18.7.3）；升级需单独评审（Teleport 跨版本有数据迁移，不走自动跟随 latest） |
| 网络 | **占位（2026-11-09 裁决：Teleport 暂不开工，优先优化 Agent 协作机制）**。原案：独立子域 `tp.example.com` 走独立 tcp 端口（公网入口属部署环境，frp 配置不再由项目交付）。proxy 的 `public_addr` 必须是 node / tbot **实际可达**的地址；容器化时让两者共用 proxy 的网络命名空间或使用服务名，否则注册与签发都会失败 |
| 证书 | `tp.example.com` 复用 frps 上已有的 `*.example.com` 通配证书：私钥 `0600` 挂进容器，只在 Teleport 进程内可见。**取舍**：通配私钥因此存在两台机，换来不必再维护一条 ACME 续期链；若日后拿不到私钥，改用 ACME **DNS-01** 单独签发 `tp.example.com`，不使用自签证书 |
| tbot | 以独立进程运行，持 Teleport 侧的 bot 身份，**只允许签发审批已通过的角色**；不授予 `editor` / `admin`。身份模型：**每个 Agent 一个 bot、每个任务一个 trait（`aw_task_id`）**，任务切换由续期生效；要求证书与任务强绑定时改用每任务一个 bot（一次性签发）。bot 的加入令牌只存哈希；tbot 在本机保存的机器身份是长期秘密，按密钥管理并可吊销 |
| 许可 | Teleport CE 为 **AGPL-3.0**：以独立进程 / 容器运行，本项目只经 HTTP API 与 `tsh`/`tctl` 调用，**不 import 其源码、不静态或动态链接、不改动后分发**；本仓库不与其存在编译期依赖，故不构成衍生作品 |
| 续期 | 由 `--renewal-interval` 驱动；15 分钟 TTL 取约 11 分钟（TTL×3/4），即证书剩余约 25% 时刷新。实测 interval 可配，改 trait 后一个新周期内反映到证书；续期失败即视为过期，且不改变 `capability` 的审批记录 |
| 吊销 | 以 TTL 自然过期为主；主动吊销调用 Teleport API，并在 `capability` 置 `revoked` |
| 审计 | 会话录制保留在 Teleport；控制台只存 `ticket_id` 与判定记录，两边可对账 |
| 故障 | Teleport 不可达时**拒绝签发**，不降级为长期密钥 |

## 5. 审批流

单一审批人（当前仅本人），未来可扩展为专用审批 Agent。

```
申请 ──▶ 待批 ──┬──▶ 批准 ──▶ 签发中 ──┬──▶ 生效 ──▶ 过期 / 吊销
                │                      └──▶ 签发失败 ──▶ 驳回 + 告警
                └──▶ 拒绝 ──▶ 归档
```

| 规则 | 说明 |
|------|------|
| 展示完整 | 卡片与控制台都必须展示 target、action、scope、task、TTL，不允许折叠关键字段 |
| 绑定任务 | 每条授权必须挂 `task_id`；无任务的授权直接拒收。**需要授权的活必须先建单**——单人私聊通常只记 run，但一旦要拿凭证就必须先有任务（需求 §1.2 建单规则第 2 条） |
| 幂等 | 批准 / 拒绝是条件更新（`WHERE status='pending'`），重复提交返回 `applied:false`，副作用只执行一次 |
| 补偿（saga） | Teleport 是外部 HTTP，「改状态」与「签发」**不可能同一事务**。流程为：批准 → `issuing`（写审计）→ 调 Teleport 签发 → 成功置 `active` / 失败置 `rejected` 并告警。`issuing` 停留超过 60s 由后台按 `ticket_id` 对账收敛，**不存在「已批准但永远没凭证」** |
| 防重放 | 飞书长连接由应用凭据认证，入站校验时间戳、`open_id` 白名单与 `event_id` 唯一索引；不使用 Verification Token / Encrypt Key |
| 过期 | 待批超过 24 小时自动置 `rejected`，并通知申请人重新申请 |

> 用户可见的口径：`issuing` 显示「签发中」，`rejected` 显示「签发失败·可重试」。不允许把 `issuing` 呈现成「已生效」。

> **反面参考**：某成熟项目把「审批记录」与「真正提额 / 签发」拆成两个入口，通用 approve 接口只改状态不改实际权限，形成陷阱。本项目合并为一个动作。

## 6. 控制类工具闸门

### 6.1 范围与分类

闸门只覆盖控制台自有 `/mcp` 工具，未知工具名直接拒绝；本机第三方 MCP、Claude Code 原生工具与终端直跑不在覆盖范围内。

| 级别 | 定义 | 处置 |
|------|------|------|
| L0 | 自有只读工具（`a2a_inbox`、`kb_search`、`work_read`、`work_inbox`） | 放行 + 审计 |
| L1 | 写自己的业务账（`task_create/update`、`a2a_send/ack`、`kb_write`、`work_ack/handback`、`work_report/decide`） | 归属与白名单校验后放行 + 审计 |
| L2 | 高危或新增且尚未明确等级的控制工具 | 默认拒绝；如确需引入，另行走人工审批设计 |

`a2a_send` 必须同时满足任务属于调用方、收件方在委派白名单内；`task_create/update` 的 `assignee` 必须是 Bearer 对应 Agent；`kb_write` 只能写 `candidate`；Assignment ACK 必须绑定承接 Agent 自己创建且属于同一 WorkItem 的 Task；`work_decide` 只认上报该 Bug 的机器人（origin 触发 `actor.agent_id` 与 Bearer 一致）。以上判定都在控制台完成，不能靠提示词维持。

### 6.2 不扩展到任意命令与第三方工具

本项目不解析 shell 文本来推断安全性，也不代理执行机上的第三方 MCP。第三方工具若由运行时直接连接，其调用、参数和结果不进入本项目的拦截与审计承诺；这与 Claude Code 原生工具、终端直跑的范围边界一致。一期不做 OS 级沙箱、托盘或进程急停。

### 6.3 判定入口

```ts
type Decision =
  | { verdict: "allow"; level: "L0" | "L1" }
  | { verdict: "deny"; reason: string };

function decide(ctx: ControlContext, call: ToolCall): Decision;
```

- `ControlContext` 由控制台根据 Agent Bearer、目标 Task/WorkItem、委派白名单与当日用量生成；首版不引入 `run_token`，也不信任工具参数中的主体自述。
- 判定顺序：**用量与暂停 → 身份/归属/白名单 → 工具等级**。用量硬停只作用于控制台自有工具与新 Assignment，不代表能停止第三方 MCP、原生工具或正在运行的进程。
- **没有配置上限 = 不限**；配置了但读不出当日用量或读取报错 = `deny`（fail-closed）。任何判定异常同样拒绝，并写原因。
- 拒绝结果作为普通工具错误返回，附可读原因与下一步建议。

### 6.4 控制台执行落点

```
Agent ──HTTPS + Bearer──▶ 控制台 /mcp ──decide(ctx, call)
                                        ├─ allow → 调用对应领域服务
                                        └─ deny  → 返回工具错误，不产生业务副作用
```

- `decide()` 唯一实现在 `src/domain/capability/`，MCP 协议层只负责传输与参数校验，不再存在 `src/mcp/proxy/` 或本地 wrapper。
- 每次判定先写 `tool_call_log`，写失败即拒绝执行；`capability_id` 由控制台根据实际命中授权写入，不经过 proxy 的 `AW_GRANTS`。
- 自有工具列表是封闭集合，第三方 MCP 不进入 `tools/list`，也不被转发。控制台不可达时由客户端失败重试，不降级为本地代理。

### 6.5 业务路由与续接的授权不变量

确定性 Router 位于「是否以及由谁继续一件工作」的规则层，`decide()` 位于「这一次自有控制工具调用能否执行」的应用层，Teleport 位于资源层。三者不能互相替代：WorkItem 获得业务 Mandate，不等于获得 B/C 类资源能力；持有资源凭证，也不等于可以扩大工作范围。

1. **Router 无执行特权**：只按 Thread owner 与 Git RouteRule 落地，不携带资源凭证，不直接执行 Shell、GitHub 写接口或生产部署；一期没有在线模型路由。
2. **授权强度由宿主判定**：可信 Source、人的显式请求、人的确认和书面项目规则分别形成可审计依据。消息正文、引用文档、Source Memory、Agent 自报和模型输出都不能自述为授权。
3. **续接不扩权**：有效 Thread owner 可免去新工作路由，但每次续接仍复核原 Mandate、当前 `policy_version`、项目策略和预算。超范围事件由 Worker Handback，不得借原 Thread 自动放行。
4. **巡检与 Bug 不混权**：人主动反馈且预期明确的 Bug 可直接进入修复与验证；巡检只能形成建议与人工确认，未经确认不得修改。
5. **质量策略不可被路由改写**：阻塞式 PR 只能由 Squadsight 评审、复审和放行；非阻塞式由 Agent B 承接。两类均最多三轮，三轮届满不等于通过。
6. **生产发布独立确认**：需求、Bug、Task、PR、CI、A2A ACK 或 WorkItem 人工接受均不产生生产发布权限，生产动作仍走 C 类一次性人工确认。
7. **预算与暂停优先**：每次新 Assignment 和自有控制工具调用前检查 Token 硬停和全局暂停；已超预算或暂停时不开新工作，但仍接收事实与验证结果。该能力不冒充进程急停。
8. **旧配置不得覆盖新策略**：策略变化、事项换绑、人停止或授权吊销后，未落地 Assignment/Input 必须按当前 `policy_version` 复核；旧版本规则只能用于解释历史，不能覆盖新结论。

路由与落地审计至少保存 Trigger 引用、Mandate、RouteRule ID/work_kind/Git 版本、目标事项 / Agent、disposition 与 reason_code。审计失败时不落地路由副作用，与「无审计即不授权」保持一致。

## 7. 审计

| 事件 | 记录内容 |
|------|----------|
| 申请 | 申请人、目标、动作、范围、任务、时间 |
| 决定 | 批准 / 拒绝、决定人、理由 |
| 签发 | `ticket_id`、有效期 |
| 使用 | 调用、目标、结果（成功 / 失败 / 拒绝） |
| 吊销 / 过期 | 方式（主动 / 自然）、时间 |
| 业务路由 | Trigger 与证据引用、Mandate、RouteRule ID/work_kind/Git 版本、目标事项 / Agent、disposition、reason_code |
| 续接 / 退回 | 业务 Thread、原 / 新事项、原 Mandate 复核结果、Handback 理由与操作者 |

资源授权与工具审计记录 append-only，按各自保留策略保存，并可经 `task_id` 追溯到具体任务、与 Teleport 侧录像按 `ticket_id` 对账。业务路由发生在建 Task 之前时，以 `trigger_id` / `work_item_id` / `rule_id + rule_version` 追溯，禁止为了审计整齐伪造 `task_id`。

**`task_id` 怎么落到 Teleport 侧**（否则「可追溯」只是口号）：

1. 签发前，控制台把 `task_id` 写进 bot 的 traits（`aw_task_id`）。证书扩展由 role 的 `options.cert_extensions` 在签发时插值写入：`{type: ssh, mode: extension, name: aw-task-id, value: "{{ external.aw_task_id }}"}`。**模板必须用 `external.*`**——`internal.*` 不参与插值，会原样留成字面量。tbot 只持 bot 身份并申请签发，**不写 label**。控制台在自己的事务里记录 `ticket_id`；两处同源但不同事务域，这正是需要按 `ticket_id` 对账的原因。
2. Agent 侧的 `AW_TASK_ID` 环境变量只作业务标识透传，**不参与授权判定**，也改不了证书内容（证书只认 bot traits）。
3. 归因读 Teleport `session.start` 事件的 `user_traits.aw_task_id`（实测存在），查询链路固定为 `capability(task_id) → ticket_id → Teleport session.start(sid) → 录像`；两边的 `ticket_id` 必须对得上，对不上即视为审计缺口并告警。证书扩展用于连接时刻校验，**不作为归因来源**。**已知窗口**：改 trait 后审计立即反映新值，证书要等下一次续期——要求两者强一致时使用每任务一个 bot。

**签发时序约束**（M2-2 实测）：`tctl` 写入的 bot traits 是**异步**同步到 Teleport user 的，证书插值读的是 user；同步未完成就签发会把 `{{ external.* }}` 原样写进证书（实测同步约 229ms，轮询 `tctl get user/bot-<name>` 可消除）。因此控制面不得把「traits 写入成功」当作「证书已带新身份」：批准后的 `issuing` 只表示已向 Teleport 提交变更，「生效」只能由对账（证书扩展或 `session.start.user_traits`）确认。M2-3 的 60s 收敛与 M2-7 的对账都按此口径实现。

### 7.1 对账实现（M2-7）

归因链的前两跳落在数据库内，第三跳读 Teleport 审计日志：

- **`tool_call_log.capability_id`**：控制台自有控制工具命中已生效授权时，由 `decide()` 返回并写入对应 `capabilityId`。身份来自 Agent Bearer，任务与授权归属由控制台查询校验；L0/L1 直通与非授权调用该列仍为 `null`，不再使用 proxy 的 `AW_GRANTS`。
- **Teleport 侧**：控制台按 `TELEPORT_AUDIT_LOG_PATH` 读 `events.log`（JSONL），只取 `event === "session.start"`，从 `user_traits.aw_task_id[0]` / `aw_ticket_id[0]` 与 `sid` 还原会话。该路径未配置时不启动作业，只记 warn，接口仍可查（空列表），**不伪造缺口**；文件不可读则整轮失败记 error，同样不落假缺口。
- **对账作业**：`src/domain/capability/audit-reconcile.ts` 每 5 分钟跑一轮，窗口为近 24 小时。正向逐条核对 `tool_call_log → capability.ticket_id → session.start`，反向遍历会话找库里查不到票据的连接。三类缺口落 `audit_reconcile_gap`（表结构见 [02](./02-数据服务设计.md)）：`missing_session`（有票据无会话，含 `ticket_id` 为空的防御分支）、`ticket_mismatch`（票据命中但 `aw_task_id` ≠ `capability.task_id`）、`orphan_session`（Teleport 侧有会话而库中无票据）。缺口表 append-only（触发器拦 UPDATE/DELETE），`dedup_key` 保证重跑幂等。
- **查询**：`GET /api/audit/gaps` 需会话鉴权，支持 `kind` 过滤与键集分页，返回缺口列表供控制台排查；告警出口（飞书通知）留待后续通知作业。

## 8. 失败模式

| 故障 | 行为 |
|------|------|
| Teleport 不可达 | 拒绝签发，任务标记阻塞并通知 |
| 审批服务超时 | 保持 `pending`，不自动批准 |
| 分类器异常 | 按 L2 拦截 |
| 审计写失败 | **拒绝执行**——无审计即不授权 |
| 时钟漂移 | 凭证与回调均以服务器时间为准，客户端时间只用于展示 |
| 会话绕开托管启动（终端直跑） | 不受拦截、不推事件；采集侧按 [04](./04-采集器设计.md) §4 档 3 处理且不计入 `unattributed_streams`，不静默归属 |
| aw-node 被强杀 | 视为该执行机离线；launchd 拉起后恢复采集断点与调度锁，未 ACK 工作由控制面租约回收 |
| 无项目 / 无规则 / 规则冲突 | 保留 Trigger 并转 `needs_person`；不调用模型、不自动选择目标 |
| 旧 Assignment/Input 遇到策略变化 | 按当前 `policy_version` 复核，旧规则版本只保留用于历史解释 |
| Thread 归属冲突 | 停止自动续接并转人工；不多头执行、不反复换绑 |
| 巡检发现问题 | 只通知并请求确认；未经确认不修，生产发布仍需另一次独立确认 |

## 9. 与新基线验收的对应

| 交付标准 | 支撑点 | 口径 |
|----------|--------|------|
| 生产资源零长期凭证 | 全部 B/C 访问经 Teleport 短时证书 | 全量 |
| 自有控制工具判定与审计 | 控制台 `/mcp` 封闭工具集、Bearer、归属校验、无审计不执行 | 仅自有控制类 MCP；第三方 MCP、原生工具与终端直跑均出界 |
| TTL 15 分钟且自动续期 | tbot 按 renewal interval 续期（15m TTL 取约 11m，剩余约 25%） | 全量 |
| 审计可追溯 task_id | `session.start.user_traits.aw_task_id` + `capability.ticket_id` + append-only 审计表 | 按 `ticket_id` 双向对账 |
