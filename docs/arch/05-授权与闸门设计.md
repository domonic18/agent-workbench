# 授权与闸门设计

> 创建日期: 2026-10-29
> 上位文档: [00-总体架构设计.md](./00-总体架构设计.md)。表结构见 [02-数据服务设计.md](./02-数据服务设计.md) §3.4。

## 1. 三层模型

「Agent 能做什么」必须同时回答三个问题，缺一层都不成立：

| 层 | 问题 | 机制 | 缺口现状 |
|----|------|------|----------|
| 权限分层 | 谁能做什么 | 公开 / 登录 / 资源访问 / 资源修改 / 高危执行 | **缺** |
| 身份注入 | Agent 说自己是谁算不算数 | 宿主注入运行上下文，文本参数无效 | **缺** |
| 调用策略 | 这一次调用该不该放行 | 分类 + 拦截 / 待批 / 放行 + 审计 | 半成品：cc-connect 只有审批开关、默认 full-access，覆盖面不足，需重建 |

**身份不由 Agent 自述**：运行上下文（owner、任务、会话、能力清单）由宿主在投递时注入。Agent 传的 `agent_id`、`role` 只作为日志字段，不参与任何判定。

### 1.1 通道边界（A/B/C）

三类通道的分界不在「操作听起来多危险」，而在**凭证从哪来、经过谁、失败时怎么拒**：

| 通道 | 谁发起 | 经过哪个进程 | 凭证形态 | 失败如何拒 |
|------|--------|--------------|----------|-----------|
| **A 只读 API**（一期不实现，契约保留） | Agent 在任务内调工具；或控制台后台作业 | Agent → MCP proxy（`decide`）→ `adapters` 只读代理 → 外部 API | 无。只读凭据由代理进程持有，**不下发给 Agent** | 代理不可达或上游拒绝 → 以工具错误返回，不降级为 Agent 直连；审计写失败即拒 |
| **B SSH / DB 读写** | Agent 在任务内申请，控制台审批 | Agent → MCP proxy（`decide`）→ 控制台能力审批 → tbot 签发证书 → Agent 持证书连目标机 | Teleport 短时证书（15 分钟，自动续期） | Teleport 不可达 → **拒绝签发**并标记任务阻塞；证书过期未续 → 连接自然失败，不补发长期密钥 |
| **C 高危不可逆** | Agent 提出，**人**批准 | Agent → 控制台闸门挂起 → 审批卡片（飞书 / 控制台）→ 人确认 → 一次性票据 → 执行 | 一次性票据（绑定 `task_id`，单次有效） | 无人确认 → 300s 超时按 `deny`；票据重放 → 拒绝并告警 |

三条通道的共同前提：

1. **发起者是 Agent，判定者不是**。Agent 只能在任务上下文里提出调用，能不能执行由 proxy 判定，不由它自述。
2. **凭证按通道下沉**：A 类 Agent 拿不到任何凭证；B 类只拿到目标范围内的短时证书；C 类连证书都要人逐次确认。
3. **拒绝是默认答案**：任一环节不可达（Teleport、审批服务、审计库）都归为拒绝，不存在「先放行后补审计」。

> 控制台自身的 HTTP 会话（人 → 浏览器 → 8787）不属于 A/B/C：它没有资源凭证，鉴权口径见 [01](./01-后端服务设计.md) §3.1。

## 2. 能力模型

一次授权 = 一条 `capability` 记录：

| 字段 | 含义 | 约束 |
|------|------|------|
| `subject` | 谁用（Agent 身份） | 必须已注册 |
| `target` | 对什么（主机 / 数据库 / 云资源） | 必须命中资源白名单 |
| `action` | 做什么（读 / 写 / 执行） | 枚举，不接受自由文本 |
| `scope_json` | 细化范围（路径、命令白名单、库表） | 解析失败即拒绝 |
| `ttl_seconds` | 有效期 | 默认 900，上限 14400 |
| `ticket_id` | Teleport 凭证标识 | 真实证书不落库 |
| `task_id` | 归属任务 | 必须已存在且 `assignee` 为 `subject` 本人；审计可追溯 |
| `status` | `pending` / `issuing` / `active` / `expired` / `revoked` / `rejected` | 状态机单向；`issuing` 是「已批准、正在调 Teleport 签发」的中间态，超 60s 由对账作业收敛 |

TTL 以 **15 分钟为默认**，最长 4 小时；到期前由 tbot 自动续期，续期不改变 `capability` 的原始审批记录。

## 3. 通道分级

| 级别 | 场景 | 实现 | 凭证形态 |
|------|------|------|----------|
| A | 只读 API（云资源查询、监控） | 控制台自建只读代理，不下发凭证给 Agent | 无长期凭证 |
| B | SSH / 数据库读写 | Teleport 短时证书 | 15 分钟，自动续期 |
| C | 高危不可逆操作 | 人必须在场，逐次确认 | 一次性票据 |

**A 类一期不建**：一期没有任何任务需要读云资源 API，先只保留上面这条通道契约（凭证形态与失败口径），代理实现与至少一个真实上游留二期。不做半成品代理——没有真实上游的只读代理只是一个假的安全边界。M2/M3 的任务清单里不出现 A 类实现，二期开工时按本表补。

**生产资源零长期凭证**：所有 B/C 类访问都经 Teleport 签发，Agent 本地不保存**目标资源**的长期凭证。签发使用的私钥由 tbot 在本机生成并随短时证书使用——它是**机器身份**，按密钥管理（权限收敛、可吊销），不等同于长期资源凭证；一次性签发（`--oneshot`）不在本机留任何持久状态。

## 4. Teleport 集成

```
Agent 请求 ──▶ 控制台判定 ──▶ 审批通过 ──▶ tbot 签发 15 分钟证书
                                              │
                                              ▼
                                      Agent 持证书访问目标机
                                              │
                                              ▼
                                      Teleport 会话录制 → 审计事件
```

| 项 | 约定 |
|----|------|
| 角色 | Teleport CE 提供 auth + proxy；tbot 负责签发与续期；node agent 装在目标机 |
| 部署形态 | **独立容器、单机 all-in-one**（auth + proxy 同进程），作为 compose 里独立服务 `teleport`，与 `console` 同网络但互不 import；数据目录挂 `workspace/teleport/`（gitignore），不与会话库混放。18.7.3 已在本地 Docker 验证该形态（127.0.0.1 + 自签 CA 即可跑通签发与 SSH） |
| 版本 | 镜像 tag 钉死到具体补丁版（当前基线 18.7.3）；升级需单独评审（Teleport 跨版本有数据迁移，不走自动跟随 latest） |
| 网络 | 独立子域 `tp.example.com`，走 frpc 第二条规则（`tcp 8443 → 443`）；控制台是 `aw.example.com → 8787`，两条规则互不复用。proxy 的 `public_addr` 必须是 node / tbot **实际可达**的地址；容器化时让两者共用 proxy 的网络命名空间或使用服务名，否则注册与签发都会失败 |
| 证书 | `tp.example.com` 复用 frps 上已有的 `*.example.com` 通配证书：私钥 `0600` 挂进容器，只在 Teleport 进程内可见。**取舍**：通配私钥因此存在两台机，换来不必再维护一条 ACME 续期链；若日后拿不到私钥，改用 ACME **DNS-01** 单独签发 `tp.example.com`，不使用自签证书 |
| tbot | 以独立进程运行，持 Teleport 侧的 bot 身份，**只允许签发审批已通过的角色**；不授予 `editor` / `admin`。身份模型：**每个 Agent 一个 bot、每个任务一个 trait（`aw_task_id`）**，任务切换由续期生效；要求证书与任务强绑定时改用每任务一个 bot（一次性签发）。bot 的加入令牌只存哈希；tbot 在本机保存的机器身份是长期秘密，按密钥管理并可吊销 |
| 许可 | Teleport CE 为 **AGPL-3.0**：以独立进程 / 容器运行，本项目只经 HTTP API 与 `tsh`/`tctl` 调用，**不 import 其源码、不静态或动态链接、不改动后分发**；本仓库不与其存在编译期依赖，故不构成衍生作品 |
| 续期 | 由 `--renewal-interval` 驱动；15 分钟 TTL 取约 11 分钟（TTL×3/4），即证书剩余约 25% 时刷新。实测 interval 可配，改 trait 后一个新周期内反映到证书；续期失败即视为过期，且不改变 `capability` 的审批记录 |
| 吊销 | 以 TTL 自然过期为主；主动吊销调用 Teleport API，并在 `capability` 置 `revoked` |
| 审计 | 会话录制保留在 Teleport；控制台只存 `ticket_id` 与判定记录，两边可对账 |
| 故障 | Teleport 不可达时**拒绝签发**，不降级为长期密钥 |

## 5. 审批流

单一审批人（当前仅本人），未来可扩展为专用审批 Agent。

```
申请 ──▶ 待批 ──┬──▶ 批准 ──▶ 签发中 ──┬──▶ 生效 ──▶ 过期 / 吊销
                │                      └──▶ 签发失败 ──▶ 驳回 + 告警
                └──▶ 拒绝 ──▶ 归档
```

| 规则 | 说明 |
|------|------|
| 展示完整 | 卡片与控制台都必须展示 target、action、scope、task、TTL，不允许折叠关键字段 |
| 绑定任务 | 每条授权必须挂 `task_id`；无任务的授权直接拒收。**需要授权的活必须先建单**——单人私聊通常只记 run，但一旦要拿凭证就必须先有任务（需求 §1.2 建单规则第 2 条） |
| 幂等 | 批准 / 拒绝是条件更新（`WHERE status='pending'`），重复提交返回 `applied:false`，副作用只执行一次 |
| 补偿（saga） | Teleport 是外部 HTTP，「改状态」与「签发」**不可能同一事务**。流程为：批准 → `issuing`（写审计）→ 调 Teleport 签发 → 成功置 `active` / 失败置 `rejected` 并告警。`issuing` 停留超过 60s 由后台按 `ticket_id` 对账收敛，**不存在「已批准但永远没凭证」** |
| 防重放 | 飞书入站校验来源 token + 时间戳 + `event_id` 唯一索引去重（不启用加密，不做验签） |
| 过期 | 待批超过 24 小时自动置 `rejected`，并通知申请人重新申请 |

> 用户可见的口径：`issuing` 显示「签发中」，`rejected` 显示「签发失败·可重试」。不允许把 `issuing` 呈现成「已生效」。

> **反面参考**：某成熟项目把「审批记录」与「真正提额 / 签发」拆成两个入口，通用 approve 接口只改状态不改实际权限，形成陷阱。本项目合并为一个动作。

## 6. 工具调用闸门

### 6.1 分类

| 级别 | 定义 | 处置 |
|------|------|------|
| L0 | 只读、无副作用（读文件、查询） | 放行 + 记账 |
| L1 | 可逆写（工作区内文件，或控制台自身的记录写，如 `a2a.ack`） | 放行 + 审计 |
| L2 | 高危 / 不可逆（越界写、删除、执行任意命令、网络外发） | 拦截，转人工审批 |
| 未知 | 无法分类 | 按 L2 处理（fail-closed） |

**L0 是白名单，不是「看起来无害就放行」**。清单包含 `fs.read`（工作区内）、`db.query`（只读）、`kb.search`、`a2a.inbox`（拉取，见 [01](./01-后端服务设计.md) §5.2）。其中 `kb.search` 是 Agent 获取知识的唯一入口，必须常驻放行——否则「知识第二次不重复解释」的验收无法成立。清单外的一律按 L2 走审批。

**L1 是「写自己的账」**：`task.create`（`assignee` 恒为调用方；带 `parent_task_id` 时父任务必须是调用方自己的、且不成环）、`task.update`（只能改自己的任务）、`a2a.send`、`a2a.ack`、`kb.write`（对应 MCP 工具名 `task_create` / `task_update` / `a2a_send` / `a2a_ack` / `kb_write`，闸门侧统一用点分名）。这五类要么只写控制台自己的记录，要么只写知识目录内的候选文件——`kb.write` 的 `status` 由服务端强制为 `candidate`，Agent 无法写 `active`，采纳只能人工（见 [01](./01-后端服务设计.md) §5.2）。都不触达外部资源，故放行 + 审计。但 `a2a.send` 放行前要多两道校验，任一不满足即 `deny`：

1. **任务归属**：`task_id` 必须是调用方自己的已存在任务。没有任务就没有 A2A——这是「谁干活谁建单」能落地的地方，不靠提示词约束。
2. **委派白名单**：`to` 必须在 `agent.allowed_targets_json` 内（默认 `[]`，即不可向任何 Agent 发消息）。拒绝时错误信息列出该 Agent 当前可达的目标，便于申请人到控制台开通（字段与维护权限见 [02](./02-数据服务设计.md) §3.7）。

白名单由控制台会话维护，Agent 的 Bearer 无权修改自己的名单；否则「谁能找谁」由被约束方自定，白名单形同虚设。

### 6.2 不放行「解析 shell 文本」

调研结论：靠解析命令行文本来判定安全性是**不可靠的**。实测同类实现（参数级策略）可被以下方式绕过：

- 解释器：`python3 -c`、`node -e`、`bash -c`、`sh -c`
- 下载执行：`curl -o`、`wget`、`git clone` 到任意路径
- 目录切换：`cd /etc && rm ...`（不跟踪每段 cwd）
- 包装器：`timeout 10 rm ...`、`nice -n 10 rm ...`（参数被误认为命令名）
- 间接执行：`find -exec`、`sed -n '1w file'`、`awk -f script`
- 非路径工具：环境变量写入；以及某些实现里 MCP 工具在工作区模式下完全不过闸
- 失败开放：解析异常时放行

因此本项目**不把文本解析当安全边界**：闸门只按登记的工具名与等级判定（未知按 L2），不解析参数文本。

**Claude Code 原生工具不在职责边界内**（2026-10-31 用户裁决）：原计划的「托管权限规则 + `PreToolUse` hook」不实施。原生工具以自由文本命令行执行，上述绕过面无法可靠收敛；控制台的核心是 Agent 间协作与外部资源（尤其生产环境）的授权，MCP 通道是唯一受控的工具入口。

**一期不做 OS 级沙箱**：`sandbox-exec` 需要控制 Claude Code 的启动命令，而 cc-connect 1.5.0 不提供启动命令覆盖，只能在 PATH 上做 shim——cc-connect 升级即失效，比没有沙箱更危险。终端直跑会话不受拦截，作为范围外缺口记入 [06](./06-架构评审记录.md) O6。

### 6.3 判定入口

```ts
type Decision =
  | { verdict: "allow"; level: "L0" | "L1" }
  | { verdict: "require_approval"; level: "L2"; reason: string }
  | { verdict: "deny"; reason: string };

function decide(ctx: RunContext, call: ToolCall): Decision;
```

- `RunContext` 由宿主注入，包含 `agent_id`、`task_id`、能力清单、工作区根、**当日已用 token 与日上限余量**，**不来自工具参数**。
- 判定顺序：**用量硬停 → 能力/白名单 → 等级**。用量先判，任何工具调用（含 L0 只读）在超日上限后一律 `deny`，否则「到顶停止」只能挡住写操作、挡不住继续烧 token 的读循环。
- 用量判定由 proxy 前置执行（M4-1 交付）。**没有配置上限 = 不限**（放行）；**配置了但读不出当日用量或读取报错 = `deny`**（fail-closed）。两者不可混同，不能因为查不到就当成没上限。
- 任何异常一律 `deny`，并记录原因；不允许 fail-open。
- 拒绝结果作为普通工具错误返回给模型，附可读原因与下一步建议（申请哪类能力 / 今日还剩多少 token）。

### 6.4 执行落点

`decide()` 必须由**唯一实现**提供，由 MCP proxy 调用（2026-10-31 裁决：原生工具通道取消，不再有第二个执行点），否则闸门只是文档。候选与裁决：

| 候选落点 | 结论 | 理由 |
|----------|------|------|
| cc-connect 前置 | 否 | 只管消息层，工具调用根本不经过它；且它绑定一种接入方式，换个 Agent 实现闸门就失效 |
| Claude Code hooks | **否（已取消）** | 只覆盖部分事件、各原生工具分别触发，形不成唯一入口；原计划作为第 2 层拦截点，2026-10-31 用户裁决原生工具不在职责边界内，M2-6 取消，不再实施 |
| 沙箱（`sandbox-exec` / 容器） | **不入一期** | 只能限制能力边界，回答不了「这一次该不该放行」；且 cc-connect 不提供启动命令覆盖，无法把 Claude Code 放进去，PATH shim 随升级失效。原生工具既不在职责边界内，也不设系统边界隔离 |
| **MCP proxy** | **选定** | 模型与工具之间唯一必经路径，与 Agent 实现解耦；可注入 `RunContext`、可挂起待批、可强制审计 |

本项目选定 **MCP proxy**：

```
模型 ──工具调用──▶ MCP proxy ──decide(ctx, call)──┬── allow  ──▶ 目标工具 / MCP server
                                                   ├── require_approval ──▶ 挂起待批
                                                   └── deny   ──▶ 工具错误返回，不触达目标
```

| 项 | 约定 |
|----|------|
| 为什么是 proxy | 所有 MCP 工具调用必经此处；Claude Code hook 只能覆盖部分事件；cc-connect 前置只管消息层 |
| 上下文 | `RunContext` 由 proxy 注入；模型传入的 `agent_id` / `role` 一律丢弃 |
| 审批挂起 | 挂起有超时（默认 300s），超时按 `deny`，不无限等 |
| 审计 | 每次判定写 `tool_call_log`（放行 / 待批 / 拒绝都写）；写失败即拒绝执行 |
| 工具命名 | proxy 对外名 `<upstreamId>__<tool>`，Claude Code 再补 `mcp__<server>__`；`toolMap` 把上游工具名映射为闸门点分名，未映射一律按 L2 |
| 落点 | 判定唯一实现在 `src/domain/capability/gate.ts`，协议层在 `src/mcp/proxy/`；M2-5 阶段代理直连控制台库写审计，接入 Agent Bearer 的控制面 API（M2.5-0 / M2.5-5）后改为 HTTP，不再跨进程开库 |
| 覆盖面（必须写进验收） | 仅 MCP 通道，**不宣称「100% 拦截」**；原生工具调用与终端直跑会话列为范围外（见下表） |

**单通道覆盖**（2026-10-31 用户裁决：取消原生工具拦截层）：

| 覆盖 | 落点 | 失效时 |
|----|------|--------|
| 全部 MCP 工具调用 | MCP proxy → `decide()`，判定后写 `tool_call_log` | proxy 不可达 → 工具错误返回，**不降级为直连** |

- Claude Code 原生工具（Bash / Read / Write / Edit …）不在本项目职责边界内：不做托管权限规则、`PreToolUse` hook 与启动自检，也不宣称拦截率。控制台的核心是 Agent 间协作与外部资源授权，工具层过度设计不在本期范围。
- 终端直跑 Claude Code 的会话既不受拦截，也归不到任何已登记项目，采集侧按 [04](./04-采集器设计.md) §4 档 3 处理（不推送、不计入未归因指标），不假装受控。
- 托盘与进程急停**不入一期**：控制台只能拒绝下一次调用，杀不掉正在空转的进程，一期接受该缺口。

> 选型理由：MCP 通道的闸门放在「模型与工具之间」的唯一必经路径上，而不是放在某一个 Agent 的配置里；原生工具通道没有这条路径，且不属于本项目要解决的问题，故整体移出范围。一期不设沙箱，缺口如实记入 [06](./06-架构评审记录.md) O6。

## 7. 审计

| 事件 | 记录内容 |
|------|----------|
| 申请 | 申请人、目标、动作、范围、任务、时间 |
| 决定 | 批准 / 拒绝、决定人、理由 |
| 签发 | `ticket_id`、有效期 |
| 使用 | 调用、目标、结果（成功 / 失败 / 拒绝） |
| 吊销 / 过期 | 方式（主动 / 自然）、时间 |

审计记录 append-only，永久保留；每条都可经 `task_id` 追溯到具体任务，与 Teleport 侧录像按 `ticket_id` 对账。

**`task_id` 怎么落到 Teleport 侧**（否则「可追溯」只是口号）：

1. 签发前，控制台把 `task_id` 写进 bot 的 traits（`aw_task_id`）。证书扩展由 role 的 `options.cert_extensions` 在签发时插值写入：`{type: ssh, mode: extension, name: aw-task-id, value: "{{ external.aw_task_id }}"}`。**模板必须用 `external.*`**——`internal.*` 不参与插值，会原样留成字面量。tbot 只持 bot 身份并申请签发，**不写 label**。控制台在自己的事务里记录 `ticket_id`；两处同源但不同事务域，这正是需要按 `ticket_id` 对账的原因。
2. Agent 侧的 `AW_TASK_ID` 环境变量只作业务标识透传，**不参与授权判定**，也改不了证书内容（证书只认 bot traits）。
3. 归因读 Teleport `session.start` 事件的 `user_traits.aw_task_id`（实测存在），查询链路固定为 `capability(task_id) → ticket_id → Teleport session.start(sid) → 录像`；两边的 `ticket_id` 必须对得上，对不上即视为审计缺口并告警。证书扩展用于连接时刻校验，**不作为归因来源**。**已知窗口**：改 trait 后审计立即反映新值，证书要等下一次续期——要求两者强一致时使用每任务一个 bot。

**签发时序约束**（M2-2 实测）：`tctl` 写入的 bot traits 是**异步**同步到 Teleport user 的，证书插值读的是 user；同步未完成就签发会把 `{{ external.* }}` 原样写进证书（实测同步约 229ms，轮询 `tctl get user/bot-<name>` 可消除）。因此控制面不得把「traits 写入成功」当作「证书已带新身份」：批准后的 `issuing` 只表示已向 Teleport 提交变更，「生效」只能由对账（证书扩展或 `session.start.user_traits`）确认。M2-3 的 60s 收敛与 M2-7 的对账都按此口径实现。

## 8. 失败模式

| 故障 | 行为 |
|------|------|
| Teleport 不可达 | 拒绝签发，任务标记阻塞并通知 |
| 审批服务超时 | 保持 `pending`，不自动批准 |
| 分类器异常 | 按 L2 拦截 |
| 审计写失败 | **拒绝执行**——无审计即不授权 |
| 时钟漂移 | 凭证与回调均以服务器时间为准，客户端时间只用于展示 |
| 会话绕开托管启动（终端直跑） | 不受拦截、不推事件；采集侧按 [04](./04-采集器设计.md) §4 档 3 处理，不静默归属 |
| 执行面进程被强杀 | 视为 Agent 离线；恢复后重新建立代理与上下文 |

## 9. 与 M2 验收的对应

| 交付标准 | 支撑点 | 口径 |
|----------|--------|------|
| 生产资源零长期凭证 | 全部 B/C 访问经 Teleport 短时证书 | 全量 |
| 高危拦截 100% | 未知按 L2；无审计不执行 | **仅 MCP 通道**：由 proxy 全量判定；原生工具与终端直跑会话列为范围外，不宣称拦截率 |
| TTL 15 分钟且自动续期 | tbot 按 renewal interval 续期（15m TTL 取约 11m，剩余约 25%） | 全量 |
| 审计可追溯 task_id | `session.start.user_traits.aw_task_id` + `capability.ticket_id` + append-only 审计表 | 按 `ticket_id` 双向对账 |
