# 【项目】智能体工作台 · 立项书 · v0.2
> 立项日期：2026-10-29 ｜ 提出：诸葛东明 ｜ 承办：随行-小W（WorkBuddy）
> 文档定位：项目启动授权文件。**不是技术方案**，技术方案在《调研报告》与《需求文档》里。
> **v0.2 变更（13:34）**：产品形态定案为「控制台 + 飞书链路双面并存」——控制台管状态与权力，飞书管说话与拍板。控制台不替代飞书，也不被要求承担 IM 功能。
---
## 一、一句话定义
把散落在飞书群、黑板表格、本地脚本里的多 Agent 协作，收进一个可看、可控、可计量的工作台——**人能看到它在干什么，系统能拦住它不该干的事，账上能算清它花了多少。**
---
## 二、为什么现在立项
### 2.1 我们当前的真实状态
现在的协作栈是四件东西拼起来的：cc-connect 负责把 Claude Code 接进飞书，飞书群负责协调，黑板多维表格负责记任务，规范文档负责约束行为。这套东西把 A2A 跑通了，也跑出过真实成果（知识库取数、评测 spec 同步、图谱任务），但三个结构性问题一直没解。
**问题一：状态不可见。** 一个任务派出去之后，除了刷群和盯表格，没有第二种办法知道它跑到哪一步、卡在哪、是不是还在跑。人不在电脑前，等于失控。
**问题二：知识用不上。** 规范写了 v1.4、踩坑记了几十条，但这些知识散在十几个 md 和飞书文档里，Agent 不会主动去读，人也不会每次都翻。同一个错误会重复犯——这不是记性差，是知识没有被做成「可被检索的接口」。
**问题三：约束停在纸面。** R6 把风险分成 L0 只读 / L1 表达 / L2 高危，写得很清楚，但没有任何代码在执行它。高危操作拦不拦得住，取决于当时那个 Agent 有没有老实读规范。
### 2.2 外部信号
- 抖音博主「起点 | 胡扯Ai」用 45 天、3000 元 Token 做出一个 AI-Native 智能体中台，把消息、知识库、任务工作台收进一个后台；他对前作的复盘是「界面好用但链路打不通」——说明难点从来不在 UI
- 开源生态已经成熟到不必从零：消息网关、知识检索、任务编排、可视化四条线各有 10 万星级项目，缺的是把它们按我们的场景缝起来
- 我们自己的定位被外部确认过：PilotDeck 的 README 明确把 WorkBuddy 归为「把 Agent 接进企微飞书 IM 生态」的那一类
**结论：这件事该做，但做法不是重写，是在现有骨架上补三个缺口。**

## 三、项目目标（可衡量）
| 编号 | 目标 | 验收口径 |
|---|---|---|
| O1 | 能力授权（服务器优先） | 线上资源无长期凭证可用；高危操作拦截率 100%；凭证有期限、可吊销、可追溯到任务 |
| O2 | 统一观测与控制台 | 两类 Agent（WorkBuddy / cc-connect+Claude Code）同屏可见；控制台首屏 3 秒内答出「谁在跑、跑到哪、花了多少」；飞书链路保持可用，人手机上一句话仍能下任务与批复 |
| O3 | 沟通可信 | 消息有骨架、内容有模板、轮次有上限；缺字段被拒收，一发通过率 ≥ 60% |
| O4 | 产出可量化 | 任务闭环率、耗时、返工、产出物、成本可按 Agent 与项目统计，周报自动生成 |
| O5 | 知识可沉淀 | 沟通中的方法论被萃取成条目，Agent 每轮自动取；同一问题第二次不再要求人重复解释 |
> **2026-10-29 13:00 修订**：按真实痛点重排——O1 授权权重最高（不可逆），O2 看板次之（决定人敢不敢离开键盘），O3/O4 随后。原「权限代码化」升级为「能力授权」，因为要管的不只是本地工具调用，而是线上服务器与云资源的访问权。
> **2026-10-29 13:03 增补**：新增 O3「沟通可信」。前四条都默认沟通是通的，实际不是——通道混用、消息没有骨架、内容质量靠自觉。沟通机制是其他四条的公共地基。
> **2026-10-29 13:34 增补**：O2 由「统一观测」扩为「统一观测与控制台」。调研四个参考项目后的共同规律是「状态与权力在控制面，IM 只是输入输出口」；我们现在是反的——飞书被当成控制台用。定案：补控制台，保留飞书，两者分工而非替代。

## 四、范围
**做（In Scope）**
- 本地 / 单机优先的部署形态，复用现有飞书协作方式，不改变人的使用习惯
- 工具调用闸门：分类、拦截、审批、审计四件事
- 运行态看板：任务视角 + Agent 视角两张视图
- 知识层：规范与复盘的结构化整理、向量检索、以 MCP 形式暴露给 Agent
- 成本度量：token 记账与预算控制
**不做（Out of Scope）**
- 不做多租户 SaaS，不做对外商业化
- 不重写 Agent 运行时（Claude Code / cc-connect 是资产，不是负担）
- 不做像素风 / 游戏化可视化
- 不追求接入 20+ 消息渠道：人机交互只用飞书，**Agent 之间的往返走系统内通道，不再经过群，也不再建邮件通道**
- 不在此项目内替换 cc-connect（是否替换另行评估，见《调研报告》第七节）
